> **AI 时代项目 VibeCoding 开发流程规范**（2026-06-29 起草，0629 细化版）。
> 一句话：**一人一项目全栈负责，用 AI 工作流把「想法 → 原型 → 设计 → 代码 → 交付」串起来；需求在低成本的原型阶段就和客户磨稳再开发；全程靠「需求 / 交互 / 架构 / 交付」四个评审节点卡质量，靠变更管理保商务，靠度量复盘自迭代。**
> 配套工具链直接复用本仓库工作流技能：`工作流-原型`→`工作流-设计`→`工作流-开发`→`工作流-测试`→`工作流-部署`（必要时 `工作流-规格`、交付前 `/security-review`）。
> ⚠️ **脱敏**：本仓库推送公开 GitHub。客户合同、报价、对接人手机号、服务器凭据、密钥一律不入库，以 `【已脱敏】` 记录；完整信息只进私有知识库 / 受限飞书表。

## 一、总则

### 1.1 目的
统一研发立项与研发流程，把「单人负责制 + 原型驱动 + AI 工作流」固化为可执行规范，做到：需求早收敛、返工少、质量有节点卡控、变更有商务保护、过程可追溯、流程能自迭代。

### 1.2 适用范围
公司全部对外交付类软件项目（官网、系统、小程序、平台）。**满足「立项门槛」（§三）的项目必须走完整立项 + 评审流程**；小改动 / 内部工具走简化流程（§三.4 / §三.5 分级）。

### 1.3 三大核心理念（规范的地基）

> [!abstract] 理念一：单人全栈负责制
> **一个项目一个负责人，不区分工种，一人完成整个项目**（需求、原型、设计、开发、测试、交付、对接客户）。
> 缺的工种由 **AI 工作流 + 项目 AI 机器人** 补齐——负责人是「指挥 + 把关 + 决策」，AI 干「画原型、出设计、写代码、补测试、打部署包」的体力活。
> 风险对冲见 §二.3「巴士因子」——单人制的命门是人一走项目停摆，靠**可接管知识库 + 双人知晓**兜底。

> [!abstract] 理念二：原型驱动，需求在原型阶段收敛
> **把原始需求转成需求文档 + 高保真可交互可访问原型（基于真实数据），让客户上手用、边用边提，反复改到稳定版本，再开始开发。**
> 核心逻辑：**原型阶段改需求 ≈ 改几个 HTML；开发后改需求 = 推翻架构 + 返工。** 把需求博弈前移到最便宜的阶段。
> 反面风险——客户无限改耗死单人——靠 §五阶段② 的 **timebox + 冻结 + 变更管理（§七）** 兜住。

> [!abstract] 理念三：AI 工作流贯穿全生命周期（VibeCoding）
> 每个阶段都有对应 AI 工作流产出标准化交付物，每个交付物对应评审 gate。**人审「方向、逻辑、风险」，AI 保「产出、格式、完整度」——但 AI 产出一律不盲信**，每阶段配「人工必检清单」（§五各阶段）。

### 1.4 流程弹性原则
- **分级不一刀切**：评审、文档深度按项目大小分级（§三.5），大项目走全套，小项目走最小集。
- **能并行就并行**：守住「需求/原型不稳不大规模开发」的底线后，允许阶段内并行（如设计期做选型验证 spike、开发期同步写测试）。
- **可度量、可复盘**：流程本身靠数据迭代（§九）。

## 二、角色与组织

| 角色 | 谁 | 职责 |
|---|---|---|
| **项目负责人（Owner）** | 单人，全栈负责 | 对接客户、跑通六阶段、提交评审、对最终交付负总责 |
| **评审委员会** | **原、韦、明明、鄂 + 该项目需求负责人** | 把守评审节点；需求负责人因熟悉背景固定列席本项目评审 |
| **安全维度责任人** | 委员会内固定 1 人 | 在架构评审、交付评审固定盯安全/合规维度（§六） |
| **决策对口人** | 委员会内指定 1 人 | 与 Owner 双人知晓关键决策，应对巴士因子（§二.3） |
| **项目 AI 机器人** | 每项目 1 个（§八） | 知识库问答、生成/检索交付物、辅助评审准备 |
| **客户** | 甲方对接人 | 重点参与「原型阶段」，使用原型并提迭代意见、书面冻结确认 |

### 2.1 评审分级（防止 4 人委员会成为瓶颈）
评审走多少 gate 按项目级别定，详见 §三.5。核心：**大项目全 4 gate，中项目合并，小项目仅交付评审。**

### 2.2 异步评审 + SLA（评审是「闸」不是「会」）

> [!note] 评审运作规则
> - **三态结论**：过 / 不过 / 有条件过；不过则打回对应阶段，整改后复审。
> - **异步优先**：材料发评审群，限时反馈——
>   - 普通 gate（①②③）：**24h 内反馈，到点沉默视为通过**；
>   - **交付评审④ 必须显式通过，不可沉默通过**（对外交付，红线）。
> - **SLA**：阻塞性问题委员会**即时**响应；普通评审 24h 内给结论，避免单人 Owner 空等。
> - 评审结论（意见 + 决议 + 责任人）写回知识库 `04-评审记录/`，作为追溯与复盘依据。

### 2.3 巴士因子对冲（单人制的命门）
- **关键决策双人知晓**：Owner + 决策对口人（架构选型、客户重大承诺、变更决议）。
- **知识库做到可接管**：以「另一个人靠知识库 + AI 机器人能接手」为验收标准（§八.2），不是只存档。

## 三、立项制度

### 3.1 立项门槛（满足任一即「主要项目」，必须立项）
- 有正式合同 / 报价，或预计投入 ＞ 约定人天阈值（待定，建议先定一个具体数）；
- 对外交付、署公司名；
- 需要多方资源协调或跨期超过约定周期。

### 3.2 立项材料（提交评审委员会，用模板填空，§八.3）
1. **立项申请**：背景、客户、目标、范围边界（做什么 / 不做什么）、项目级别预判；
2. **原始需求**：客户原话、合同/SOW 要点（敏感信息脱敏）；
3. **可行性与投入估算**：技术路线初判、工期、风险；
4. **负责人指派**：明确单一 Owner + 决策对口人。

### 3.3 立项评审（流程入口闸）
评审委员会审「该不该做、谁来做、范围清不清、定什么级别」。通过后：
- 建项目知识库（§八.2）+ 项目 AI 机器人（§八.1）+ 代码仓库；
- 按定级走对应评审路径，进入研发主流程（§五）。

### 3.4 简化流程
不达门槛的小改动 / 内部工具：免立项，保留「需求 → 原型/直接改 → 交付」最小留痕；重大改动仍需走交付评审。

### 3.5 项目分级矩阵

| 级别 | 判定 | 走哪些评审 | 评审方式 | 文档深度 |
|---|---|---|---|---|
| **大型 / 高风险** | 达门槛 + 高金额/高复杂/强合规 | ① ② ③ ④ 全走 | ②③ 同步会，①④ 可异步 | 全套（含 `工作流-规格` SRS） |
| **中型** | 一般立项项目 | ②（并入①）③ ④（合并 ① 至 ②、视情合并 ③）| 异步优先 | 需求文档 + 设计书 |
| **小型 / 简化** | 免立项的小改/内部工具 | 仅 ④ 交付评审 | 异步 | 最小留痕 |

## 四、项目基础设施（开工前必须就位）

> [!info] 立项通过后、需求阶段开始前，三件套必须搭好
> 1. **项目 AI 机器人** —— 挂载本项目知识库，作为 Owner 的「第二大脑」（§八.1）。
> 2. **项目知识库** —— 存原始需求、会议记录、合同、各阶段交付物、评审记录、变更单（§八.2）；**验收标准 = 可接管**。
> 3. **代码仓库 + 脱敏基线** —— 仓库初始化；敏感信息入私有库，公开库一律 `【已脱敏】`。

## 五、研发主流程：六阶段 + 四评审

整体流水线（阶段产出 → 评审 gate）：

```text
立项
  │
  ▼
①需求阶段 ──────────────▶【评审① 需求评审】
  │（工作流-原型:需求提取 / 工作流-规格）
  ▼
②原型阶段 ◀──客户迭代(timebox)──▶【评审② 交互评审】──┐
  │（工作流-原型: 高保真可交互原型, 基于真实数据）      │
  │                                          冻结后变更→§七变更管理
  ▼
③设计阶段 ──────────────▶【评审③ 架构评审】（可并行: 选型 spike）
  │（工作流-设计 / 工作流-规格）
  ▼
④开发阶段（可并行: 同步写测试）
  │（工作流-开发）
  ▼
⑤测试阶段（硬门槛）
  │（工作流-测试）
  ▼
⑥交付部署（强制安全闸 /security-review）──────▶【评审④ 交付评审】
   （工作流-部署）
```

> [!tip] 评审节点 ≠ 阶段数
> 六个执行阶段，但只有四个评审 gate：**需求评审（①后）、交互评审（②后）、架构评审（③后）、交付评审（⑥后）**。开发④、测试⑤不单设 gate——它们的质量由架构评审（事前）和交付评审（事后）双向夹住，再加测试硬门槛（§五⑤）。

---

### 阶段① 需求阶段

| 项 | 内容 |
|---|---|
| **输入** | 原始需求、合同、客户访谈/会议记录 |
| **动作** | 把原始需求结构化为**需求文档**：目标、范围边界、功能清单、角色、关键业务规则、验收口径 |
| **AI 工具** | `工作流-原型`（需求提取与范围界定）；复杂时 `工作流-规格` 出 SRS |
| **产出物** | `01-需求/需求文档.md`（+ 功能定义 / 范围说明） |
| **入库** | `01-需求/` |

> [!check] 退出标准（DoD 硬指标 → 交评审①）
> - [ ] 功能清单逐条编号，无「等等/待定」黑洞
> - [ ] 范围边界写明「**不做什么**」
> - [ ] 每条需求有可度量的验收口径
> - [ ] 角色与关键业务规则明确

> [!warning] AI 产出人工必检（不盲信）
> - AI 提取的需求是否有**臆造/夸大**？逐条对回客户原话/合同。
> - 有没有把客户没说的"合理推断"当成确定需求？标注为待确认。

---

### 阶段② 原型阶段（本规范的重心）

| 项 | 内容 |
|---|---|
| **输入** | 通过评审①的需求文档 |
| **动作** | 产出**高保真、可交互、可访问原型**，**基于真实/拟真数据**；交客户上手用，**边用边提，迭代到稳定版本** |
| **AI 工具** | `工作流-原型`（多文件 Tailwind + 原生 JS 高保真原型） |
| **产出物** | 可访问原型站点（给客户的真链接）、`specs` 功能定义、每轮变更记录、**客户冻结确认** |
| **入库** | `02-原型/` |

> [!danger] 原型阶段纪律（这一阶段决定项目成败与利润）
> - **必须给客户能点的真链接**，不是截图/PPT——可交互、可访问是硬要求。
> - **基于真实数据**搭原型，让客户在贴近真实的场景里发现问题。
> - **timebox**：迭代设上限（建议 ≤ 3 轮 / ≤ 2 周，按项目定），超出即触发**变更管理（§七）**。
> - **demo 节奏**：固定周期 demo（如每周 1 次），杜绝黑盒憋大版本。
> - **客户书面冻结**：原型确认 = 客户**可追溯确认**（飞书/邮件确认 + 截图存 `02-原型/`），口头"行"不算数。
> - **原型未冻结 + 评审② 未过，不进设计/开发。**

> [!check] 退出标准（DoD 硬指标 → 交评审②）
> - [ ] 原型覆盖需求文档全部功能清单（逐条对照）
> - [ ] 关键交互流可点可走通，非死链
> - [ ] 客户书面冻结确认已存档
> - [ ] 本轮及历轮变更记录完整

> [!warning] AI 产出人工必检
> - 原型里 AI 自动生成的交互/字段，是否有客户没要、纯属"补全"的内容？删或标注。
> - 真实数据是否脱敏？原型链接是否泄露敏感信息？

---

### 阶段③ 设计阶段

| 项 | 内容 |
|---|---|
| **输入** | 冻结的原型 + specs 功能定义 + 需求文档 |
| **动作** | 反推**技术设计**：架构、数据流、数据库 ER、接口契约、安全合规、运维部署、非功能性 |
| **AI 工具** | `工作流-设计`（proto-to-design）；接口/数据结构级详设配 `工作流-规格` |
| **产出物** | `03-设计/设计说明书`（Markdown + HTML） |
| **入库** | `03-设计/` |
| **可并行** | 高风险技术点先做**选型验证 spike**（小 demo 验可行），降低架构评审风险 |

> [!check] 退出标准（DoD 硬指标 → 交评审③）
> - [ ] 架构图 / 数据流 / ER / 接口契约齐全
> - [ ] 关键技术选型有理由（必要时附 spike 结论）
> - [ ] 安全合规、运维部署、非功能性指标各有方案
> - [ ] 主要风险有预案

> [!warning] AI 产出人工必检
> - AI 给的架构/选型是否"看着合理实则过度设计"？对小项目是否杀鸡用牛刀？
> - 接口契约与冻结原型是否一致？数据库设计有无明显硬伤（缺索引、字段冗余/缺失）？

---

### 阶段④ 开发阶段

| 项 | 内容 |
|---|---|
| **输入** | 通过评审③的设计 + 冻结原型 |
| **动作** | 落地可运行实现：后端 + 接线后的前端 + 数据库 + 一键启动 |
| **AI 工具** | `工作流-开发`（design-to-code） |
| **产出物** | 本机可真实运行的 MVP/参考实现，提交代码仓库 |
| **可并行** | **同步写测试**（不必等开发全完再测）；前端复用原型 |

> [!warning] AI 产出人工必检（VibeCoding 核心风险）
> - AI 生成代码**看着对≠对**：关键业务逻辑、边界条件、错误处理逐段人审。
> - 是否引入不必要的依赖 / 重复造轮子？是否偏离设计的接口契约？
> - **公开库零明文凭据**：提交前自查。

---

### 阶段⑤ 测试阶段

| 项 | 内容 |
|---|---|
| **输入** | 阶段④的可运行实现 |
| **动作** | 生成并真实执行单元 + 接口测试，拿到通过率与失败归因 |
| **AI 工具** | `工作流-测试`（code-to-test） |
| **产出物** | 测试报告（Markdown + HTML）、缺陷修复记录 |

> [!check] 测试硬门槛（不达不进交付）
> - [ ] 关键路径用例**全部通过**
> - [ ] 整体通过率 ≥ 约定阈值（建议 ≥ 90%，按项目定）
> - [ ] **0 个未归类的疑似 code-bug**（要么修、要么明确记录为已知问题并经 Owner 确认）

> [!warning] AI 产出人工必检
> - 「用例自身 bug」自修；疑似「代码 bug」**回阶段④整改**，不得为了过门槛改弱用例。

---

### 阶段⑥ 交付部署

| 项 | 内容 |
|---|---|
| **输入** | 通过测试的实现 |
| **动作** | 打可移植部署包并净室演练；准备交付物（部署/验收/操作手册）；**跑安全闸** |
| **AI 工具** | `工作流-部署`（app-to-deploy）；**交付前强制 `/security-review`** |
| **产出物** | 部署包（含离线依赖、一键脚本）、交付清单、安全检查结论 |

> [!check] 退出标准（DoD 硬指标 → 交评审④）
> - [ ] 部署包净室演练通过（拷到干净环境能起、健康检查过）
> - [ ] 逐项对照需求/冻结原型验收通过
> - [ ] **`/security-review` 已跑，无未处理高危项**
> - [ ] 部署 / 验收 / 操作手册齐全

## 六、四个评审节点（核心控制点）详解

> [!important] 评审是「闸」不是「会」
> 四个 gate 是研发流程的核心控制点：**不过不放行**。分级（§三.5）+ 异步 + SLA（§二.2）规则统一适用；结论写回 `04-评审记录/`。

### 评审① 需求评审
- **时机**：阶段①后，做原型前。**材料**：需求文档、范围边界、验收口径。
- **重点**：范围清不清？该做的有没有漏？不该做的有没有混进来？验收能不能量？
- **通过标准**：见 §五① DoD。**不过**：打回阶段①。

### 评审② 交互评审
- **时机**：阶段②后，原型经客户书面冻结时。**材料**：可交互原型链接、客户冻结确认、变更记录。
- **重点**：交互流顺不顺、是否覆盖全部需求、客户是否真认可、有无隐藏体验/可行性坑。
- **通过标准**：见 §五② DoD。**不过**：打回阶段②。**这是拦住「带病进开发」最关键的闸。**

### 评审③ 架构评审
- **时机**：阶段③后，写代码前。**材料**：设计说明书（架构/数据/接口/安全/运维/非功能性）。
- **重点**：架构能不能扛、选型合不合理、数据/接口有无硬伤、**安全维度责任人专项过安全合规**、非功能性是否可达。
- **通过标准**：见 §五③ DoD。**不过**：打回阶段③。

### 评审④ 交付评审
- **时机**：阶段⑥后，交付客户前。**材料**：可运行系统 + 测试报告 + 部署包 + 安全检查结论 + 对照原型/需求验收结果。
- **重点**：是否实现冻结原型与需求、质量是否达标、**安全闸是否通过**、部署是否可复现、文档是否齐全。
- **通过标准**：见 §五⑥ DoD。**必须显式通过，不可沉默通过。不过**：打回阶段④/⑤。

| 评审 | 时机 | 卡什么 | 安全维度 | 通过才允许 |
|---|---|---|---|---|
| ① 需求评审 | 需求后 | 范围与验收 | — | 做原型 |
| ② 交互评审 | 原型冻结后 | 客户确认 + 覆盖度 | 原型脱敏 | 做设计 |
| ③ 架构评审 | 设计后 | 架构与选型 | ✅ 安全合规专项 | 写代码 |
| ④ 交付评审 | 部署后 | 实现与质量 | ✅ /security-review | 交付客户 |

## 七、变更管理（原型冻结后 / 商务护城河）

> [!danger] 为什么单列一节
> 原型冻结后客户**一定**还会改——这是必然不是意外。没有变更流程 = 无限免费返工，单人 Owner 被拖死、项目不挣钱。

### 7.1 变更触发
- 原型已冻结（评审② 已过）后，客户提出新增/修改需求；
- 或原型阶段超出 timebox（§五②）仍要继续改。

### 7.2 变更流程
```text
客户提变更
  │
  ▼
Owner 填变更单（§7.3）→ 评估影响（工期/成本/架构）
  │
  ├─ 小变更（不动架构、工时小）→ Owner + 决策对口人确认 → 简化执行 → 入库
  │
  └─ 大变更（动架构/工时大/改合同）→ 回评审②（必要时连带③）
        → 触发报价 / 工期调整 → 客户书面确认 → 执行
```

### 7.3 变更单字段（存 `02-原型/变更/` 或 `99-`）
| 字段 | 说明 |
|---|---|
| 变更内容 | 改什么 |
| 来源 | 谁提的、哪次会议 |
| 影响评估 | 工期 / 成本 / 架构 影响 |
| 处理路径 | 简化执行 / 回评审② |
| 报价工期调整 | 是否加钱加时（脱敏存私有库） |
| 客户确认 | 可追溯确认留痕 |

## 八、AI 机器人与知识库规范

### 8.1 项目 AI 机器人（每项目 1 个）
- **定位**：Owner 的「项目第二大脑」，挂载本项目知识库。
- **职责**：① 答项目背景/需求/决策类问题；② 检索与生成各阶段交付物（接 §五 工作流）；③ 辅助评审准备（汇总材料、对照 DoD/checklist）；④ 沉淀会议纪要与决策。
- **边界**：对外信息脱敏；产出仅辅助，决策与责任在 Owner。

### 8.2 项目知识库（统一目录，验收标准 = 可接管）

```text
项目知识库/
├── 00-合同与商务/      （合同、报价、SOW —— 私有，脱敏后才可外引）
├── 01-需求/            （原始需求、需求文档、范围说明）
├── 02-原型/            （原型站点、specs、各轮反馈、冻结确认、变更/）
├── 03-设计/            （设计说明书：架构/数据/接口/安全/运维）
├── 04-评审记录/        （四个 gate 的材料与结论）
├── 05-开发与测试/      （实现说明、测试报告、缺陷记录）
├── 06-交付与部署/      （部署包、部署手册、验收与操作手册、安全检查结论）
└── 99-会议与决策/      （会议纪要、关键决策、复盘）
```

> [!note] 沉淀纪律 + 喂养标准
> - **当天入库**：客户会议 / 关键决策当天入 `99-`。
> - **阶段交付物**入对应目录，评审结论入 `04-`，变更单入 `02-原型/变更/`。
> - **可接管验收**：阶段末自检「另一个人靠这个库 + AI 机器人能否接手」，不能则补。
> - **机器人保鲜**：每阶段结束同步知识库给 AI 机器人，避免它基于过时信息答题。
> - 商务与凭据类只进私有库；要进公开仓库的先脱敏。

### 8.3 模板与脚手架（降低单人负担）
立项申请、需求文档、设计说明书、评审记录、变更单、交付清单做成 **Templater 模板**（本仓库 `Assistants/Templater/`，复制改名后用，勿改原件）；Owner 填空而非从零写。

## 九、度量与复盘（让流程自迭代）

> [!info] 没有数据，流程就没法优化
> 流程本身要靠项目数据迭代。Owner 在项目收尾汇总指标 + 做一次 retro，沉淀进 `99-`，反哺本规范。

### 9.1 项目级指标（每项目收尾埋点）
- 各阶段实际耗时 vs 估算
- 评审打回次数（按 gate）
- 原型迭代轮数 / 是否超 timebox
- **冻结后变更数**（衡量需求收敛质量）
- 返工率（开发后因需求/设计变动返工的占比）
- 测试通过率、交付后客户缺陷数

### 9.2 复盘（retro）
- 时机：交付评审通过后 1 周内。
- 内容：哪些 gate 有效/形式化、原型阶段是否磨够、AI 工作流哪段省力/哪段坑、变更是否收住。
- 产出：改进项回写本规范（版本号 + 日期），形成闭环。

## 十、质量与脱敏红线

> [!danger] 红线（违反即打回 / 安全事故）
> - **原型未经客户书面冻结 + 评审② 通过，不得进入设计/开发。**
> - **原型迭代超 timebox 仍改，必须走变更管理（§七），不得免费无限返工。**
> - **架构未过评审③，不得写业务代码。**
> - **测试未达硬门槛（§五⑤），不得进交付。**
> - **交付前未跑 `/security-review` 或有未处理高危项，不得交付；评审④ 不可沉默通过。**
> - **公开仓库零明文**：合同金额、客户手机号、服务器/数据库凭据、密钥、Token 一律 `【已脱敏】`，完整信息只进私有库。
> - **凭据不入聊天、不入文档**：统一进私有密码管理器 / 受限飞书表。
