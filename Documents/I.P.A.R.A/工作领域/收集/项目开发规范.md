<progress value="40" max="100" style="width: 100%;"></progress>

> **AI 时代项目 VibeCoding 开发流程规范**（2026-06-29 起草）。
> 一句话：**一人一项目全栈负责，用 AI 工作流把「想法 → 原型 → 设计 → 代码 → 交付」串起来；需求在低成本的原型阶段就和客户磨稳，再进开发；全程靠「需求 / 交互 / 架构 / 交付」四个评审节点卡质量。**
> 配套工具链直接复用本仓库工作流技能：`工作流-原型`→`工作流-设计`→`工作流-开发`→`工作流-测试`→`工作流-部署`（必要时 `工作流-规格`）。
> ⚠️ **脱敏**：本仓库推送公开 GitHub。客户合同、报价、对接人手机号、服务器凭据、密钥一律不入库，以 `【已脱敏】` 记录；完整信息只进私有知识库 / 受限飞书表。

---

## 一、总则

### 1.1 目的
统一研发立项与研发流程，把「单人负责制 + 原型驱动 + AI 工作流」固化为可执行规范，做到：需求早收敛、返工少、质量有节点卡控、过程可追溯。

### 1.2 适用范围
公司全部对外交付类软件项目（官网、系统、小程序、平台）。**满足「立项门槛」（§三）的项目必须走完整立项 + 评审流程**；小改动 / 内部工具可走简化流程（§三.4）。

### 1.3 三大核心理念（规范的地基）

> [!abstract] 理念一：单人全栈负责制
> **一个项目一个负责人，不区分工种，一人完成整个项目**（需求、原型、设计、开发、测试、交付、对接客户）。
> 缺的工种由 **AI 工作流 + 项目 AI 机器人** 补齐——负责人是「指挥 + 把关 + 决策」，AI 干「画原型、出设计、写代码、补测试、打部署包」的体力活。
> 好处：消除跨工种沟通损耗、责任到人、客户单一对接窗口。

> [!abstract] 理念二：原型驱动，需求在原型阶段收敛
> **先把原始需求转成需求文档 + 高保真可交互可访问的页面原型（基于真实数据），让客户上手用、边用边提，反复改到稳定版本，再开始开发。**
> 核心逻辑：**原型阶段改需求的代价 ≈ 改几个 HTML；开发后改需求的代价 = 推翻架构 + 返工。** 把需求博弈前移到最便宜的阶段。

> [!abstract] 理念三：AI 工作流贯穿全生命周期（VibeCoding）
> 每个研发阶段都有对应的 AI 工作流产出标准化交付物，每个交付物对应一个评审 gate。人审「方向、逻辑、风险」，AI 保「产出、格式、完整度」。

## 二、角色与组织

| 角色 | 谁 | 职责 |
|---|---|---|
| **项目负责人（Owner）** | 单人，全栈负责 | 对接客户、跑通六阶段、提交四次评审、对最终交付负总责 |
| **评审委员会** | **原、韦、明明、鄂 + 该项目需求负责人** | 把守四个评审节点；需求负责人因熟悉背景固定列席本项目评审 |
| **项目 AI 机器人** | 每项目 1 个（§七） | 承接知识库问答、生成/检索交付物、辅助负责人决策 |
| **客户** | 甲方对接人 | 重点参与「原型阶段」，使用原型并提迭代意见 |

> [!note] 评审委员会运作
> - 固定成员：**原、韦、明明、鄂**；浮动成员：**当前项目的需求负责人**。
> - 评审采「过 / 不过 / 有条件过」三态；不过则打回对应阶段，整改后复审。
> - 评审结论（含意见与决议）必须写回项目知识库 `04-评审记录/`，作为后续追溯依据。

## 三、立项制度

### 3.1 立项门槛（满足任一即「主要项目」，必须立项）
- 有正式合同 / 报价，或预计投入 ＞ 约定人天阈值；
- 对外交付、署公司名；
- 需要多方资源协调或跨期超过约定周期。

### 3.2 立项材料（提交评审委员会）
1. **立项申请**：项目背景、客户、目标、范围边界（做什么 / 不做什么）；
2. **原始需求**：客户原话、合同/SOW 要点（敏感信息脱敏）；
3. **可行性与投入估算**：技术路线初判、工期、风险；
4. **负责人指派**：明确单一 Owner。

### 3.3 立项评审（流程入口闸）
评审委员会审「该不该做、谁来做、范围清不清」。通过后：
- 建项目知识库（§七.2）+ 项目 AI 机器人（§七.1）+ 代码仓库；
- 正式进入研发主流程（§五）。

### 3.4 简化流程
不达门槛的小改动 / 内部工具：免立项，但仍建议保留「需求 → 原型/直接改 → 交付」最小留痕；是否要评审由 Owner 自判，重大改动仍需走交付评审。

## 四、项目基础设施（开工前必须就位）

> [!info] 立项通过后、需求阶段开始前，三件套必须搭好
> 1. **项目 AI 机器人** —— 挂载本项目知识库，作为负责人的「第二大脑」（§七.1）。
> 2. **项目知识库** —— 存原始需求、会议记录、合同、各阶段交付物、评审记录（§七.2）。
> 3. **代码仓库 + 脱敏基线** —— 仓库初始化；敏感信息入私有库，公开库一律 `【已脱敏】`。

## 五、研发主流程：六阶段 + 四评审

整体流水线（阶段产出 → 评审 gate）：

```text
立项
  │
  ▼
①需求阶段 ──────────────▶【评审① 需求评审】
  │（工作流-原型:需求提取 / 工作流-规格）
  ▼
②原型阶段 ◀──客户迭代──▶【评审② 交互评审】
  │（工作流-原型: 高保真可交互原型, 基于真实数据）
  ▼
③设计阶段 ──────────────▶【评审③ 架构评审】
  │（工作流-设计 / 工作流-规格）
  ▼
④开发阶段
  │（工作流-开发）
  ▼
⑤测试阶段
  │（工作流-测试）
  ▼
⑥交付部署 ──────────────▶【评审④ 交付评审】
   （工作流-部署）
```

> [!tip] 评审节点 ≠ 阶段数
> 六个执行阶段，但只有四个评审 gate：**需求评审（①后）、交互评审（②后）、架构评审（③后）、交付评审（⑥后）**。开发④、测试⑤不单设 gate——它们的质量由架构评审（事前）和交付评审（事后）双向夹住。

---

### 阶段① 需求阶段

| 项 | 内容 |
|---|---|
| **输入** | 原始需求、合同、客户访谈/会议记录 |
| **动作** | 把原始需求结构化为**需求文档**：目标、范围边界、功能清单、角色、关键业务规则、验收口径 |
| **AI 工具** | `工作流-原型`（需求提取与范围界定阶段）；需求复杂时用 `工作流-规格` 出 SRS |
| **产出物** | `01-需求/需求文档.md`（+ 功能定义 / 范围说明） |
| **入库** | 写入知识库 `01-需求/` |
| **退出标准** | 功能清单完整、范围边界清晰、验收口径可度量 → 交**评审①** |

---

### 阶段② 原型阶段（本规范的重心）

| 项 | 内容 |
|---|---|
| **输入** | 通过评审①的需求文档 |
| **动作** | 产出**高保真、可交互、可访问的页面原型**，**基于真实/拟真数据**；交付客户上手使用，**边用边提需求，反复迭代到稳定版本** |
| **AI 工具** | `工作流-原型`（多文件 Tailwind + 原生 JS 高保真原型） |
| **产出物** | 可访问的原型站点（部署一个可点链接给客户）、`specs` 功能定义、原型变更记录 |
| **入库** | `02-原型/`（含每轮客户反馈与版本） |
| **退出标准** | **客户在原型上确认「就按这个做」、原型版本冻结** → 交**评审②** |

> [!warning] 原型阶段的纪律
> - **必须给客户能点的真链接**，不是截图、不是 PPT——可交互、可访问是硬要求。
> - **基于真实数据**搭原型，让客户在贴近真实的场景里发现问题。
> - 把「需求博弈」尽量耗在这一阶段；**原型未冻结，不进设计/开发**。
> - 每轮迭代留痕（改了什么、谁要求的），冻结版本作为后续评审与开发基准。

---

### 阶段③ 设计阶段

| 项 | 内容 |
|---|---|
| **输入** | 冻结的原型 + specs 功能定义 + 需求文档 |
| **动作** | 反推**技术设计**：系统架构、数据流、数据库 ER、接口契约、安全合规、运维部署、非功能性 |
| **AI 工具** | `工作流-设计`（proto-to-design）；需接口/数据结构级详设时配 `工作流-规格` |
| **产出物** | `03-设计/设计说明书`（Markdown + HTML） |
| **入库** | `03-设计/` |
| **退出标准** | 架构自洽、关键技术选型有据、风险有预案 → 交**评审③** |

---

### 阶段④ 开发阶段

| 项 | 内容 |
|---|---|
| **输入** | 通过评审③的设计 + 冻结原型 |
| **动作** | 落地可运行实现：后端 + 接线后的前端 + 数据库 + 一键启动 |
| **AI 工具** | `工作流-开发`（design-to-code） |
| **产出物** | 可在本机真实运行的 MVP/参考实现，提交至代码仓库 |
| **要点** | 复用原型前端；按设计的接口契约实现；不在公开库写入任何凭据 |

---

### 阶段⑤ 测试阶段

| 项 | 内容 |
|---|---|
| **输入** | 阶段④的可运行实现 |
| **动作** | 生成并真实执行单元 + 接口测试，拿到通过率与失败归因 |
| **AI 工具** | `工作流-测试`（code-to-test） |
| **产出物** | 测试报告（Markdown + HTML）、缺陷修复记录 |
| **要点** | 「用例自身 bug」自修；疑似「代码 bug」归类回阶段④整改 |

---

### 阶段⑥ 交付部署

| 项 | 内容 |
|---|---|
| **输入** | 通过测试的实现 |
| **动作** | 打可移植部署包并净室演练；准备交付物（部署手册、验收说明、操作手册） |
| **AI 工具** | `工作流-部署`（app-to-deploy） |
| **产出物** | 部署包（含离线依赖、一键脚本）、交付清单 |
| **退出标准** | 部署可复现、对照需求/原型逐项验收通过 → 交**评审④**，过后正式交付客户 |

## 六、四个评审节点（核心控制点）详解

> [!important] 评审是「闸」不是「会」
> 四个 gate 是研发流程的核心控制点：**不过不放行**。每个 gate 由评审委员会（原、韦、明明、鄂 + 需求负责人）评，结论写回 `04-评审记录/`。

### 评审① 需求评审
- **时机**：阶段①后，做原型前。
- **材料**：需求文档、范围边界、验收口径。
- **重点**：范围清不清？该做的有没有漏？不该做的有没有混进来？验收能不能量？
- **通过标准**：需求完整、边界清晰、验收可度量。
- **不过**：打回阶段①补充/澄清。

### 评审② 交互评审
- **时机**：阶段②后，原型经客户确认冻结时。
- **材料**：可交互原型链接、客户确认记录、原型变更记录。
- **重点**：交互流是否顺、是否覆盖全部需求、客户是否真的认可、有无隐藏的体验/可行性坑。
- **通过标准**：原型完整覆盖需求 + 客户确认 + 无重大体验/可行性风险。
- **不过**：打回阶段②继续迭代。**这是拦住「带病进开发」的最关键一道闸。**

### 评审③ 架构评审
- **时机**：阶段③后，写代码前。
- **材料**：设计说明书（架构 / 数据 / 接口 / 安全 / 运维 / 非功能性）。
- **重点**：架构能不能扛、选型合不合理、数据/接口设计有没有硬伤、安全与运维是否考虑、非功能性指标是否可达。
- **通过标准**：架构自洽、选型有据、风险有预案。
- **不过**：打回阶段③重设计。

### 评审④ 交付评审
- **时机**：阶段⑥后，交付客户前。
- **材料**：可运行系统 + 测试报告 + 部署包 + 对照原型/需求的验收结果。
- **重点**：是否实现了冻结原型与需求、质量是否达标、部署是否可复现、文档是否齐全。
- **通过标准**：逐项对照需求/原型验收通过、测试达标、部署可复现。
- **不过**：打回阶段④/⑤整改后复审。

| 评审 | 时机 | 卡什么 | 通过才允许 |
|---|---|---|---|
| ① 需求评审 | 需求后 | 范围与验收 | 做原型 |
| ② 交互评审 | 原型冻结后 | 客户确认 + 覆盖度 | 做设计 |
| ③ 架构评审 | 设计后 | 架构与选型 | 写代码 |
| ④ 交付评审 | 部署后 | 实现与质量 | 交付客户 |

## 七、AI 机器人与知识库规范

### 7.1 项目 AI 机器人（每项目 1 个）
- **定位**：负责人的「项目第二大脑」，挂载本项目知识库。
- **职责**：① 回答项目背景/需求/决策类问题；② 检索与生成各阶段交付物（接 §五 工作流）；③ 辅助评审准备（汇总材料、对照 checklist）；④ 沉淀会议纪要与决策。
- **边界**：对外信息须脱敏；机器人产出仅作辅助，最终决策与责任在负责人。

### 7.2 项目知识库（统一目录）
每个项目建一个知识库，建议结构：

```text
项目知识库/
├── 00-合同与商务/      （合同、报价、SOW —— 私有，脱敏后才可外引）
├── 01-需求/            （原始需求、需求文档、范围说明）
├── 02-原型/            （原型站点、specs、各轮客户反馈与冻结版本）
├── 03-设计/            （设计说明书：架构/数据/接口/安全/运维）
├── 04-评审记录/        （四个 gate 的材料与结论）
├── 05-开发与测试/      （实现说明、测试报告、缺陷记录）
├── 06-交付与部署/      （部署包、部署手册、验收与操作手册）
└── 99-会议与决策/      （会议纪要、关键决策记录）
```

> [!note] 沉淀纪律
> - 每次客户会议 / 关键决策当天入 `99-会议与决策/`。
> - 每个阶段交付物入对应目录，评审结论入 `04-评审记录/`。
> - 商务与凭据类只进私有库；任何要进公开仓库的内容先脱敏。

## 八、质量与脱敏红线

> [!danger] 红线（违反即打回 / 安全事故）
> - **原型未经客户冻结 + 评审② 通过，不得进入设计/开发。**
> - **架构未过评审③，不得写业务代码。**
> - **未过评审④，不得向客户交付。**
> - **公开仓库零明文**：合同金额、客户手机号、服务器/数据库凭据、密钥、Token 一律 `【已脱敏】`，完整信息只进私有库。
> - **凭据不入聊天、不入文档**：统一进私有密码管理器 / 受限飞书表。

> - [ ] 提交立项材料并通过立项评审

> [!todo] 需求 → 评审①
> - [ ] 原始需求结构化为需求文档（`工作流-原型` / `工作流-规格`）
> - [ ] 范围边界 + 验收口径明确
> - [ ] 通过**需求评审**

> [!todo] 原型 → 评审②
> - [ ] 用 `工作流-原型` 出高保真可交互原型（基于真实数据）
> - [ ] 部署可访问链接交客户使用
> - [ ] 多轮迭代留痕，客户确认 + 版本冻结
