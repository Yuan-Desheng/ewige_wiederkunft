## 一、什么是工作流技能

- **定义**：一族封装好的 Claude Code Skill（多以「工作流-XXX」命名）。每个技能 = 一个有固定输入、固定阶段、固定产出的自主流程，用户给一句话（或一个文件）即可触发它跑完整段工作。
- **与开发规范的关系**：[[项目立项与研发流程规范]] 讲「流程与评审」，本笔记讲「跑流程用的工具」。规范里每个研发阶段，背后就是这里的一个工作流技能。

> [!info] 一个工作流技能在磁盘上由几部分组成（理解这点才能复现）
> 1. **技能触发包**：`~/.claude/skills/<name>/SKILL.md`（+ `assets/ references/ scripts/`）。SKILL.md 的 frontmatter `description` 决定触发词；正文是「何时触发 / 如何运行 / 阶段 / 入参」。
> 2. **工作流引擎脚本**：研发流水线 5 个技能的 SKILL.md 只是「薄壳」，真正逻辑在 `~/.claude/workflows/<name>.js`，由 SKILL.md 里的 `Workflow({ name: '<name>' })` 调起。**复现时这两层都要拷。**
> 3. **市场插件**：docx/xlsx/pdf/duckdb 等能力来自插件市场，走 `/plugin` 重装，不随文件拷贝。
> 4. **平台内置技能**：`deep-research`、`stock-growth-valuation`（选股）、`loop`、`schedule` 等是平台统一下发，磁盘无文件、新账号自带、**无需迁移**。

## 三、安装与复现（到别的机器）

> [!important] 复现 = 三件事
> ① 拷「技能触发包」到 `~/.claude/skills/`；② 拷「工作流引擎脚本」到 `~/.claude/workflows/`；③ 市场插件用 `/plugin` 重装；④ 内置技能（deep-research/选股/loop）免装。

### 3.1 本机现成的迁移包（两个，任选其一/互补）

| 迁移包路径 | 内容 | 安装方式 |
|---|---|---|
| `claude-skills-migration/`（2026-06-29，**最全**） | `skills/`（9 个自定义技能）+ `workflows/`（7 个 .js）+ 插件清单 + `README.md` | `cp -a` 两个目录 |
| `claude-skills-bundle/`（2026-06-18） | `user-skills/`（11 个含流水线 5 壳）+ `plugins/` + `install.sh` | `bash install.sh` 一键 |

> 互补点：`-migration` 有 workflow **引擎 js**（流水线真正逻辑）；`-bundle` 有流水线 5 个**触发壳 SKILL.md** + 离线插件 + 一键脚本。**最稳的做法是两个都拷**，确保「壳 + 引擎 + 插件」齐全。

### 3.2 推荐复现步骤（目标账号本人执行，勿用 sudo / 勿用 work 跑）

```bash
# 0) 确保已装并启动过 Claude Code，~/.claude 已存在
mkdir -p ~/.claude/skills ~/.claude/workflows

# 1) 拷自定义技能 + 工作流引擎（来自最全的 migration 包）
cp -a /path/to/claude-skills-migration/skills/*    ~/.claude/skills/
cp -a /path/to/claude-skills-migration/workflows/* ~/.claude/workflows/

# 2) 补流水线 5 个「触发壳」+ 离线插件（来自 bundle 包，一键脚本会自动落位+修路径）
cd /path/to/claude-skills-bundle && bash install.sh

# 3) 重启 Claude Code，验证
#    输入 /skills 应能看到技能；或直接打触发词「工作流-原型」「工作流-可研」
```

### 3.3 市场插件（不随文件迁移，新机联网重装）
docx / xlsx / pdf / duckdb / example-skills / claude-hud / pyright-lsp 等：在新机 `/plugin` 添加对应市场后安装。市场来源见迁移包 `known_marketplaces.json`、清单见 `installed_plugins.json`。

### 3.4 复现注意（来自实测）
- **认证**：每个用户用自己账号 `claude /login`，**绝不**复制他人 `.credentials.json`。
- **PDF 输入**：本机无 poppler，先 `pip install pypdf` 把 PDF 抽成 .md/.txt 再喂工作流。
- **路径写死**：`webapp-to-installer` 等含写死的 `/home/work` 路径，`install.sh` 会自动 `sed` 改成当前用户家目录；手动拷则需自行替换。
- **权限**：多用户机器上 `chmod -R u+rwX,go-rwx ~/.claude/skills ~/.claude/plugins` 收敛。
- `cp -n` / `cp -a` 同名不覆盖，可安全重复跑。

````text
# 工作流-原型 (req-to-proto)

「需求→原型→设计→开发→测试→部署」闭环的**第 1 环**。从可研/指南/需求文件提炼功能需求并生成高保真 HTML 原型。

## 何时触发
用户说「**工作流-原型**」,或描述"基于可研/指南/需求文件生成功能需求 + 高保真 HTML 原型"。

## 如何运行
调用已保存的 Workflow 脚本(脚本位于 `.claude/workflows/req-to-proto.js`):

```
Workflow({ name: 'req-to-proto', args: { reqFile: '<文档路径>', outDir: 'prototype', style: 'auto' } })
```

## 五个阶段
1. **需求提取与范围界定** — 吃可研/指南,提炼功能需求、界定 inScope/outOfScope、写《需求提取与范围界定》文档(可研/指南不是现成需求,必须先提取再拆模块)。
2. **设计系统** — 定主色/强调色/字体/组件约定。
3. **功能定义** — 按业务边界拆 3-8 个模块(MECE),各模块并行,每模块写 `spec.md`。
4. **生成高保真原型** — 各页面并行产出。
5. **汇总** — `index.html` + `README.md`。

## 入参
| 参数 | 默认 | 说明 |
|------|------|------|
| `reqFile` / `reqFiles` | — | 可研/需求文档路径(**生效**) |
| `outDir` | `prototype` | 输出目录(⚠️见下,实际未生效) |
| `style` | `auto` | `auto` 按文档调性二选一；`gov`=政企稳重；`dashboard`=深色数据大屏+ECharts |
| `model` | 混合档 | `'sonnet'`/`'haiku'` 一键全局降档做低成本草稿跑 |

## 默认偏好(已与用户确认)
- 技术栈:**多文件 HTML + Tailwind CDN + 少量原生 JS**(免构建、双击即开、可跨页跳转)。**不要**用单文件、本地构建版或 React/Vue。
- 视觉风格:政企/审批类→`gov`；监测/调度/可视化类→`dashboard`。
- 调用前先确认 `reqFile` 路径存在；运行后引导用户打开 `<outDir>/index.html`,功能文档在 `<outDir>/specs/`。

## 本机运行坑(2026-06-14 实测)
1. **无 poppler/pdftoppm**,Read 无法直接打开 PDF。先 `pip install pypdf` 把 PDF 全文抽成 .md/.txt 再喂给工作流,远好于让子代理直接 Read PDF。
2. **`outDir` 参数未生效** — 即便传绝对路径,结果仍按相对 `prototype/` 写到子代理 cwd 下。`reqFiles` 是生效的。跑完手动把 `<cwd>/prototype/` 整体搬到目标目录(导航是相对扁平文件名,平铺不断链)。

## 运行后:git pull 并提交产物到远端(必做)
工作流跑完后立即执行(遵循项目规约「提交前先 git pull」,见 CLAUDE.md):
```bash
cd [当前项目目录]
git pull --rebase
git add prototype/
git commit -m "工作流-原型: 生成高保真HTML原型产物(prototype/)"
git push
```
- 先核对产物落盘位置(`outDir` 可能不生效),确认是真实产物目录再 `add`。
- `git pull` 若有冲突:停下报告,**不要强推**。
- 只提交本次产物,不顺带提交无关改动。

下一环:`proto-to-design`(工作流-设计)。
````

````text
# 工作流-设计 (proto-to-design)

「需求→原型→设计→开发→测试→部署」闭环的**第 2 环**。承接 `req-to-proto` 产出的功能定义,反推一整套技术设计文档。

## 何时触发
用户说「**工作流-设计**」,或描述"从原型产物+原始文件反推技术设计文档/HTML 设计说明书"。

## 如何运行
脚本位于 `.claude/workflows/proto-to-design.js`:

```
Workflow({ name: 'proto-to-design', args: { reqFiles: '<原始文件>', protoDir: 'prototype', outDir: 'design', dims: 'all', style: 'auto' } })
```

读取 `protoDir/specs/`(功能定义)+ 原始可研/需求文件,反推产出技术设计。

## 设计维度
**架构**(基线先行,其余维度统一引用其 techBaseline 保证选型一致)、**数据流**、**数据库**(ER)、**接口/API**、**安全**、**运维**、**非功能性/容量**、**集成对接**。
可用 `args.dims` 子集化(`architecture` 始终保留并置顶)。

## 产物
- `design/specs/*.md` — 结构化设计文档,含 Mermaid 图
- `design/*.html` — 同款 gov/dashboard 风格、可点击跳转、Mermaid@11 渲染的设计说明书
- `index.html` + `README.md`

## 入参
| 参数 | 默认 | 说明 |
|------|------|------|
| `reqFiles` | — | 原始可研/需求文件 |
| `protoDir` | `prototype` | 上游原型目录 |
| `outDir` | `design` | 输出目录(⚠️同 req-to-proto,可能不生效,核对落盘) |
| `dims` | `all` | `'all'` 或维度子集(architecture 始终保留) |
| `style` | `auto` | `auto`/`gov`/`dashboard` |
| `model` | 混合档 | `'sonnet'`/`'haiku'` 全局降档 |

## 注意
- `outDir`/`protoDir` 入参可能未被脚本收到(返回值常显示默认值),**别依赖**,跑完务必核对落盘位置(子代理通常会自行 ls 找到 specs 和 _source)。
- 已修脚本 bug:分维度合并改为规范键优先(`{...r,...d}`),避免 `07-07-nfr` 类文件名错位与导航断链。
- **2026-06-14 紧水滩实测**:20 子代理/~101 万 token/~21min,8 维度 specs 共 4212 行,Mermaid 图为项目专属,质量高。

## 运行后:git pull 并提交产物到远端(必做)

git pull --rebase
git add design/
git commit -m "工作流-设计: 生成技术设计文档与HTML设计说明书(design/)"
git push
```
- 先核对产物落盘位置(`outDir` 可能不生效),确认是真实产物目录再 `add`。
- `git pull` 若有冲突:停下报告,**不要强推**。

上游:`req-to-proto`。下游:`design-to-code`(工作流-开发)。
````

````text
# 工作流-开发 (design-to-code)

「需求→原型→设计→开发→测试→部署」闭环的**第 3 环**。承接设计+原型,产出可在本机**真实运行**的参考实现(MVP),不盲目跟设计里的企业栈。

## 何时触发
用户说「**工作流-开发**」,或描述"把设计+原型落成可运行的 MVP/参考实现"。

## 如何运行
脚本位于 `.claude/workflows/design-to-code.js`:

```
Workflow({ name: 'design-to-code', args: { designDir: 'design', protoDir: 'prototype', outDir: 'app', stack: 'auto', run: true } })
```

## 五个阶段
1. **实现规划** — Bash 真探测 node/python/pip/网络/sqlite → 自选依赖轻的可运行栈(`canRunLocally` 基于探测判断)。
2. **脚手架与数据基线** — 建库 + 把 protoDir 的 `*.html` 搬为前端 + `modules/*` 自动注册路由。
3. **分模块实现** — 并行,靠"文件归属:各模块独占 ownDir + `public/<key>__*.html`"防冲突。
4. **集成与冒烟** — 真执行 装/起/curl,有界自修复(`maxRepair` 次)。
5. **汇总** — README + IMPLEMENTATION + 差距。

## 入参
| 参数 | 默认 | 说明 |
|------|------|------|
| `designDir` | `design` | 上游设计目录 |
| `protoDir` | `prototype` | 上游原型目录(前端复用源) |
| `reqFiles` | — | 原始需求(可选) |
| `outDir` | `app` | 实现输出目录 |
| `stack` | `auto` | 务实可运行栈(用户拍板:不跟企业栈,优先零依赖) |
| `run` | `true` | `false` 则只产码不验证 |
| `maxRepair` | `3` | 集成自修复上限 |
| `model` | 混合档 | `'sonnet'`/`'haiku'` 全局降档 |

## 本机运行坑(aarch64,/home/work,务必遵守)
1. **前台 `sleep` 被禁**(带 sleep 的 Bash 整条 exit 1 无输出)→ 起服务用 `run_in_background: true`,等就绪用 `curl --retry --retry-connrefused` 而非 sleep。
2. **端口 8080 被外部占死** → 服务入口支持 `PORT` 环境变量,探测空闲端口避开 8080(如 `PORT=8092`)。
3. pkill 后立刻重启会抢端口,要确认端口空闲再起。
4. 后台起服务用**绝对路径**(Bash cwd 常被重置回 /home/work)。

## 实测(2026-06-14 紧水滩,成功)
选栈 **Python 3.9 标准库(http.server)+ SQLite**,零三方依赖。7 模块全实现、49 张表启动自建、复用 29 个原型页,接口全绿。

## 运行后:git pull 并提交产物到远端(必做)
```bash
cd [当前项目目录]
git pull --rebase
git add app/
git commit -m "工作流-开发: 生成可运行参考实现(app/)"
git push
```
- 先核对产物落盘位置(`outDir` 可能不生效),确认是真实产物目录再 `add`。
- 排除运行期生成物:`data.db`、`__pycache__/`、日志等不入库(必要时加进 `.gitignore`)。
- `git pull` 若有冲突:停下报告,**不要强推**。

上游:`proto-to-design`。下游:`code-to-test`(工作流-测试)。
````

````text
# 工作流-测试 (code-to-test)

「需求→原型→设计→开发→测试→部署」闭环的**第 4 环**。承接开发产物,自动生成并真实执行测试。

## 何时触发
用户说「**工作流-测试**」,或描述"给可运行实现自动补测试用例、真跑一遍、出通过率与失败归因报告"。

## 如何运行
脚本位于 `.claude/workflows/code-to-test.js`:

```
Workflow({ name: 'code-to-test', args: { appDir: 'app', run: true } })
```

## 四个阶段
1. **测试规划** — 探测栈 + 选轻量框架(优先栈内置:Python→unittest、Node→node:test);解析**绝对路径** `appRoot`(含服务入口与 core/ modules/ 的那层)。
2. **生成用例** — 并行,每模块独占测试文件(放 `<appRoot>/tests/` 绝对路径,消除 app/app 嵌套),覆盖正常+边界+错误。
3. **执行测试** — 真跑,如实统计(跑不起来报 `ran:false`,绝不谎报)。
4. **分析与报告** — 失败归类 `test-bug`/`code-bug`/`env`;**只修 test-bug**,code-bug 列入 `suspectedCodeBugs` 交回开发环;出 HTML+MD 报告到 `<outDir>/test-report/`。

## 入参
| 参数 | 默认 | 说明 |
|------|------|------|
| `appDir` | `app` | 开发产物目录 |
| `outDir` | 同 appDir | 报告输出目录 |
| `run` | `true` | 是否真实执行测试 |
| `maxFix` | `1` | test-bug 自修复上限 |
| `model` | 混合档 | `'sonnet'`/`'haiku'` 全局降档 |

## 关键约定
- 所有执行类子代理用 `agentType:'general-purpose'` 确保有 Bash。
- 沿用本机约定:绝对路径、避开 8080、`curl --retry` 轮询非 sleep、服务用 `PORT` 覆盖。
- 测试文件统一用绝对 `appRoot` + `tests/`,避免子代理 cwd 造成嵌套。

## 实测(2026-06-14 紧水滩,成功)
选 **unittest**(标准库内置)。生成 16 个测试文件、**506 条用例**;504/506 通过,**揪出 2 个真实 code-bug**(audit-logs 的 ambiguous column 500、`json.loads` 类型误判 500),按设计未擅改业务代码、精确定位交回。修复后 506/506 全过。**至此闭环端到端验证通过。**

## 运行后:git pull 并提交产物到远端(必做)
```bash
cd [当前项目目录]
git pull --rebase
git add app/tests/ app/test-report/
git commit -m "工作流-测试: 生成测试用例与测试报告(tests/、test-report/)"
git push
```
- 先核对产物落盘位置(测试可能落在 `app/tests/` 或嵌套层),确认是真实产物目录再 `add`。
- `git pull` 若有冲突:停下报告,**不要强推**。

上游:`design-to-code`。下游:`app-to-deploy`(工作流-部署)。
````

````text
# 工作流-部署 (app-to-deploy)

「需求→原型→设计→开发→测试→部署」闭环的**最后一环**。承接开发产物,打成拷到其它机器、让智能体照运行手册自主部署的可移植离线部署包。

## 何时触发
用户说「**工作流-部署**」,或描述"把可运行实现打成可移植/离线/智能体自主部署的部署包"。

## 如何运行
脚本位于 `.claude/workflows/app-to-deploy.js`:

```
Workflow({ name: 'app-to-deploy', args: { appDir: 'app', offline: true, rehearse: true } })
```

## 五个阶段
1. **部署探查** — 解析绝对 `appRoot`;探明运行时/最低版本/第三方依赖/启动命令(读 PORT、避开 8080)/数据位置/环境变量/健康检查/外部服务依赖,Bash 实测启停。
2. **依赖离线打包** — 有第三方依赖则打到 `<appRoot>/vendor/`(`pip download`/`npm pack`)并给离线安装命令;纯标准库则 `method=none`;无网下不了如实报告 + 给"有网机器上打包"的命令。
3. **生成部署物**(并行) — 文档:`DEPLOY.md`(人看)+ **`AGENT_DEPLOY.md`(给 AI 的确定性运行手册:编号步骤+预期输出+校验+失败处置)**;脚本:`deploy.sh`/`stop.sh`/`Dockerfile`/`docker-compose.yml`/`<appName>.service`/`.env.example`。
4. **净室演练** — 复制部署所需内容到 /tmp 临时目录(排除 data.db/__pycache__/node_modules/.git/test-report/tests),`bash deploy.sh` 离线部署 + curl 轮询健康检查 + 冒烟,有界自修复并回写;证明"拷过去真能起"。完后清临时目录 + kill。
5. **汇总** — `DEPLOY-BUNDLE.md`(部署包清单 + 拷贝部署指引 + 演练结论)。

## 入参
| 参数 | 默认 | 说明 |
|------|------|------|
| `appDir` | `app` | 开发产物目录 |
| `offline` | `true` | 是否离线打包依赖 |
| `rehearse` | `true` | 是否做净室演练 |
| `maxRepair` | `3` | 演练自修复上限 |
| `model` | 混合档 | `'sonnet'`/`'haiku'` 全局降档 |

## 关键约定
沿用全套鲁棒约定:绝对路径、避开 8080、`curl` 轮询非 sleep、跑不起来如实报告、`general-purpose` 子代理、`.filter(Boolean)`、关键 agent 返回 null 优雅中止。

## 运行后:git pull 并提交产物到远端(必做)
```bash
cd <项目目录>
git pull --rebase
git add app/DEPLOY.md app/AGENT_DEPLOY.md app/deploy.sh app/stop.sh app/Dockerfile app/docker-compose.yml app/*.service app/.env.example app/DEPLOY-BUNDLE.md
git commit -m "工作流-部署: 生成可移植离线部署包(部署物+运行手册)"
git push
```
- 先核对产物落盘位置(部署物在 `appRoot` 下),确认真实文件名再 `add`;`vendor/` 离线依赖按需纳入。
- 排除净室演练的临时目录(在 /tmp,已自动清理)与运行期数据。
- `git pull` 若有冲突:停下报告,**不要强推**。

上游:`code-to-test`。这是闭环六环的终点。
````

## 七、真实实践（取自实际会话，已脱敏）

> 以下为同事项目里这些工作流的真实调用（路径/IP/端口已脱敏）。重点不是项目本身，而是**这些工作流到底接什么输入、怎么串、跑出什么**。

### 7.1 全链路实践（一条龙跑通）

> [!example] 案例 A · 广义储能协同规划平台（新疆科技项目）—— 原型→设计→开发→测试→打包 全链路
> - **原型**：`工作流-原型` 输入任务书 PDF +《新型电力系统广义储能协同规划平台》需求 docx（含电网拓扑、风光出力数据）→ 产出 33 个 HTML 页面 + `specs/` 功能定义 + `theme.js` 深浅主题 + 本地化 Tailwind/ECharts。
> - **设计**：`工作流-设计` 基于上面 33 页原型 + 原始需求 → 技术设计文档。
> - **开发 / 测试 / 打包**：`工作流-开发` → `工作流-测试` → 打包 exe。
> - **自动化**：用 `loop` 把「设计→开发→测试→打包exe 四阶段流水线一路跑完，并在用量限额中断后自动续跑」。
> - **要点**：纯静态前端也能走完整链路；`app-to-deploy` 也被用来给这套 33 页静态原型打可移植部署包。

> [!example] 案例 B · 四币种实时汇率转换系统 —— 原型→测试→打包 exe
> - **原型**：`工作流-原型` 输入需求 md（人民币/美元/越南盾/U币 双向汇率、走势、提醒、换算）→ 每个原型独立 HTML + 详细注释，覆盖用户端 + 管理端；可指定风格（此处要求「严肃、准确、简单大方」）。
> - **测试**：`工作流-测试` 对后端做接口测试 —— `target=api_health_rates type=api`，源文件 `main.py` → 生成 `test_api_health_rates.py`。
> - **打包**：`工作流-打包`（webapp-to-installer）把 Web 应用打成 Windows .exe（离线、桌面图标）。

### 7.2 原型工作流的「多源输入」实践（req-to-proto 用得最多）

`工作流-原型` 是全家族里调用最频繁的（10+ 次）。真实输入源五花八门，说明它对输入格式很宽容：

- **思维导图 PDF** → 能碳管理平台原型（要求高保真、高端大气、交互炫酷）
- **采购计划 xlsx** → 提取功能需求 → 城乡垃圾流向监测平台 + 智慧环卫系统原型
- **答辩 docx** → 零碳园区多主体协同治理原型
- **可研 + 需求 + 设计方案（多文件）** → 浙江虚拟电厂仿真原型（要求体现「融合大模型智能体」创新点）
- **已结构化需求包** → VPP「仿真预测」模块原型（需求已拍板，跳过需求访谈直接出原型）
- **参考风格目录** → 可传入「参考 HTML 风格目录」让新原型对齐既有视觉

### 7.3 把通用工作流「fork 成项目专用工作流」（重要洞察）

> [!tip] VPP server 项目把通用工作流沉淀成了一套 `vpp-*` 专用技能
> - `vpp-req-to-change`（需求变更，带 `changeId`）→ `vpp-design` → `vpp-design-to-code` → `vpp-dev-integrate`（同一 `changeId=add-vpp-command-dashboard` 串起一次完整需求变更）。
> - `vpp-proto-to-design`（`protoDir=...prototypeV6`）、`vpp-feature-pipeline`（增量开发功能模块：需求规格 + 参考原型 → 重建模块）。
> - `vpp-metric-sql-backfill` —— **被调用 33 次**，是该项目最高频工作流：基于数仓表（`dwd_user_elec_15min_v1`、`dwd_adjustable_capacity` 等）按「行业+省+市+区县+时间点」维度算实时负荷/用电量/环比/峰谷差/可调能力等指标，产出「取数 SQL + 验数 SQL + 补数脚本」。
>
> **洞察**：通用工作流（req→design→code→...）可以按项目沉淀成带项目术语、带数仓表、带 `changeId` 流转的**专用工作流** —— 这正好印证 [[项目立项与研发流程规范]] 里「每个项目配一套自己的工作流 / AI 机器人」的主张。

- **选股估值**：`工作流-选股`（stock-growth-valuation）跑英伟达 NVDA、明略科技 02718、供销大集 000564。

### 7.5 编排 / 自动化实践

- **`loop` 自动续跑**：把多阶段流水线「一路跑完 + 限额中断后自动续跑」；也用于定时同步另一会话的进度（抓屏对比、简要汇报）。
- **`update-config` 自动留痕**：加 Stop hook —— 每轮结束检查工作流产物目录（`prototype/ design/ app/ tech/`）有无改动，有则自动 `git pull --rebase --autostash` + add + commit + push。把「工作流产物」纳入自动版本管理。

## 八、经验提炼（对照开发规范）

> [!summary] 实践验证了开发规范的哪些点
> - **原型驱动可落地**：`工作流-原型` 能吃 PDF/xlsx/docx/md 多种原始材料，直接产出高保真可交互原型 —— 印证规范「先原型、低成本收敛需求」。
> - **全链路可自动化**：原型→设计→开发→测试→打包能用 `loop` 串成一条龙并自动续跑 —— 单人负责制下，AI 工作流确实能补齐工种。
> - **工作流可 per-project 定制**：VPP 把通用工作流 fork 成 `vpp-*` —— 印证规范「每项目配专用工作流 / AI 机器人」。
> - **产物要纳管**：Stop hook 自动提交工作流产物 —— 对应规范「各阶段产出物入知识库」。

> [!warning] 用的时候注意
> - 工作流产物（尤其 AI 生成代码 / SQL）仍要**人工必检**（见规范 §五各阶段），别盲信。
> - 涉及内网地址 / 凭据 / 真实数据时先脱敏，工作流产物入公开库前自查。
> - 大任务用 `loop` 续跑前，先确认产物目录与提交策略（参考 7.5 的 Stop hook）。
