## 一、什么是工作流技能

- **定义**：一族封装好的 Claude Code Skill（多以「工作流-XXX」命名）。每个技能 = 一个有固定输入、固定阶段、固定产出的自主流程，用户给一句话（或一个文件）即可触发它跑完整段工作。
- **与开发规范的关系**：[[项目立项与研发流程规范]] 讲「流程与评审」，本笔记讲「跑流程用的工具」。规范里每个研发阶段，背后就是这里的一个工作流技能。

> [!info] 一个工作流技能在磁盘上由几部分组成（理解这点才能复现）
> 1. **触发层（三种实现，2026-07-16 起研发 5 环推荐路线 C）**——三者都是"壳"：本身不含业务逻辑，只负责把输入接到引擎 js：
>    - **路线 A · SKILL.md 薄壳**：`~/.claude/skills/<name>/SKILL.md`（+ `assets/ references/ scripts/`）。frontmatter `description` 决定触发词；正文是「何时触发 / 如何运行 / 阶段 / 入参」。文档类独立 skill 都走这条。
>    - **路线 B · memory 触发记忆**：`~/.claude/projects/<项目>/memory/workflow-*-trigger.md`。正文直接写「用户说「工作流-X」时，运行 `Workflow({ name:'<name>', args:{...} })`」。**研发流水线 5 环在 `Claude-迁移包` 里走的是这条**（详见 §四·触发层实况）；只在 memory 所属项目生效。
>    - **路线 C · slash 命令（2026-07-16 新增，推荐）**：`~/.claude/commands/<name>.md`，**文件名即命令名**（`proto.md` → `/proto`）。正文写「调用 `Workflow({ name:'<name>', args:{...} })`」。打 `/` 见菜单、**显式确定命中**、全局生效——比 A 的语义匹配稳、比 B 的单项目限制广。研发 5 环的 slash 命令装法见 §六补.0+。
> 2. **工作流引擎脚本**：研发流水线 5 个环的触发层无论走 A 还是 B 都只是「薄壳」，真正逻辑在 `~/.claude/workflows/<name>.js`，由 `Workflow({ name: '<name>' })` 调起。**复现时触发层 + 引擎层都要有，缺一不可。**
> 3. **市场插件**：docx/xlsx/pdf/duckdb 等能力来自插件市场，走 `/plugin` 重装，不随文件拷贝。
> 4. **平台内置技能**：`deep-research`、`loop`、`schedule` 等是平台统一下发，磁盘无文件、新账号自带、**无需迁移**。⚠️ **`stock-growth-valuation`（选股）例外**——它虽是内置触发壳，但迁移包 `workflows/` 里**实存 `stock-growth-valuation.js`（423 行、6 阶段完整引擎）**，迁移时**必须拷这个 js**，否则复现失败（详见 §四补.4）。

> **三种触发层对比**（2026-07-16 整理；壳 = 把输入接到引擎 js 的薄入口，本身不含逻辑）：
>
> ```
> 你输入  →  [触发层 · 壳]  →  [引擎 js]  →  子代理跑起来
> "工作流-原型"     SKILL.md / memory      req-to-proto.js
> "/proto"          commands/proto.md
> ```
>
> | | 路线 A · SKILL.md 壳 | 路线 B · memory 触发 | **路线 C · slash 命令（推荐）** |
> |---|---|---|---|
> | 文件位置 | `~/.claude/skills/<name>/SKILL.md` | `~/.claude/projects/<项目>/memory/*.md` | `~/.claude/commands/<name>.md` |
> | 怎么命中 | description **语义匹配**（可能漏/误触发） | memory 读进上下文后按字面触发 | 打 `/name` **显式确定** |
> | 生效范围 | 全局 | **仅挂载的那一个项目** | 全局 |
> | 要改写死路径 | 否 | 是（`/home/work/...`） | 否 |
> | 迁移包里有 | ❌（§四 全文是唯一副本） | ✅（`memory/` 目录） | ❌（自建，装法见 §六补.0+） |
>
> 本机（`/home/yuan`，2026-07-16）研发 5 环**只装了路线 C**，故打 `/proto` 等命令可用、打「工作流-原型」触发词不生效（A/B 未装，属预期）。

## 三、安装与复现（到别的机器）

> **2026-07-15 重写**。旧版本节描述的双包方案（`claude-skills-migration` + `claude-skills-bundle`、要 `/plugin` 联网重装插件、要 `install.sh` 补壳）**已作废**，现行方案是**自包含单包 + 一条命令**。

> [!important] 复现 = 一条命令 + 两处手工补路径
> `bash restore.sh <新工作目录>` 一次搞定 **skills / workflows / settings / plugins / memory 五块**，**无需 git、无需联网**（插件本体已打进包并剥掉 `.git`）。
> 但脚本**只**改写插件路径，**skills 与 memory 里写死的旧机 `/home/work` 路径它不管**——见 §3.4，不补就有技能失灵。

### 3.1 现行迁移包（单包，自包含）

| 项 | 值 |
|---|---|
| 路径 | `资料/Claude-迁移包/Claude/`（2026-07-14 打包，约 **81M**） |
| 内容 | `skills/`（6 个文档类技能）+ `workflows/`（**6 个 .js**）+ `settings/` + `plugins/`（**本体 + 市场，已剥 .git**）+ `memory/`（9 条）+ `restore.sh` + `README-迁移说明.md` |
| 安装 | `bash restore.sh [新工作目录]` |
| 依赖 | 仅 Node.js（Claude Code 固有依赖；状态栏脚本写死 `/usr/local/bin/node`） |

> [!warning] 与旧双包的**关键差异**（别按老经验操作）
> - **插件不再需要 `/plugin` 联网重装**——本体随包，`restore.sh` 直接铺开。旧 §3.3 那套作废。
> - **流水线 5 环的 SKILL.md 壳不在包里**，触发走 `memory/`（详见 §2.1 警告框与 §四 路线 A/B 对照表）。想跨项目触发就得自己从 §四 抄壳。
> - **`yuchi-conformance-audit` 未随包**（`workflows/` 只有 6 个 js）。
> - 包内 6 个技能 = 可研 / 专利 / 规格 / 测评 / 打包 / 插图检查；`idea-to-feasibility-sci`、`idea-to-reserve-form`、`task-to-defense-ppt` **均未随包**（其 SKILL.md 全文见 §五，但模板/脚本等资源无处可取）。

### 3.2 一键还原（目标账号本人执行，勿用 sudo）

```bash
# 0) 新机先装好并启动过一次 Claude Code
cd /path/to/Claude-迁移包/Claude

# 1) 一键还原。参数 = 新机的工作目录（决定 memory 挂到哪个项目下）
bash restore.sh /home/youruser/yourproject

#    不传参数则沿用旧机默认 -home-work-guofeng —— 新机工作目录不同就必须传，
#    否则记忆挂错项目、5 环触发词全部失灵（触发靠 memory，见 §2.1）。

# 2) 重启 Claude Code，验证
#    /skills 看得到 6 个技能；在「工作目录」下打触发词「工作流-原型」应能唤起
```

脚本干了什么（`restore.sh` 实读）：`skills/`→`$DEST/skills/`；`workflows/`→`$DEST/workflows/`；`settings.json`+`settings.local.json`+`statusline-command.sh`→`$DEST/`；`plugins/`→`$DEST/plugins/` 并 `sed` 改写 `installed_plugins.json` 里的 `/home/work/.claude`→`$DEST`；`memory/`→`$DEST/projects/<工作目录路径转写名>/memory/`。
`$DEST` = `${CLAUDE_CONFIG_DIR:-$HOME/.claude}`。**转写规则**：工作目录绝对路径里的 `/` 全换成 `-`（开头也是 `-`），如 `/home/u/proj` → `-home-u-proj`。

### 3.3 随包插件（无需联网、无需 `/plugin`）

`plugins/` 里是**本体 + 市场目录**（约 44M，`.git` 已剥）：`claude-hud`（状态栏 HUD，**`settings.json` 的 statusLine 依赖它**）、`pyright-lsp`、`duckdb-skills`、`document-skills`（docx/xlsx/pptx/pdf）、`example-skills`。
`settings.json` 里 `extraKnownMarketplaces` 记着来源（`claude-hud` → `jarrodwatts/claude-hud`；`anthropic-agent-skills` → `anthropics/skills`），仅供日后更新用，**装不需要它**。

### 3.4 还原后必做的手工补路径（restore.sh 不管这两处）⚠️

`restore.sh` 只 `sed` 了 `installed_plugins.json`。**旧 `install.sh` 会顺手改技能里的写死路径，新脚本不会**——这是新包的一处退步，必须手工补：

```bash
DEST="${CLAUDE_CONFIG_DIR:-$HOME/.claude}"

# ① 技能里的写死路径（webapp-to-installer/SKILL.md 有 1 处调 pack.sh 的绝对路径）
grep -rl '/home/work' "$DEST/skills/" | xargs sed -i "s|/home/work/.claude|$DEST|g"

# ② memory 里的写死路径（9 个文件共 13 处，含 5 环的 workflows 脚本路径、论文/课题目录）
grep -rl '/home/work' "$DEST/projects/<你的项目>/memory/" \
  | xargs sed -i "s|/home/work/.claude|$DEST|g"
```

- ②尤其要紧：**5 环触发靠 memory**，里面写着 `脚本位置：/home/work/.claude/workflows/xxx.js`，不改就指向不存在的路径。
- memory 里还有**旧机工作目录**级的路径（如 `/home/work/guofeng/论文/`），那是内容不是配置，按新机实际目录酌情改。
- macOS 的 `sed -i` 需写成 `sed -i ''`。

### 3.5 复现注意（来自实测）
- **认证**：凭证未打包。每个用户用自己账号 `claude /login`，**绝不**复制他人 `.credentials.json`。
- **PDF 输入**：本机无 poppler，先 `pip install pypdf` 把 PDF 抽成 .md/.txt 再喂工作流。
- **权限**：多用户机器上 `chmod -R u+rwX,go-rwx ~/.claude/skills ~/.claude/plugins` 收敛。

### 3.6 本机 Claude Code 快捷命令（shell 别名）

本机把 `cc` 配成了启动 Claude Code 的别名（用 `type cc` 可查）：

```bash
# ~/.bashrc 里的别名
alias cc='claude --dangerously-skip-permissions'
```

| 命令 | 等价于 | 行为 |
|---|---|---|
| `claude` | — | 正常启动，执行命令/改文件/联网前**逐次弹权限确认** |
| `cc` | `claude --dangerously-skip-permissions` | **跳过所有权限确认**，全自动不打断（业内俗称 YOLO 模式） |

> [!danger] `cc`（免确认模式）用之前先想清楚
> `--dangerously-skip-permissions` 会让改文件、删文件、跑任意 Bash、`git push`、联网**全部不再询问、直接执行**，安全网撤掉。
> ⚠️ **迁移包的 `settings.json` 里还带着 `"skipDangerousModePermissionPrompt": true`**——它连「你确定要进免确认模式吗」这道**入口提示**都省了，`cc` 直接静默进 YOLO。`restore.sh` 会把这个设置一并铺到新机，等于**新机默认就是这个状态**。不想要就还原后手工删掉这行。
> - **适合**：可信、重复、低破坏的活（批量整理笔记、跑工作流、`loop` 续跑）。
> - **慎用**：大范围删改、push **公开仓库**（本仓库即公开，脱敏没把好关就直接上网）、动共享机上别人的目录。
> - 高破坏/对外操作建议用普通 `claude` 留住确认这道闸，或先 `git status` / `--dry-run` 看清再放手。

````text
# 工作流-部署 (app-to-deploy)

「需求→原型→设计→开发→测试→部署」闭环的**最后一环**。承接开发产物,打成拷到其它机器、让智能体照运行手册自主部署的可移植离线部署包。

## 何时触发
用户说「**工作流-部署**」,或描述"把可运行实现打成可移植/离线/智能体自主部署的部署包"。

## 如何运行
脚本位于 `.claude/workflows/app-to-deploy.js`:

```
Workflow({ name: 'app-to-deploy', args: { appDir: 'app', offline: true, rehearse: true } })
```

## 五个阶段
1. **部署探查** — 解析绝对 `appRoot`;探明运行时/最低版本/第三方依赖/启动命令(读 PORT、避开 8080)/数据位置/环境变量/健康检查/外部服务依赖,Bash 实测启停。
2. **依赖离线打包** — 有第三方依赖则打到 `<appRoot>/vendor/`(`pip download`/`npm pack`)并给离线安装命令;纯标准库则 `method=none`;无网下不了如实报告 + 给"有网机器上打包"的命令。
3. **生成部署物**(并行) — 文档:`DEPLOY.md`(人看)+ **`AGENT_DEPLOY.md`(给 AI 的确定性运行手册:编号步骤+预期输出+校验+失败处置)**;脚本:`deploy.sh`/`stop.sh`/`Dockerfile`/`docker-compose.yml`/`<appName>.service`/`.env.example`。
4. **净室演练** — 复制部署所需内容到 /tmp 临时目录(排除 data.db/__pycache__/node_modules/.git/test-report/tests),`bash deploy.sh` 离线部署 + curl 轮询健康检查 + 冒烟,有界自修复并回写;证明"拷过去真能起"。完后清临时目录 + kill。
5. **汇总** — `DEPLOY-BUNDLE.md`(部署包清单 + 拷贝部署指引 + 演练结论)。

## 入参
| 参数 | 默认 | 说明 |
|------|------|------|
| `appDir` | `app` | 开发产物目录 |
| `offline` | `true` | 是否离线打包依赖 |
| `rehearse` | `true` | 是否做净室演练 |
| `maxRepair` | `3` | 演练自修复上限 |
| `model` | 混合档 | `'sonnet'`/`'haiku'` 全局降档 |

## 关键约定
沿用全套鲁棒约定:绝对路径、避开 8080、`curl` 轮询非 sleep、跑不起来如实报告、`general-purpose` 子代理、`.filter(Boolean)`、关键 agent 返回 null 优雅中止。

## 运行后:git pull 并提交产物到远端(必做)
```bash
cd <项目目录>
git pull --rebase
git add app/DEPLOY.md app/AGENT_DEPLOY.md app/deploy.sh app/stop.sh app/Dockerfile app/docker-compose.yml app/*.service app/.env.example app/DEPLOY-BUNDLE.md
git commit -m "工作流-部署: 生成可移植离线部署包(部署物+运行手册)"
git push
```
- 先核对产物落盘位置(部署物在 `appRoot` 下),确认真实文件名再 `add`;`vendor/` 离线依赖按需纳入。
- 排除净室演练的临时目录(在 /tmp,已自动清理)与运行期数据。
- `git pull` 若有冲突:停下报告,**不要强推**。

上游:`code-to-test`。这是闭环六环的终点。
````

### 四补.1 manifest 契约链（六环串联的真正机制，薄壳全未提）

**每个研发环末尾都有一个 haiku agent 写 `manifest.<stage>.json`；下游环启动时优先 `Read` 上游 manifest 的 `handoff` 字段作**权威输入**，无清单才回退到 `ls` 探查目录。** 这是把「原型→设计→开发→测试→部署」串成一条流水线的真正纽带——§4.2 入参 `protoDir`、§4.3 入参 `designDir` 的「上游目录」正是靠它对接。

```text
req-to-proto  → manifest.proto.json  (handoff: styleKey/modules/inScope/outOfScope; outputs: specs/pages/entry)
proto-to-design → manifest.design.json (handoff: styleKey/techBaseline/dimensions/modules/dbSpec/apiSpec)
design-to-code  → manifest.dev.json   (handoff: appRoot/stack/canRunLocally/commands/port/testCommand/modules/integrationOk)
code-to-test    → manifest.test.json  (handoff: appRoot/framework/generated/result/suspectedCodeBugs
                                                + gatePassed = ran && failed===0  ← 供部署环判门禁)
app-to-deploy   → manifest.deploy.json (handoff: appRoot/appName/runtime/port/offlineInstall/rehearsalOk/healthCheck)
```

- 下游读上游 `handoff` 作权威输入，弱化对 `outDir` 目录猜测与传参依赖。
- `app-to-deploy` 阶段1 会先读 `manifest.dev.json`/`manifest.test.json`。⚠️ **2026-07-15 起 `gatePassed` 不再只是「参考」，已升级为代码级阻断门**（见 §四补.7）。

### 四补.5 结构机制补充（薄壳阶段名对了，但漏了并行/屏障细节）

- **req-to-proto**：阶段3 功能定义按**模块**并行、阶段4 生成原型按**页面**并行；阶段3 结尾设**屏障**等齐所有模块，才能拼出完整 sitemap 供跨页跳转；页面文件名 = `${模块key}__${页面key}.html`（确定性命名，平铺搬目录不断链）。
- **proto-to-design**：meta 声明 6 阶段但实际 5 次 `phase()`（视觉系统与总体架构基线并行同一 phase）；理论子代理数约 21（1+2+7+9+2），实测 20 是计数口径差。⚠️ **21 / 7 维 / 9 张 HTML 这组数字只在 `dims:'all'`（默认）下成立**——传 `dims:['database','security']` 之类子集会等比减少；代码强制 `architecture` 必留且置顶（它是 techBaseline 基线，其余维度都引用它保选型一致）。

### 四补.6 贯穿式运行纪律（已焊进 3 个执行环的 prompt，复现踩坑高发区）

`design-to-code` / `code-to-test` / `app-to-deploy` 这三个**真跑命令**的环，prompt 里固化了同一套环境约定。它们是 2026-06-14 紧水滩实测踩坑后回填进脚本的，换机复现时最容易在这里翻车：

1. **禁前台 `sleep`** —— 本机带 `sleep` 的 Bash 整条 `exit 1` 无输出。等服务就绪一律用 `curl -s --retry 8 --retry-connrefused --retry-delay 1` 轮询，不用 sleep。
2. **后台起服务用 `nohup` + 绝对路径** —— 子代理 Bash 的 cwd 常被重置，相对路径起不来。
3. **端口一律避开 8080** —— 8080 常被其它服务占死（`ss` 还看不到 pid，因非本用户）。服务入口必须支持 `PORT` 环境变量覆盖，plan 阶段探测空闲端口。⚠️ 两环兜底值不一致：`design-to-code` 兜底 `3000`，`app-to-deploy` 兜底 `8090`，跨环传递时留意。
4. **绝对 `appRoot` 解析** —— `code-to-test` / `app-to-deploy` / `design-to-code` 都强制子代理先 `pwd`/`find` 出含 `core/`+`modules/` 的那层绝对路径，动机是消除 `app/app` 这类嵌套（即四补.3 那条根因的上游修复手段）。
5. **不谎报** —— 跑不起来如实 `ok:false`/`ran:false`；执行类子代理一律 `agentType:'general-purpose'` 以确保有 Bash；并行结果都 `.filter(Boolean)`；关键单 agent 返回 null 时优雅中止。

另：`proto-to-design` 有一处防坑容错值得记——分维度结果合并用 `{...r,...d}`（**规范键 d.key/d.num/d.title 优先**），防止子代理回传的 key 覆盖导致文件名错位（如 `07-07-nfr`）与导航断链。

#### 0715 两处改动（commit `fe2bc7d` / `cea9710`，分支 `feat/workflow-quality-gates`）

1. **`req-to-proto.js`**：补 `spec`/`design` 空值守卫 + `style` 白名单。动机是**修 bug**——另三环（`design-to-code:177`/`code-to-test:134`/`app-to-deploy:148`）都有「agent 未返回即中止」的守卫，**唯独入口环没有**，扫描件 PDF 抽不出字 → schema 失败 → `spec` 为 null → `:154` 裸 deref 抛 TypeError。
2. **`app-to-deploy.js`**：`gatePassed` 从 prompt 里的「部署前提参考」升级为**代码级阻断**。`SPEC_SCHEMA` 加 `testGate` 字段（要求探查 agent **只如实回填、不做判断**），阶段1 解析出绝对 `appRoot` 后加真 `if` + `return { error:'test gate failed' }`。

   - **fail-closed 用 `!== true`**：agent 抄漏字段时挡住而非放行。门误挡的代价是重跑测试环；误放的代价是部署包已经打出去了。
   - **未跑过测试环**（`found:false`）则告警放行——这是唯一通道，**没加 `skipTestGate` 逃生阀**（测试真红了就该去修测试）。
   - ⚠️ 边界：测试**跑都没跑起来**时 `handoff.result` 只有 `{ran:false}` 没有 `failed` 字段，但 `gatePassed` 照样 `false` → 门仍拦住，显示 `failed=未知`。这是对的。

> [!important] 一条贯穿性结论：**跨环 prompt 传达做不成硬门**
> 铁证在本工程自己的代码里：`handoff.inScope`/`outOfScope` 早在 `req-to-proto.js:303-304` 就写进 manifest，而 `proto-to-design.js:255` **从未提及它们**——写了没人读的 handoff 字段，本工程已有先例。这条链等于已经跑完了「prompt 层门」的对照实验，**结论是零牙齿**。
> 所以：**真阻断只能在本环自己 `return { error }`**。这也是 0715 只改出两处、且都是 `if` + `return` 的原因。

> [!tip] 判定「该阻断还是该告警」的口径
> **严格度 = 下游被浪费的成本 × 错误的不可见性**
> - `gatePassed` 必须**阻断**：下游浪费巨大（4 个阶段 + opus 净室演练），且「测试红了」这件事在部署包里完全不可见。
> - 产出缺页只**告警**：人眼一秒可见，剩余页仍有汇报价值。
>
> 别做「什么都拦」的门——那种门第一次误伤后就会被绕过去，然后变回装饰。

⚠️ **状态**：两处改动**语法校验通过、字段名与上游 `code-to-test.js:214-228` 核对通过，但尚未端到端真跑验证**（本机未装 workflows、手头无可研文档与测试环产物）。真验证路径：装 workflows → 跑原型环（验改动1）→ 跑到测试环 → 故意留个失败用例 → 跑部署环看门拦不拦（验改动2）。

````text
# 工作流-规格:需求文档 → 详细规格说明书

把一份(粗或细的)需求材料,落成一份**可直接指导开发与验收**的规格文档:既细化
"做什么"(功能需求 SRS:功能项、输入输出、业务规则、异常边界、验收标准),又落到
"怎么做"(详细设计:领域模型、数据库、接口契约、架构与关键流程)。

核心难点是:需求材料和一份可开发的规格之间隔着大量未定信息,且规格文档只有满足
三件事才真正有用——**可追溯**(每条需求都连得到设计与验收)、**可验证**(每条需求
都有客观可测的验收标准)、**前后一致**(实体/模块/接口/字段全文同名同义)。本技能
**一次性自主跑完、中途不打断用户**:对未定信息用**行业合理默认值**自行补全并标注,
靠 **编号 + 追溯矩阵** 串起需求与设计、**事实台账** 保一致、**Mermaid 图 + 工程配图**
提清晰度、**全文自检** 收口,所有假设与缺口汇成"开放问题清单"随成稿交回供事后审阅。

## 运行风格(重要)
**一气呵成,不设中途确认关卡。** 用户要的是直接拿到成稿,不是被反复追问。所以:
读完需求即开干,自己定画像、自己裁章、自己起草,**不要**用 `AskUserQuestion` 逐章问、
**不要**"交用户过目后再动笔"。遇到需求材料没说清的地方,按 `references/chapter-playbook.md`
的默认值策略**自己做出合理且明示的假设**,就地标 `〔批注:…〕` 并记入开放问题清单,
继续往下写——把判断权后置到用户审阅成稿时,而不是打断创作过程。只有在**需求材料严重
不足以判断系统到底要做什么**(连定位和核心功能都无法推断)时,才停下来问一个澄清问题。

## 第一原则(贯穿全程)

1. **分清需求与设计,但装进同一本文档。** 第 2–4 章回答"做什么"(需求,面向业务与验收),
   第 5–7 章回答"怎么做"(设计,面向开发)。别在需求章里写技术实现,也别在设计章里
   重新定义需求——否则评审时谁也说不清哪条是约束、哪条是选型。
2. **一切可追溯。** 每个功能需求给一个稳定编号(如 `FR-<模块>-001`),设计章节明确"实现
   哪几条 FR",验收章节回指 FR。最后用一张**追溯矩阵**(需求↔设计↔验收)收口。没有编号
   的需求等于没法验收,也没法在变更时评估影响面。
3. **一切可验证。** 每条需求都要有**客观可测**的验收标准——能写成一句"给定…当…则…"的
   判定。看到"系统应友好/高效/稳定"这类没法测的话就追问到可测为止,或标注假设。
4. **一致性靠台账,不靠记忆。** 建一份 `工作台账.md` 登记实体名、模块名、接口名、字段名、
   关键约束的**唯一口径**;全文只用台账里的叫法,改名只改台账再全文同步。规格文档最常见
   的低级失分就是同一个东西在三章里三个名字。
5. **凡未定必标注,不杜撰。** 材料没说清的,给行业合理默认值并就地标 `〔批注:…〕`(脚本
   渲染红色),同时在"开放问题清单"里挂账,随成稿交回用户事后核对——不要把猜测写成既定事实。

## 总流程(九步,一次性跑完)

### 第0步 · 吃输入,自定画像与颗粒度
1. **读需求材料。** Word(.docx)先抽成文本:`python3 -c "import docx;print('\n'.join(p.text for p in docx.Document('需求.docx').paragraphs))"`;
   PDF 先 `pip install pypdf` 抽文本;一段话/口头描述直接用。
2. **自己**定下**画像**(不向用户确认,直接写进台账):系统名称(暂定)、一句话定位、目标
   用户与核心场景、范围(inScope/outOfScope)、规模量级、技术约束。需求里没说的,按常理推断
   并标注为假设。画像是后面裁章与起草的锚。
3. **自己**定颗粒度:需求材料覆盖整套系统就写总体规格;只聚焦某模块就写深那几块。按材料
   重心判断,不反问。
4. 建 `工作台账.md`,起**实体/模块/接口/术语清单**,全程维护、单一来源。
- 仅在**需求严重不足、连系统要做什么都判断不出**时,才停下来问**一个**澄清问题;否则一律
  自主推断、标注假设、继续。

### 第1步 · 需求分析:去伪存真(应用方法论)
照 `references/req-analysis-principles.md` 把原始材料炼成**澄清需求基线**(自主推演,不访谈用户):
1. **条目化 + 四过滤**:拆成独立需求条目,过一遍范围/合规/技术可行/去重合并。
2. **剥方案见问题(5 Why)**:对每个"方案式诉求"自己往下追几层为什么,补出真实业务目标。
3. **标准句式重写**:每条写成「作为[角色],我希望[能力],以便[价值]」,逼出角色与价值。
4. **三分类 + 编号**:分功能(`FR-*`)/非功能(`NFR-*`)/约束;非功能就地往可测细化。
5. **MoSCoW 优先级**:每条标 Must/Should/Could/Won't,据业务价值砍低值项。
推断与取舍都标 `〔批注:…〕` 并记入开放问题清单。基线落进台账,作为后面建模与起草的源头。

### 第2步 · 对照模板裁剪章节
读 `references/spec-template.md`,按项目类型**自行**裁出实际章节大纲(如纯后端服务可砍前端
交互章;无外部对接可砍集成章;数据简单可把"数据字典"并入数据库设计)。大纲写入台账,
直接据此起草,不交用户过目。编号连续,目录与正文一致。

### 第3步 · 逐章自答 + 建模
按 `references/chapter-playbook.md` 的逐章清单**自己逐条回答**(材料优先,缺则用行业默认值并
标〔批注〕),同时把需求**建模成可开发的剧本**:
- **核心功能写用例规约**:参与者/前置/**基本流**/**备选流(异常+边界,灵魂)**/后置——漏掉的
  异常分支正是开发返工根源。
- **建数据字典 + 业务规则**:把模糊术语定义成原子项;业务规则给 `BR-*` 编号 + 触发条件。
- **识别接口**:每个对外接口定目的/请求/响应/非功能约束。
关键事实(实体及字段、模块边界、接口、外部系统、非功能指标、技术选型)必落台账;全程不提问。

### 第4步 · (按需)联网检索补设计依据
仅在有把握提质时做,用 `WebSearch`/`WebFetch` 查**真实**资料:相关技术/框架的标准做法、
要遵循的规范或协议(如 OAuth2、OpenAPI、行业数据标准)、要对接的第三方接口文档。检索结论
入台账并记来源;查不到的标准号/接口细节别杜撰,挂到开放问题清单。

### 第5步 · 逐章起草 Markdown
按 `references/spec-template.md` 的体例与写法生成结构化 Markdown(见下"产出格式"):
- **功能需求**:简单功能用功能需求项模板;有分支的核心功能用**用例规约**写全
  (编号、参与者、前置、基本流、备选流、后置、优先级、验收标准),能用表就用表。
- **数据设计**:核心实体给字段表(字段/类型/约束/说明)、ER 图(Mermaid `erDiagram`)、数据字典与业务规则表。
- **接口设计**:每个接口给契约表(方法/路径/鉴权/入参/出参/错误码/幂等),复杂交互配时序图
  (Mermaid `sequenceDiagram`)。
- **架构与流程**:分层架构与关键业务流程用 `make_figures.py` 出 PNG(见第6步)。
- 全程守第一原则:编号、追溯、可验证、台账口径。

### 第6步 · 配图
把架构图/数据流/主流程写成一份 `figures.json`,`python3 scripts/make_figures.py figures.json -o <目录>/figures`
生成工程风 PNG(`layered` 分层架构 / `flow` 流程图)。在 Markdown 用 `![图7-1 系统总体架构](figures/fig-arch.png)`
引用,正文写"如图7-1所示"。ER 图、时序图保持 Mermaid(在 .md 里可视化;docx 里降级为源码块)。

### 第7步 · 全文自检(去模糊化 / 朗读自审 / 双向追溯)
出稿前对照 `references/req-analysis-principles.md` 的**朗读自审清单**逐项过并修掉,重点:
- **去模糊化**:`grep` 一遍"快/友好/健壮/稳定/大约/安全/高效/实时"等词,逐个换成带数字的
  可验收描述(对照去模糊化词表),换不了的标〔批注〕。这是规格最值钱、最容易偷懒的一步。
- **备选流与边界**:每个备选流都写明了系统行为?边界(0/负/空/超长/并发重复)都定义了?
- **双向追溯**:从左查每个业务目标有功能承载(不遗漏),从右查每个功能都有需求支撑(无孤儿功能);
  追溯矩阵无断点。
- **可验证 / 一致 / 不混**:每条需求有可测验收标准;实体/模块/接口/字段全文同名、接口与表字段口径
  吻合;需求章无技术选型、设计章无新需求。
- **编号与残留**:编号连续、目录与正文一致;无模板提示语残留;假设均有 `〔批注〕` 且进了开放问题清单。

### 第8步 · 出 Markdown + 转 .docx + 回执
1. Markdown 成稿落盘(这是可进版本库、可继续改的主产物)。
2. `python3 scripts/build_docx.py 规格.md -o 详细规格说明书-<系统名>.docx` 生成交付版 .docx。
3. 一次性交付,附**回执**(这是用户唯一的审阅入口,要让它顶用):
   - **开放问题清单**:逐条列出本次自行做的关键假设与缺口(哪一章、假设了什么、影响什么),
     方便用户事后一次性核对/纠偏;
   - **待手填项**:留空字段一览;
   - 一句话提示在 Word 里右键目录→更新域生成页码。

## 产出格式(喂给 build_docx.py 的 Markdown)
````

````text
# 工作流-可研:想法 → 可行性研究报告

把一段话的项目想法,落成一份合规、文风专业、版式贴合模板的《实验条件建设项目
可行性研究报告》。核心难点:一段话与 ~1 万字合规成稿之间隔着大量未知信息,且体例
强制要求"名称、数量、金额前后严格一致"。本工作流靠:**严格对照样例**定每节深度、
**逐章交互访谈**补事实、**联网检索**充实背景与单位基础、**事实台账**保证前后一致、
**专业术语**与**配图**提升质感、**全文自检**消重复与口径冲突。

## 资源
- `assets/sample-filled.docx` — **已成稿样例(最重要)**:虚拟电厂仿真,~9000字/7表。
  **每节写到什么深度、保留哪些章节,一律以样例为准**(样例≠空模板,见下"对齐样例")。
- `assets/template.docx` — 官方空模板(章节框架+每节提示语+四类目录+参编表)。
- `assets/fonts/NotoSansMonoCJKsc.otf` — 配图用中文字体(随技能分发,中英文齐全)。
- `references/chapter-playbook.md` — **逐章作业手册**:每章问什么、查什么、写到样例哪种深度、一致性红线。起草前必读。
- `references/tailoring-and-style.md` — 章节裁剪、公文文风、表格规范、**专业术语表**、**配图规范**、批注/脱敏策略、版式参数。
- `scripts/build_docx.py` — 结构化 Markdown(YAML frontmatter+正文+`![图](png)`) → 合规公文版式 .docx。
- `scripts/make_figures.py` — 生成系统架构图/业务功能图/技术路线图(工程蓝图技术风)。

## 对齐样例(贯穿全程的第一原则)
**先精读 `sample-filled.docx`,按它的实际章节与颗粒度来做,不要照空模板自由发挥。**
样例给出的真实做法(同类项目沿用):
- 章节按样例重排:`1概况 / 2背景必要性 / 3建设方案 / 4实施和组织管理 / 5投资 /
  6效益 / 7风险 / 8经济性财务合规 / 9结论`——软件/能力建设类**砍掉"外部建设条件"章**。
- 1.1 通常**只一句项目名称**;1.2 建设地点等脱敏项**可整节留空**;1.3 重在"研究范围";
  1.4 拆 `1.4.1编制依据(政策清单)`+`1.4.2技术原则(数条)`;1.6 含 1.6.1~1.6.5(进度/投资/里程碑/成果节点/控制要点,带多张表);1.8 用(1)必要性(2)可行性(3)建议。
- 用样例的措辞密度与表格样式;能用表(进度、投资、岗位、指标)就用表。

## 总流程(八步)

### 第0步 · 接收想法,建画像,定"批注模式"
1. 读想法 + 精读样例。判定**项目类型**(软件/能力建设 vs 物理工程,决定裁章)。
2. 产出《项目画像》草稿交用户确认:项目名称(暂定)、类型、定位、核心内容、规模量级。
3. **定批注模式**(关键,因用户而异):
   - **脱敏留空**(默认,适合熟悉模板的用户):缺口字段留空,由用户后续手填,不满篇批注;
   - **批注留痕**:每个假设就地标 `〔批注：…〕`(脚本渲染红色),出稿附批注清单回执。
   先问用户用哪种;拿不准用脱敏留空。
4. 建 `工作台账.md`,登记"已知事实/待确认假设",全程维护、单一来源。

### 第1步 · 对照样例裁剪章节
按"对齐样例"与 `tailoring-and-style.md` 裁剪表定下实际章节大纲(同类沿用样例结构),
写入台账交用户过目。**编号连续、目录与正文一致**。

### 第2步 · 逐章交互访谈(全交互)
**每章动笔前先问清,不要一次性问几十个问题。** 按 `chapter-playbook.md` 问题库一章一组:
- 用 `AskUserQuestion` 给带推荐项的选择题,或列编号问题。
- 答不上来的给**行业合理默认值**(脱敏留空模式下留空或写量级,批注模式下标〔批注〕)。
- 每组答复即时更新台账;关键事实(单位、地点、投资量级、技术路线、设备、周期)必落台账。

### 第3步 · 联网检索背景、依据与单位基础
用 `WebSearch`/`WebFetch` 检索**真实**资料:
- 第2章宏观背景、技术趋势;编制依据的政策/标准号(查不到的别杜撰文号)。
- **2.1.2 项目单位情况**:检索该单位在**本项目方向上**的真实基础(数据资源、相关平台、
  已开展工作),写"在此方向有哪些基础",**不是**工商注册式单位简介;涉密内容/具体科技
  项目名留给用户手填(可写"在科技项目方面，"作接口)。检索结论入台账并记来源。

### 第4步 · 逐章起草(用专业术语、把建设方案写厚)
按 `chapter-playbook.md` 与样例文风生成结构化 Markdown(见"产出格式")。纪律:
- **一致性红线**:名称/数量/金额/面积/周期只用台账值;改台账即全文同步。
- **专业术语**(见 `tailoring-and-style.md` 术语表):用规范叫法,如"用电信息采集系统""
  营销业务应用系统""新型电力负荷管理系统",勿用"营销系统/计量系统"等口语化说法。
- **建设方案(第3章)要厚、有技术含量**,写到方法层:
  - 系统功能逐模块写"做什么+用什么方法+输出什么";
  - 系统架构分层写到组件/接口/数据流;
  - 关键技术写"痛点+具体方法路径+对项目的支撑";
  - **加 `数据方案`(来源/粒度/处理流程/质量安全)与 `关键技术指标表`**(指标+设计目标)。
- 进度/投资/岗位/指标等用**表格**;投资分项之和必须=总投资。

### 第5步 · 配图
`python3 scripts/make_figures.py <项目目录>/figures` 生成三张图(可按项目改文案):
系统架构图、业务功能图、技术路线图。风格=**工程蓝图技术风,克制不花哨**(浅点阵底纹、
深蓝+青色 accent、箭头标注流转的数据对象、卡片内嵌方法标签、架构图含纵向支撑栏)。
在 Markdown 用 `![图3-1 系统架构图](figures/xxx.png)` 引用,正文写"如图3-1所示"。

### 第6步 · 全文自检(一致性 / 重复 / 术语 / 口径)
出稿前逐项过并修掉:
- **一致性**:名称/数量/金额全文一致;分项和=总投资;指标表与正文吻合;编号连续不跳号。
- **去重**:跨节不重复同一"定位句/套话";相邻段不连用同一短语(如两处"填补…空白")。
- **术语**:全文系统名/概念用规范术语,无口语化残留;`grep` 旧词排查。
- **时间口径**:进度在 1.6、4.1、里程碑等处跨章一致(月份/季度口径统一)。
- **残留**:无模板提示语残留;脱敏留空字段确为空(非半截话),批注模式下假设均有批注。

### 第7步 · 生成 .docx + 回执
1. `python3 scripts/build_docx.py 内容.md -o 输出.docx`(自建公文版式:仿宋_GB2312三号正文、
   黑体三号标题、方正小标宋封面、页边距上4/下3/左右2.8cm;生成封面/签署页/参编表/目录域;
   嵌入 `![]()` 配图;`〔批注：…〕`渲染红色)。文件名仿样例
   `实验条件建设项目可行性研究报告-<项目名称>.docx`。
2. 给用户**回执**:列出待手填项(脱敏留空字段)或全文批注清单(批注模式),便于一次性回填。
````

````text
# 工作流-科技可研:想法 → 科学技术项目可行性研究报告

把一段话的科技项目想法,落成一份合规、文风专业、版式贴合模板的《国网浙江省电力有限
公司科学技术项目可行性研究报告》。核心难点:一段话与 ~2 万字合规成稿之间隔着大量未知
信息,且体例强制"研究内容与实施方案逐条对应、预期目标与研究内容一一对应、经费分项之和
=总经费"。本工作流靠:**严格对照样例**定每节深度、**逐章交互访谈**补事实、**联网检索**
充实背景与研究现状、**事实台账**保证前后一致、**专业术语**与**配图**提升质感、
**全文自检**消重复与口径冲突。

> 本技能脱胎于 `idea-to-feasibility`(实验条件建设项目可研),复用其公文渲染与配图底座,
> 但**体例、章节、经费科目、封面完全不同**。两者勿混用:实验条件建设=买设备建条件建平台;
> 科技项目=做研究开发出成果。判断不准时看模板封面抬头("科学技术项目")与章节(有"国内外
> 研究水平综述""理论和实践依据""研究内容和实施方案")。

## 省份适配(默认浙江,换省必读)
本技能的 `assets/template.docx`、`sample-filled.docx`、经费科目、文号均取自**国网浙江省电力
有限公司**,默认按浙江出稿。国网各省科技项目可研共性大(同遵《国家电网公司科技项目预算编制
实施细则》),但**细节不通用**。**目标不是浙江时,先做以下校准,缺该省模板就停下来找用户要,
不得照搬浙江、更不得臆造别省文号/科目:**
1. **拿到该省模板 + 样例**(同今天浙江的两份),用 python-docx 抽其章节框架与经费表科目。
2. **改封面**:`build_docx.py` 封面单位用 frontmatter `封面单位` 字段即可换(无需改码);核对该省
   封面是否仍是"两张信息表"版式,不同则改 `add_cover`。
3. **核对章节裁剪表**(`tailoring-and-style.md`):章节增删/编号是否与浙江一致。
4. **核对经费科目**(最易出错):该省 25 行科目名称、取费比例、配套口径、审计费档位逐条对模板改写。
5. **换文号**:把浙江相关文号换成该省/国网现行有效文号,查不到的留空待手填,**不杜撰**。
建议:多省常用时,按省另存模板/样例(如 `assets/template-江苏.docx`)并在台账记录所用省份版本。

## 对齐样例(贯穿全程的第一原则)
**先精读 `sample-filled.docx`,按它的实际章节与颗粒度来做,不要照空模板自由发挥。**
样例给出的真实做法(同类项目沿用):
- **章节用中文编号**(一、二…十二),节用 1.1 / 1.1.1 / 1.1.1.1,最深到**四级**。
- 第七章(项目实施单位的条件)**整章留给用户手填**,正文从"六"直接跳到"八"(样例即如此),
  但编号不要错——按模板该是"七",工作流产出时此章**只留标题占位**或按用户选择处理。
- **第四章是绝对核心**(占全文约六成):4.1 项目研究内容按"研究内容一/二/三/四"列,每个
  研究内容下挂 3~4 个子专题(4.1.1.1…);4.2 项目实施方案**逐条对应 4.1 的每个子专题**写"怎么做"。
- 1.3/1.4 在样例里**进一步细分**(1.3.1 应用途径 / 1.3.2 推广途径;1.4.1 直接效益 / 1.4.2 间接
  效益);2.2 细分国外/国内现状;3.1 理论依据按"多目标优化/动态包络/强化学习/数字孪生…"逐条列。
- 能用表(分工、进度、预算、人员)就用表;经费表严格按模板科目。
````

````text
# 工作流-专利:论文/成果 → 中国发明专利申请材料

把一份(最好尚未公开的)研究成果,落成一套可直接交代理机构定稿的发明专利材料。
核心难点:① 论文语气≠专利语气(论文讲创新点,专利要"充分公开+界定边界");
② 方法/算法类发明易被判"智力活动规则"而不适格;③ 新颖性常不在单点而在组合;
④ 一旦论文先公开就破坏新颖性。本工作流用**技术内核提取→查新研判→先权项后说明书→
黑白线条附图→交底书**串起来,并全程守住两条红线(见下)。

## 🔴 两条贯穿全程的红线(最优先)

1. **先专利,后论文**:论文/预印本/答辩/任何公开发表都会破坏新颖性,且中国专利法
   第24条6个月宽限期**不覆盖**普通期刊发表。**必须在成果公开前提交专利并拿到申请号。**
   开工第一件事就是确认公开状态;若论文已公开或排期不可逆,立即走「加急路径」(见
   `references/filing-process.md`)。
2. **客体适格**:方法/算法/模型类发明,务必把算法**绑定到具体技术系统**(真实设备、
   物理量、数据流)并强调**技术效果**(降本/降耗/提效等可测量的物理改善),写成"控制/
   调度一套真实系统"而非"解一道数学题"。否则易被以"智力活动的规则和方法"驳回。

## 总流程(七步)

> 在用户的工作目录下建一个 `专利/` 子目录(或 `5_专利/`)作为产出区,并建 `工作台账.md`
> 登记"已知事实/待确认假设/检索结果",全程维护。

### 第0步 · 收成果,守红线,定基调
1. 读取用户提供的成果材料:**论文稿、数据、结果图、公式、代码、可研/需求**都要读。
   数据/图/公式往往比一句话描述更能还原真实技术方案——**逐个看**(含图片用 Read 看)。
2. 🔴 **确认公开状态**:论文是否已投稿/预印/答辩/任何公开?用 `AskUserQuestion` 问清。
   - 未公开 → 最佳窗口,正常推进,并提醒"提交拿到申请号前别公开"。
   - 已公开/排期不可逆 → 读 `filing-process.md` 加急路径,以"先拿申请号"为第一目标。
3. 用 `AskUserQuestion` 定三件事:**专利类型**(方法/系统类默认发明专利;纯硬件结构可
   考虑实用新型或双报)、**申报方式**(推荐"自写交底书+草稿,再交代理机构定稿")、
   **权属**(是否职务发明、是否有合作方——先理清再定申请人)。

### 第1步 · 技术内核提取 + 可专利点清单(关键)
1. 通读全部材料,**反推出技术方案的骨架**:系统组成、输入、关键步骤/模块、输出、
   约束与公式(给变量物理含义)、量化效果(从数据/结果里取真实数字)。
2. **列可专利点清单 P1…Pn**:每个发明点 = 一个"区别于现有技术的特征 + 它带来的技术
   效果"。这是后面每一条权利要求的种子。给每个点标注证据(哪张图/哪个数据/哪个公式)。
3. 产出《技术内核确认稿》交用户校正——**源材料常不完整或有歧义,把你的反推明确标
   〔待确认〕让用户改**,这是所有材料的地基。未确认前不要硬写进权利要求。

### 第2步 · 检索查新 + 新颖性研判
按 `references/novelty-search.md`:
1. 用 `WebSearch`(中英双语)检索最接近的在先专利/论文,逐发明点找"它有什么/我多什么"。
2. **诚实研判**:单点(如某优化方法、某感知策略)常已被公开;新颖性多落在**要素组合 +
   具体集成系统**。逐点给"已覆盖/部分覆盖/可主张"的判断。
3. 据此定**独立权利要求策略**:必要时把关键区别特征上收进独权(收窄换授权概率),
   或采用"宽独权 + 窄独权并列"。产出《检索查新报告》。
4. 提醒:这是自检,不能替代代理机构/查新机构的专业检索。

### 第3步 · 撰写三件套(**先权利要求,后说明书,再摘要**)
读 `references/drafting-playbook.md`,套 `templates/`:
1. **权利要求书**:1 条方法独权(含核心区别特征组合)+ 从权层层设防(把其余发明点、
   可替代方案逐条变从权)+ 系统独权 + 存储介质/电子设备独权(软件类必备兜底)。
2. **说明书**:技术领域→背景技术(只讲现有技术痛点,不剧透自己方案)→发明内容(要解决
   的问题/技术方案/有益效果三件套齐全)→附图说明→具体实施方式(最长最实,公式给物理
   含义,≥1个可复现完整实施例,覆盖可替代方案)。**自查:权利要求每个特征都能在说明书
   找到支持**(驳回高发点)。
3. **摘要**:≤300字,含领域+问题+方案+效果,无宣传语;指定一张摘要附图(通常是总流程图)。
   写完务必用脚本或字数统计核对≤300。

### 第4步 · 出黑白线条专利附图
按 `references/drafting-playbook.md` 制图规范,用 `scripts/figs_helper.py` 改写:
- 必含至少一张方法流程图;系统类加架构框图;数据结论可出线条曲线图。
- 硬规范:**纯黑白线条、无彩色/无灰度照片/无截图**、部件用阿拉伯数字标记(与说明书一致)、
  缩印仍清晰。把彩色结果图**重绘**成线条示意图,不要直接塞彩图。

### 第5步 · 写技术交底书
套 `templates/技术交底书模板.md`,面向代理人,把第1步的内核、第2步的对比文件、可替代
方案、量化效果整理成交底材料(代理人据此定稿)。

### 第6步 · 转 Word + 汇总交付
1. `python3 scripts/md2docx.py <产出目录>` 把全部 .md 转成 `word版/*.docx`;附图可单独
   生成 `说明书附图.docx`(把图嵌入)。
2. 产出 `README_材料清单.md`:文件清单 + 发明点↔权利要求对照 + **提交前核对清单**
   (技术准确性由用户拍板的项 + 法律/流程项)。
3. 给出**下一步**:用户确认技术点 → 选代理机构定稿 → 电子提交+缴费+费减+实审
   (照 `references/filing-process.md`)。再次提醒🔴先专利后论文。
````

````text
# 工作流-答辩PPT:任务书 → 答辩汇报 PPT

把一份《项目任务书》落成一份**答辩级、版式严格对标母版**的项目汇报 PPT。核心难点:
答辩 PPT 要求极严、高度图形化(几乎无纯文字页),手工做耗时且风格难统一。本工作流靠
**母版克隆**(复用范本 PPT 全部版式/配色/配图,只改文字+增删课题页)、**逐章交互访谈**补
任务书外的事实、**联网检索**充实背景、**占位批注**把无法自动复刻的复杂图交还用户手动替换、
**PIL 重建 QA** 在无 LibreOffice 环境下查版式问题。

## 资源
- `assets/template.pptx` — **母版(最重要)**:国家重大专项答辩范本,46页,16:9。青绿低碳配色
  (主色#00706B/#039093,强调#C00000),封面方正小标宋、正文微软雅黑。**一切版式以它为准**。
- `assets/slot-map.json` — 母版 801 个文本槽位地图(slide+path 定位+原文+字号+色)。机器可读。
- `references/slot-anchors.md` — 槽位锚点字典(每页关键 path),写 fills 时查它定位。
- `references/page-playbook.md` — **页型作业手册(起草前必读)**:46页骨架、任务书→各页映射、
  课题页增删规则、占位批注用法、全局替换边界。
- `scripts/parse_task.py` — 任务书(.docx/.pdf)→ 纯文本(+扫描页转图供视觉读),供你通读理解。
- `scripts/build_pptx.py` — **克隆引擎**:读 fill-plan.json,增删页+按 path 填字(保样式/字号
  自适应)+加占位批注,输出 .pptx。原语(整页深拷贝含图、删页、填字)均已验证。
- `scripts/gen_slotmap.py` — 重建槽位地图(执行 ops 改了页序后须重跑,得到新 path)。
- `scripts/render_qa.py` — 无 LibreOffice 下 PIL 整页重建为 PNG,供视觉 QA。

## 第一原则:对齐母版
**不自由发挥版式。** 母版每页长什么样,产出就长什么样——只换文字、按课题数增删课题页、
复杂图留原图占位。新项目主题即使与"青海低碳"不同,也沿用这套五章答辩骨架与视觉系统。

## 总流程(七步)

### 第0步 · 收任务书,建画像
1. 用 `parse_task.py` 把任务书转文本(扫描件转图,必要时 OCR/视觉通读)。**通读全文**。
2. 精读 `page-playbook.md` 与母版(可先 `render_qa.py assets/template.pptx /tmp/tpl 1,13,28` 看几页)。
3. 产出《项目画像》交用户确认:项目名称、负责人、承担单位、**课题数 K 及各课题名**、
   示范地区/对象、科学问题、技术挑战数、考核指标要点、经费(总/国拨/自筹)、进度里程碑。
   课题数 K 是后续增删的关键,务必先定。

### 第1步 · 定批注模式 + 建台账
- **批注模式**(问用户):①**脱敏留空**(默认):任务书没写的字段留空由用户手填;
  ②**批注留痕**:每处假设就地标占位批注。复杂图一律走占位批注(见 playbook 第五节)。
- 建 `工作台账.md`:登记 已知事实/待确认假设/全局替换表/课题对增删计划,全程单一来源维护。

### 第2步 · 逐章交互访谈(全交互)
**每章动笔前先问清,不要一次性问几十个问题。** 按 `page-playbook.md` 分章问,用
`AskUserQuestion` 给带推荐项的选择题或编号问题。重点补任务书未覆盖项:负责人/课题负责人简介、
单位完整列表、藏头诗主题词、复杂图是否由用户提供成图。联网检索充实政策背景/研究现状(检索免确认)。

### 第3步 · 先做结构(ops),再重建 slot-map
1. 据课题数 K 写 `ops`(增删课题对,见 playbook 第三节),先**只跑 ops** 出中间稿:
   `python scripts/build_pptx.py plan_ops_only.json mid.pptx`
2. 对中间稿重跑 `gen_slotmap.py mid.pptx mid-slotmap.json`,得到**增删后的真实 path**。
   后续 fills 一律以 mid-slotmap 的页号/path 为准。(K=5 时可跳过,直接用母版 slot-map。)

### 第4步 · 写填充计划 fill-plan.json
按 `page-playbook.md` 逐页把任务书内容映射到 fills(slide+path+text)。要点:
- 文风对齐母版:短句、要点化、关键数字用具体值;一句话概述放主段槽位。
- 全局替换只用于高频纯专名;青海专有数据(场站/千瓦/县名/单位)按页 fills 改或留占位。
- 复杂图页(技术路线/架构/大屏/饼图/照片)只填标题与概述,图本身写进 `notes` 占位批注。
- 致谢藏头诗按新主题重写(两句七言、点题)。

### 第5步 · 生成 + QA(必做至少一轮)
1. `python scripts/build_pptx.py fill-plan.json out/答辩PPT.pptx`
2. `python scripts/render_qa.py out/答辩PPT.pptx /tmp/qa 1,13,14,28,34,43,45`
3. **派子代理**按 pptx 技能视觉 QA 清单查错:溢出/错位/配图丢失/占位批注到位/课题增删后
   页序与目录一致/无残留原项目字样。列出问题 → 改 fills/notes → 重新生成 → 重验受影响页。

### 第6步 · 交付
交付 .pptx + 一份《占位清单》(列出所有需用户手动替换的复杂图与留空字段及其页号),
并说明:复杂图(技术路线/架构/大屏/经费饼图/负责人照片)需用户用任务书对应图手动替换。

## 红线
- 不改版式/配色/字体/母版图形结构;不删除非课题类固定页;不把复杂图强行自动改图内细标签。
- 增删页后必重建 slot-map 再写 fills,否则 path 错位。
- 产出前必跑一轮 render_qa 子代理视觉 QA。
- 所有自动无法复刻的图,必须有占位批注,不能静默留旧项目的图冒充新内容。
````

````text
## 第一原则(贯穿全程)
1. **条款可追溯** —— 每个测评项都标注对应 GB/T 25000.51-2016 的质量要求/GB/T 25010 子特性,报告可回溯。
2. **以"声称"为基准** —— 功能与质量是否符合,以**产品说明 + 用户文档集**所声称的为准;产品没声称的
   功能不替它脑补,声称了却缺失/不正确即判不符合。所以**产品说明与用户文档集审查必须最先做**。
3. **证据留痕** —— 每项结论都挂证据(命令输出/日志/截图/数据文件的路径),报告附"证据索引"。
4. **不谎报** —— 自动项如实统计:跑不起来记 `ran:false`,未授权记 `skipped`,缺工具记 `degraded:manual`。
5. **渗透授权红线** —— **无书面授权、无明确范围与时间窗,绝不执行渗透测试**;越界立即停并上报。
6. **脱敏** —— 报告中凭据、真实业务数据、内网拓扑等敏感信息脱敏处理。

1. **产品说明审查**:完整性、正确性、一致性、可测试性、标识与说明信息(按 standard-map.md 清单逐条记)。

### 阶段2 · 测评设计(派生测评项与用例库)
按 `quality-playbooks.md` 与 `security-playbooks.md`,对**选定的每个子特性**派生测评项:

### 阶段3 · 测评执行(自动跑 + 人工取证)
- **可自动化度量项** → 用 `scripts/run_scans.py` 或启动 `auto-measure.workflow.js` 并行执行:

- **人工/取证项** → 按各 playbook 的记录模板执行并逐项留痕:产品说明/文档审查、易用性、用户文档测试、

- 本机执行约定(沿用):用绝对路径、避开 8080 端口、起服务用 `PORT` 覆盖、等服务就绪用
  `curl --retry` 轮询而非 `sleep`、执行类子代理用有 Bash 的 agentType。
- **如实统计**:任何跑不起来/未授权/缺工具的项都显式标注,不得以"通过"掩盖未执行。

### 阶段4 · 结果判定与报告
1. **逐测评项判定**:`符合 / 不符合 / 不适用`;不符合按缺陷分级(严重/重要/一般/提示,见 report-and-style.md)。
2. **汇总**:子特性→特性→产品级结论;按测评准则给出**是否通过测评**的总体结论与不符合项整改建议。
3. 生成结构化报告 Markdown(格式见 report-and-style.md),含:封面、签署页、测评依据与对象、测评环境、
   产品说明与用户文档集审查结论、**逐特性测评结果表**、安全测试结果、缺陷清单、总体结论、**附录证据索引**。
4. `python3 scripts/build_report.py 报告.md -o <产品名>-软件产品质量测评报告.docx`
   —— 同时产出同名 `.html`(可点击章节导航)。文件名形如
   `软件产品质量测评报告-<产品名>-<版本>.docx`。
````

````text
# 工作流-打包:静态网页 → Windows 安装程序 (.exe)

把任意"能用浏览器打开的静态前端目录"变成一个**单文件 Windows 安装程序**。
最终用户双击 exe 安装 → 桌面出现图标 → 双击图标**以应用窗口方式直接打开**
(无地址栏/标签页,像原生程序) → 全程离线、目标机不需要装任何依赖。

## 适用前提
- 输入是**纯静态**前端目录:有一个入口页(默认 `index.html`),页面间用相对路径引用,
  依赖(如 Tailwind/ECharts/字体)已**本地化**或可离线工作(没有必须联网的 CDN/接口)。
- 若依赖仍指向 CDN,先把它们 vendor 到本地、改成相对路径(否则离线打开样式/图表会缺失)。

## 一步到位
```bash
bash /home/work/.claude/skills/webapp-to-installer/scripts/pack.sh \
  --app-dir "/path/to/静态站点目录" \
  --name "显示名称" \
  [--out "/输出/安装-显示名称.exe"] \
  [--slug InstallId] [--entry index.html] [--icon /path/app.ico] \
  [--port 48710] [--version 1.0]
```
- `--app-dir` 必填:静态站点目录(会被整体内置进 exe)。
- `--name` 必填:显示名(用于标题、桌面图标名、开始菜单分组)。
- `--out` 默认 `<app-dir 同级>/安装-<name>.exe`。
- `--icon` 不给则自动生成(有 Pillow 时)或用 `assets/default.ico`。
- `--port` 本地 http 服务端口(默认 48710,非通用端口)。
- `--mode file|server`(默认 `file`):
  - `file`:桌面图标以 `--app=file://` 直接打开,适合**经典脚本**的纯静态站点(无 ES Module、无 fetch 本地文件)。
  - `server`:桌面图标经 `打开平台.vbs` 隐藏启动内置 PowerShell 静态服务,再以 `--app=http://localhost:<port>` 应用窗口打开。**当站点用 ES Module / 需要 http 源 / 有相对 fetch 时必须用 server 模式**(否则 file:// 下模块与 fetch 会被 CORS 拦截)。仍是双击、零安装、离线。

脚本会:复制站点→清理垃圾→放图标→注入 `server.ps1`/`启动-本地服务.bat`/`使用说明`
(若站点没有)→用模板渲染 NSI→`makensis` 编译→校验 PE→打印输出路径。

## 产物里给最终用户的东西
- **桌面图标**「<name>」:Edge/Chrome `--app` 应用窗口直接打开入口页;无浏览器时回退默认浏览器。
- **开始菜单**:打开 / 本地服务(http链接) / 使用说明 / 卸载。
- 安装到 `%LOCALAPPDATA%\<slug>`(**不需要管理员**),进"程序和功能"可卸载。
- 完全离线、零依赖(http 链接用 Windows 自带 PowerShell,也无需装 Python/Node)。

## 给智能体的注意事项
- 工具链在 `assets/toolchain/`(makensis + nsisdir 的 Stubs/Include/Contrib/Plugins)。
  `pack.sh` 会自动 `export NSISDIR`,无需联网。
- **本机无法运行 Windows exe**:产物是用官方 NSIS 编译器(本仓自编 aarch64 `makensis` +
  NSIS 3.10 官方 Windows stub)生成的标准 NSIS 安装包,PE 结构校验通过,但**未在真机跑过**;
  交付时请提示用户在 Windows 上双击验证。
- 安装包**未数字签名**:首次运行可能触发 SmartScreen"未知发布者",点"更多信息→仍要运行"即可;
  告知用户属正常现象。
- 中文:NSI 以 UTF-8 + BOM 喂给 `makensis -INPUTCHARSET UTF8`,中文名/路径正常。
- **工具链缺失或换了机器架构**(makensis 跑不起来)时:运行
  `bash scripts/bootstrap-toolchain.sh` 重建(需 g++/pip/外网/zlib)。
- 自定义图标:`scripts/make_icon.py OUT.ico` 生成深色科技风图标(需 Pillow)。

## 文件
- `scripts/pack.sh` — 主入口(打包)。
- `scripts/make_icon.py` — 生成 .ico。
- `scripts/bootstrap-toolchain.sh` — 重建 NSIS 工具链(兜底)。
- `assets/installer.nsi.tmpl` — NSIS 模板(@TOKEN@ 占位)。
- `assets/toolchain/` — 自带 NSIS(makensis + nsisdir)。
- `assets/default.ico` — 默认图标。
- `assets/templates/` — 注入到站点的 server.ps1 / 启动-本地服务.bat / 使用说明。
````

````text
# Word 插图检查与修复 SOP

把一份“带配图的 .docx”过一遍**结构体检 + 肉眼质检**,定位并修掉让插图“看起来坏掉”的问题。
这些问题大多不是内容错,而是**渲染/版式坑**:文件结构没错但 WPS 不显示、或图内排版越界。
本技能 = **只读体检脚本**(抓结构性硬伤)+ **逐张视觉核查**(抓溢出/遮挡/缺字)+ **修复清单**。

## 何时触发
- 用户反馈:“word 里没有配图 / 图不显示”“图片是空白/细条”“图上文字超出框了”“图里文字遮挡/压线了”“缺了字显示成方框”。
- 主动场景:交付任何**含 matplotlib 等代码绘图配图的 .docx**(如可研、实施方案、报告)前的插图质检。

## 体检流程

### 第 1 步 运行体检脚本(结构性硬伤)
```
python3 <skill>/scripts/check_docx_figures.py "<文档.docx>" --extract
```
脚本只读、不改原文件,输出 5 段:
1. **zip 完整性**:`word/media/` 实体数、正文 blip(`r:embed`)数、图片关系数应三者一致。
2. **内联图片清单**:每张图尺寸(cm)+ 所在段落**行距规则**。出现 `EXACTLY`(固定行高)且磅值 < 图高 => 标 `[严重]`。
3. **疑似图题**:列出紧邻图片下方的“图N…”段落,用于判断是否与图内标题重复。
4. **问题清单**:自动汇总 `[严重]/[警告]/[提示]`。
5. **导出目录** `<文档同目录>/_figcheck/`:把所有图导出,供逐张 Read。

### 第 2 步 逐张视觉核查(脚本看不出的版式问题)
用 `Read` 打开 `_figcheck/` 里每张图(大图可先用 PIL 裁成上/中/下区块再 Read,看得更清),逐项检查:
- **① 溢出**:文字/数字是否伸出所在矩形框、色块或圆形边界。
- **② 遮挡/压线**:标注文字是否压在箭头、连线、相邻图形或另一段文字上;旋转的竖排标签是否贴住箭头。
- **③ 缺字方框**:是否出现“□”——多为字体缺该字形(中文字体缺拉丁/标点,或反之)。
- **④ 重复图题**:图片内部是否烤入了“图N…/标题”,与 Word 正文图题重复。

### 第 3 步 按问题修复
见下方“问题—修复”清单。配图由脚本生成时,**改绘图脚本并重新出图**;再重建 .docx;最后**重跑第 1 步**确认 0 严重项,并重看修改过的图。

## 问题 — 修复 清单(高频坑)

| 现象 | 根因 | 修复 |
|---|---|---|
| WPS/Word 里图是**空白或一条细缝** | 图片所在段落被设了**固定行高**(`paragraph_format.line_spacing=Pt(N)` 会令规则=EXACTLY),N 小于图高 => 裁切 | 图片段落**不要设固定行高**:`line_spacing` 留默认(单倍),只用 `space_before/after` 控制间距 |
| 图**完全不显示**,但文件能打开 | blip 的 `r:embed` 在 rels 里找不到、或关系指向的 `media/*` 缺失、或 Content_Types 没声明 png/jpeg | 重新用 `run.add_picture()` 正常插入;勿手工拼 XML。脚本第 1 步会指明缺哪一环 |
| 图内文字**超出框线** | 文本太长/字号过大 vs 框宽;或绝对坐标放置未估算文本宽度 | 缩短文案、降字号、加宽框体、或换行;中文按 ~字号pt 估算每字宽度反推可容字数 |
| 标注**相互遮挡/压住箭头** | 标签离图元太近;双向箭头的平行标签间距不足;旋转竖排标签贴住箭杆 | 加大标签与图元的**垂直偏移**;拉开双箭头间距;标题与图形间留白(必要时扩大坐标轴上边界) |
| 出现 **“□” 方框** | 字体缺字形。matplotlib 里中文字体(如 Droid Sans Fallback)常缺拉丁/标点,纯西文字体缺中文 | 用**逐字回退**:`plt.rcParams['font.family']=['DejaVu Sans', '<中文字体名>']`(西文在前、中文兜底);设 `axes.unicode_minus=False`;渲染后 `grep -ci glyph` 应为 0 |
| 图内标题与 Word 图题**重复** | 绘图时在图底/顶烤了“图N…”,Word 又加了图题 | 去掉**图片内**的“图N…”编号标题,编号统一由 Word 图题给出;图内只保留功能性图名/坐标标题 |

## matplotlib 中文配图小抄(生成端预防)
- 注册并逐字回退中文字体:
  ```python
  from matplotlib import font_manager as fm
  fm.fontManager.addfont('/path/DroidSansFallback.ttf')           # 或系统已装中文字体
  CN = fm.FontProperties(fname='/path/DroidSansFallback.ttf').get_name()
  plt.rcParams['font.family'] = ['DejaVu Sans', CN]               # 西文在前、中文兜底 => 不缺字
  plt.rcParams['axes.unicode_minus'] = False
  ```
- 出图后自检:命令行运行脚本时 `2>&1 | grep -ci glyph` 必须为 0(有缺字会打 `Glyph missing` 警告)。
- 放进 Word 时,图片段落**别用固定行高**(这是“图不显示”的头号原因)。

## 收尾
- 清理临时目录 `_figcheck/`(体检产物,非交付物)。
- 给用户**逐图结论**(哪张哪处改了什么)+ 复检结果(脚本 0 严重项),并提示关掉再打开文档以避免读到缓存。
````

**第 2 步 · 建 5 个斜杠命令**（`~/.claude/commands/<name>.md`，**文件名 = 命令名**）。下面这段整体跑一遍即建好（`'EOF'` 带引号 → `$ARGUMENTS` 与反引号原样落盘，不会被 shell 展开）：

````bash

## 立即执行

```

```
## 规则
- $ARGUMENTS 为空 → 先让用户提供文件路径，不要凭空跑。
- PDF 不能直接喂：先 `pip install pypdf` 抽成 .md/.txt。
- style 仅 auto/gov/dashboard，非法值引擎中止。

EOF

---
description: 工作流-设计：原型+原始需求 → 技术设计文档+HTML设计说明书（proto-to-design）
argument-hint: <原始可研/需求文件，可省略>
allowed-tools: Workflow, Bash, Read, Write, Edit, Glob, Grep
---
# /design — 研发工作流第 2 环（原型→设计）
承接 prototype/ + 原始需求，反推技术设计（架构/数据流/数据库/接口/安全/运维/非功能性/集成），出 Markdown+Mermaid 与 HTML 说明书。
```
Workflow({ name: 'proto-to-design', args: { reqFiles: "$ARGUMENTS", protoDir: 'prototype', outDir: 'design', dims: 'all', style: 'auto' } })
```
- 前置：当前目录需有 prototype/（先跑 /proto）。$ARGUMENTS 可省略。
- dims 可传子集（如 ['database','security']），architecture 始终强制保留置顶。
- outDir/protoDir 均生效。产物在 design/。规模大（~20 子代理/~百万 token/~20 分钟），跑完核对落盘。
EOF

cat > ~/.claude/commands/build.md << 'EOF'
---
description: 工作流-开发：设计+原型 → 可本机真实运行的MVP实现（design-to-code）
argument-hint: (无需参数)
allowed-tools: Workflow, Bash, Read, Write, Edit, Glob, Grep
---
# /build — 研发工作流第 3 环（设计→开发）
把 design/ + prototype/ 落成可在本机真跑的 MVP（后端+前端+数据库+一键启动）。Plan 阶段自探测选依赖最轻的栈，不盲目跟企业栈。
```
Workflow({ name: 'design-to-code', args: { designDir: 'design', protoDir: 'prototype', outDir: 'app', run: true } })
```
- 前置：需有 design/ 与 prototype/。
- ⚠️ stack 是死参数，传了也不生效（一律自探测，实测选 Python 标准库 + SQLite）。
- run:false 只产码不验证；默认 run:true 会真起服务冒烟。
- 产物在 app/。引擎 prompt 已内置本机纪律：禁前台 sleep、避开 8080、后台起服务用 nohup+绝对路径。排除 data.db/__pycache__ 不入库。
EOF

cat > ~/.claude/commands/test.md << 'EOF'
---
description: 工作流-测试：实现 → 自动生成并执行单元+接口测试+通过率报告（code-to-test）
argument-hint: (无需参数)
allowed-tools: Workflow, Bash, Read, Write, Edit, Glob, Grep
---
# /test — 研发工作流第 4 环（开发→测试）
对 app/ 自动生成单元+接口用例、真实执行、出通过率与失败归因报告（MD+HTML）。
```
Workflow({ name: 'code-to-test', args: { appDir: 'app', run: true } })
```
- 前置：需有 app/（先跑 /build）。
- 失败分三类（设计如此）：test-bug（用例自身错，自修）/ code-bug（被测代码缺陷，列入 suspectedCodeBugs 交回开发环，不擅改业务代码）/ env。
- ⚠️ outDir 几乎摆设：报告固定落在 <appRoot>/test-report/。
- 产物 app/tests/ + app/test-report/。manifest.test.json 的 gatePassed = ran && failed===0 是 /deploy 的门禁。

# /deploy — 研发工作流第 5 环（测试→部署）
把 app/ 打成拷到别的机器、让智能体照 AGENT_DEPLOY.md 自主部署的可移植离线包。

- 前置：需有 app/。
- ⚠️ 测试门禁（阻断）：读 app/manifest.test.json 的 handoff.gatePassed，fail-closed（!== true 即拦）。测试没全绿或没跑过 /test 会被拒，返回 { error: 'test gate failed' }。先跑 /test 到全绿。
- rehearse:false 跳净室演练；offline 只影响演练是否模拟无网。
- 产物在 app/：DEPLOY.md / AGENT_DEPLOY.md / deploy.sh / stop.sh / Dockerfile / docker-compose.yml / *.service / .env.example / DEPLOY-BUNDLE.md。闭环末环。

ls ~/.claude/commands/   # 应见 proto/design/build/test/deploy .md
````

| --------- | --------------- | --- | --------- |
| `/proto`  | req-to-proto    | 原型  | 可研/需求文件路径 |
| `/design` | proto-to-design | 设计  | 原始文件（可省）  |

- **不跑 `restore.sh`** → 不覆盖目标机现有 `settings.json`/`plugins/`（§六补.0 已警告其 `cp -a` 覆盖 + 铺旧机 `model:opus[1m]`/`skipDangerousModePermissionPrompt:true`）；

### 六补.1 日常用法：一环一句话，逐环过目

### 六补.2 五环调用速查

> [!tip] 2026-07-16 起本机用 **slash 命令** 触发：`/proto` `/design` `/build` `/test` `/deploy`（装法见 §六补.0+，确定性命中、全局生效）。下表"触发词"列是 memory/skill 壳方式，**本机未装则不生效**。

| 触发词 | 引擎 | 吃什么 | 产出 | 常用 args |

### 六补.3 六条实操纪律（都是踩过的）

1. **跑完先核对产物落盘位置，再 `git add`。** `outDir` 经常不生效（根因：Workflow 经 scriptPath/background 启动时 `args` 收不到，属 harness 行为，见 §四补.3 根因框），产物常落在子代理 cwd 下，需手动搬。
2. **测试环不改业务代码。** 失败分 `test-bug`（它自己修）和 `code-bug`（列进 `suspectedCodeBugs` **交回开发环**由你定夺）——这是设计如此，不是它偷懒。
3. **`gatePassed` 是部署环的门禁。** `code-to-test` 的 `manifest.test.json` 里 `gatePassed = ran && failed===0`，部署环阶段1 会读它。测试没全绿就进部署，等于自己拆闸。
4. **想指定技术栈？传 `stack` 没用**（死参数），开发环一律自探测自选（实测选了 Python 标准库 + SQLite，零依赖）。要强制得改 plan 提示词。
5. **PDF 喂不进去**：先 `pip install pypdf` 抽成 .md/.txt 再喂。
6. **别指望 `run:false` 之外的中途暂停**——开发环门禁非阻断（scaffold 不过仅告警继续，只有 plan agent 未返回才中止，见 §四补.5）。

### 六补.4 换到新环境（如 macOS）先想一下

§四补.6 那套运行纪律（禁前台 sleep、避开 8080、绝对路径、`curl --retry` 轮询）是**旧机 `/home/work` Linux/aarch64 的坑**焊进 prompt 的。换到 sleep 不禁、8080 没被占的机器上，这些约定不会出错，只是白绕路。

真正要留神的是**开发 / 测试 / 部署这三个真跑命令的环**：它们会在你机器上装依赖、起服务、开端口、写文件。**首次在新环境跑，找个空目录拿个小需求试**，别直接对着正经项目跑。

### 7.1 全链路实践（一条龙跑通）

> [!example] 案例 A · 广义储能协同规划平台（新疆科技项目）—— 原型→设计→开发→测试→打包 全链路

> - **要点**：纯静态前端也能走完整链路；`app-to-deploy` 也被用来给这套 33 页静态原型打可移植部署包。

> [!example] 案例 B · 四币种实时汇率转换系统 —— 原型→测试→打包 exe
> - **原型**：`工作流-原型` 输入需求 md（人民币/美元/越南盾/U币 双向汇率、走势、提醒、换算）→ 每个原型独立 HTML + 详细注释，覆盖用户端 + 管理端；可指定风格（此处要求「严肃、准确、简单大方」）。
> - **测试**：`工作流-测试` 对后端做接口测试 —— `target=api_health_rates type=api`，源文件 `main.py` → 生成 `test_api_health_rates.py`。
> - **打包**：`工作流-打包`（webapp-to-installer）把 Web 应用打成 Windows .exe（离线、桌面图标）。

### 7.2 原型工作流的「多源输入」实践（req-to-proto 用得最多）

`工作流-原型` 是全家族里调用最频繁的（10+ 次）。真实输入源五花八门，说明它对输入格式很宽容：

- **思维导图 PDF** → 能碳管理平台原型（要求高保真、高端大气、交互炫酷）
- **采购计划 xlsx** → 提取功能需求 → 城乡垃圾流向监测平台 + 智慧环卫系统原型
- **答辩 docx** → 零碳园区多主体协同治理原型
- **可研 + 需求 + 设计方案（多文件）** → 浙江虚拟电厂仿真原型（要求体现「融合大模型智能体」创新点）
- **已结构化需求包** → VPP「仿真预测」模块原型（需求已拍板，跳过需求访谈直接出原型）
- **参考风格目录** → 可传入「参考 HTML 风格目录」让新原型对齐既有视觉

### 7.3 把通用工作流「fork 成项目专用工作流」（重要洞察）

> [!tip] VPP server 项目把通用工作流沉淀成了一套 `vpp-*` 专用技能
> - `vpp-req-to-change`（需求变更，带 `changeId`）→ `vpp-design` → `vpp-design-to-code` → `vpp-dev-integrate`（同一 `changeId=add-vpp-command-dashboard` 串起一次完整需求变更）。
> - `vpp-proto-to-design`（`protoDir=...prototypeV6`）、`vpp-feature-pipeline`（增量开发功能模块：需求规格 + 参考原型 → 重建模块）。
> - `vpp-metric-sql-backfill` —— **被调用 33 次**，是该项目最高频工作流：基于数仓表（`dwd_user_elec_15min_v1`、`dwd_adjustable_capacity` 等）按「行业+省+市+区县+时间点」维度算实时负荷/用电量/环比/峰谷差/可调能力等指标，产出「取数 SQL + 验数 SQL + 补数脚本」。
>
> **洞察**：通用工作流（req→design→code→...）可以按项目沉淀成带项目术语、带数仓表、带 `changeId` 流转的**专用工作流** —— 这正好印证 [[项目立项与研发流程规范]] 里「每个项目配一套自己的工作流 / AI 机器人」的主张。

### 7.4 文档 / 研究 / 测评类实践

- **科技可研**：`工作流-科技可研` 写《负荷侧虚拟电厂实时感知与电碳协同智能调控》2027 科技项目可研，以已定稿储备简表为内容来源、对标浙江电网可研模板。
- **答辩 PPT**：`工作流-答辩PPT` 输入「电碳协同发展基础理论」可研 doc → 答辩级 PPT。
- **软件测评**：`工作流-测评`（rusp-quality-eval）对某端口运行的程序做 GB/T 25000.51 测评。
- **深度研究**：`deep-research` 做地平线机器人（9660.HK）估值与走势研判、核查「绿电直供算力中心」真实落地情况。
- **选股估值**：`工作流-选股`（stock-growth-valuation）跑英伟达 NVDA、明略科技 02718、供销大集 000564。

### 7.5 编排 / 自动化实践

- **`loop` 自动续跑**：把多阶段流水线「一路跑完 + 限额中断后自动续跑」；也用于定时同步另一会话的进度（抓屏对比、简要汇报）。
- **`update-config` 自动留痕**：加 Stop hook —— 每轮结束检查工作流产物目录（`prototype/ design/ app/ tech/`）有无改动，有则自动 `git pull --rebase --autostash` + add + commit + push。把「工作流产物」纳入自动版本管理。

## 八、经验提炼（对照开发规范）

> [!summary] 实践验证了开发规范的哪些点
> - **原型驱动可落地**：`工作流-原型` 能吃 PDF/xlsx/docx/md 多种原始材料，直接产出高保真可交互原型 —— 印证规范「先原型、低成本收敛需求」。
> - **全链路可自动化**：原型→设计→开发→测试→打包能用 `loop` 串成一条龙并自动续跑 —— 单人负责制下，AI 工作流确实能补齐工种。
> - **工作流可 per-project 定制**：VPP 把通用工作流 fork 成 `vpp-*` —— 印证规范「每项目配专用工作流 / AI 机器人」。
> - **产物要纳管**：Stop hook 自动提交工作流产物 —— 对应规范「各阶段产出物入知识库」。

> [!warning] 用的时候注意
> - 工作流产物（尤其 AI 生成代码 / SQL）仍要**人工必检**（见规范 §五各阶段），别盲信。
> - 涉及内网地址 / 凭据 / 真实数据时先脱敏，工作流产物入公开库前自查。
> - 大任务用 `loop` 续跑前，先确认产物目录与提交策略（参考 7.5 的 Stop hook）。
