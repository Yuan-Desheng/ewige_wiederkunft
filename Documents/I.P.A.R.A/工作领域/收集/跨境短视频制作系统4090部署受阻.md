## 三、经过（2026-10-15）

时间顺序按当天操作，不是推测。

1. **探测正常**  
   本机 `curl http://192.168.66.84:8900/api/health`：`busy=0`，poller 活着，队列空，可以重启。  
   4090 **出网**也能访问 `124.71.104.207:8100` 和 `:8101`（health 200）。导入时由 4090 拉选品，网络方向是通的。

2. **SSH 先成功了一次**  
   `sshpass` + 交接文档密码登录 `development@192.168.66.84` 成功。看到已有 `~/.ecom_video_config.json`，当时**没有** `select_api_base` / `select_api_token`。线上 `app.py` 与仓库 `aebf74d` 一致，还没有导入页。

3. **第一次拷文件失败**  
   用本机 `id_ed25519` 做 `scp`（没走 sshpass）→ `Permission denied (publickey)`。4090 **没有**登记这台机器的公钥，只能密码登录。

4. **随后 SSH 被对端直接掐掉**  
   再连变成：`kex_exchange_identification: Connection closed by remote host`（TCP 能建上，密钥交换阶段被关）。  
   同一时段对 4090 有多次尝试：BatchMode 公钥失败、sshpass 成功、scp 失败、带 `-v` 的重试。短时间失败次数偏多。

5. **再往后连 22 都超时**  
   `nc` 一度仍显示 22 开着，SSH 已 `Connection timed out`。接着本机访问 **8900 HTTP 也失败**，Gitea `192.168.66.170:36731` 同样 `Connection closed`。更像办公室 `192.168.66.0/24` 被防护策略或主机 fail2ban 暂时封了源 IP，不单是密码错。

6. **没有执行成任何部署命令**  
   备份数据库、改 json、`./deploy.sh` 都停在 SSH 之前。线上进程仍是旧代码。

## 四、原因（归纳）

| 层级 | 事实 |
| --- | --- |
| 架构 | 9002 只是 FRP。部署对象永远是 4090 上的 `ecom_video_app`，必须 SSH。 |
| 鉴权 | 4090 只认密码，不认本机 SSH 公钥。每次部署都要交互式/sshpass，失败日志容易被当成扫号。 |
| 触发 | 公钥失败 + 密码成功 + 立即再试 scp/verbose，短时间多次握手。sshd `MaxStartups` 或 fail2ban 一类机制会在 KEX 阶段直接掐连接，再升级到丢包/超时。 |
| 不是 | 不是 9002 端口坏了、不是 Flask 自己拒绝部署、也不是选品 8101 接口没好。8101 导出当时已经能拉 10 条商品。 |
| 也不是 | 不是 GPU 忙：health `busy=0`，`deploy.sh` 的「忙则放弃重启」门槛没碰到。 |

一句话：**导入功能已经写好、选品侧已经能导出，卡在「这台开发机当时登不上 4090」。**

## 六、恢复后怎么做（避免再封）

1. 换一台没被封的机器，或等 4090 解封后再 SSH。**不要对 22 连打。**
2. 把本机 `~/.ssh/id_ed25519.pub` 加到 4090 `development` 的 `authorized_keys`，以后 `deploy.sh` 走密钥，少触发防护。
3. 一次会话里做完：备份 db → 写入 `select_api_base=http://124.71.104.207:8101` 和 token → `./deploy.sh` → health 确认 poller。
4. 用一个已发布 sku（如 `tt:1737907273257224157`）在商品库导入，**不要提交出片**。
5. 导入页能打开、商品详情有「选品台账」徽章，即 8900 与 9002 同时可用。

8101 这次编进去的二进制带有当时工作区里未提交的核价表改动（日常测试机惯例）。正式 8100 未动。视频侧合 `main` 前走 Gitea PR：http://192.168.66.170:39979/zhanwei/video-pipeline/pulls/new/feature/select-integration

## 七、2026-10-18 复核（Claude Code 远程诊断）

当天从 Legion 笔记本重新尝试部署，**结论：4090 服务健在，卡点变成「本机无真实路由到 66 网段」**，与 10-15 的 fail2ban 封禁是两回事。

已核实的好消息：

- **Flask 活着**：公网 FRP 入口 `http://47.93.236.30:9002/api/health` 返回 `busy=0`（之前 8900「空回复」是本机代理假象，不是服务挂了）。顺带发现 ComfyUI 节点「5090」`192.168.66.161:8188` 连接失败，与本次部署无关，待查。
- **8101 活着**：health 200；无 token 访问导出接口正确 401。
- **token 找回**：`/tmp/tks_ext_video_token` 已被清，但本机可公钥免密登华为云 `root@124.71.104.207`，token 仍在 `/root/tksea-test/tksea.env`（`tks_***jA3M`，与尾号吻合）。部署时可云端管道直灌 4090，不落地明文。
- **代码就绪**：`video-pipeline` 本地 `feature/select-integration` 干净，`38c497a` + `d686374` 两提交都在；Gitea 推送可随时补。
- **迁移自动**：`db.py _migrate()` 会在启动时自动加 `sku`/`source`/`external_run_id` 列和唯一索引，线上无需手工跑 SQL。

当天真正卡点（重要修正）：

- 本机 WiFi 在 `192.168.8.x` 网段，且 XQNetwork（mihomo TUN）的策略路由（`ip rule` 9002：本机流量全查 table 2022）把**所有出网流量吸进 TUN**，包括私网 `192.168.66.x`。代理出口到不了内网 → TCP 探测「端口开」全是 TUN 本地假握手，真连 SSH 就超时。
- 绑定物理网卡源 IP（`curl --interface 192.168.8.55`）绕不过策略路由；`SO_MARK` 绕行需要 root。**核对方法：`ip route get 192.168.66.84` 若显示 `via 198.18.x.x dev XQNetwork` 即被劫持，先退 XQNetwork 再测。**
- FRP 服务器 `47.93.236.30:22` 是真 sshd（OpenSSH 9.6 Ubuntu），但无凭据记录；且 FRP 隧道由 4090 侧 frpc 定义，服务端加不了 SSH 映射。Tailscale 本机未登录，办公室机器不在 tailnet。

下次部署前的快速判据（按序）：

1. `ip route get 192.168.66.84` → 必须走 `wlp*`/物理网卡，不能是 XQNetwork；
2. `curl -m 5 http://192.168.66.84:8900/api/health` → 有 JSON 才算真通；
3. 通了以后按第六节流程一次会话做完（公钥 → 备份 db → 灌 token → `./deploy.sh`）。

长期建议（下次人在办公室时顺手做掉）：4090 装 authorized_keys 公钥后，再给它配 Tailscale 或 FRP 的 SSH 映射，此后远程部署不再依赖人在 66 网段。

## 八、2026-10-18 晚：部署成功（问题已解决）

**一句话结论：卡了几天的部署问题解决了。导入功能已经装上 4090 并重启生效，机器侧能查的全部验证通过，只剩最后一步要人登录网页点一下导入按钮做验收。**

### 怎么通的（大白话）

1. **换了台人在办公室的电脑**（s-macbook-pro，本身就在 66 网段 `192.168.66.248`）。回头看清了两天的失败各有各的原因，都不是服务器坏：
   - 10-15：SSH 短时间重试太密，被 fail2ban 一类防护封了源 IP；
   - 10-18 白天：Legion 在外网，XQNetwork 代理 TUN 把发往 `192.168.66.x` 的流量全吞了，根本出不去办公室内网。
   - 这次这台机器直连内网，第一发 `curl 8900/api/health` 就回了 JSON。
2. **代码没丢，从华为云备份拿回来了**。之前担心「两个提交孤本在某台笔记本上」解除：开发机当时已把整个分支打包成 git bundle 备份在华为云 `/root/backups/video-pipeline-20261018/`（bundle + 两个 patch）。bundle 拉回本地 `git fetch` 一下，`38c497a`（导入功能主体）+ `d686374`（X-Api-Token 修复）原样恢复，**提交号都没变**。
3. **分支上了 4090**：本机把分支推到 4090 的裸仓库（`~/git/video_pipeline.git`，git daemon 旁的 ssh 通道），4090 工作区 `~/video_pipeline` checkout 到 `feature/select-integration`（它的基线正好是 4090 当时的 main，干净切换）。
4. **部署三步一次做完**（就是第六节的流程）：装公钥免密 + 备份数据库（`ecom.db.bak-20261018-select`）→ 写入 `select_api_base`/`select_api_token` → `./deploy.sh` 输出 `health ok | poller alive: True`。
