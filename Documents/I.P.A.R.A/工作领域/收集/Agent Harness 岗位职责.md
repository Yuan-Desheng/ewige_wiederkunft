## 一、工牌精简版（直接印在工牌背面）

> [!abstract] Agent Harness
> **定位**：以 Agent 为生产力的全栈交付者 + Agent 工作流基建维护者。
>
> 1. **单人全栈交付**——一人跑完需求、原型、设计、开发、测试、交付全流程，对项目结果负总责。
> 2. **Agent 驱动研发**——用 `工作流-原型/设计/开发/测试/部署` 完成产出，人审方向与风险，AI 保产出与完整度。
> 3. **原型收敛需求**——把需求博弈前移到原型阶段，客户书面冻结后再开发。
> 4. **Harness 工程**——沉淀 Skills / Subagent / MCP / Prompt & Context 方案，把个人跑通的用法变成公司资产。
> 5. **质量与红线**——过四个评审 gate，守测试硬门槛与脱敏红线，不盲信 AI 产出。

*（工牌空间不足时，取前三条 + 第 4 条。）*

## 二、岗位定位

| 项 | 说明 |
|---|---|
| **岗位名称** | Agent Harness |
| **一句话定位** | 用 Agent 把「想法 → 原型 → 设计 → 代码 → 交付」全链路跑完的人，同时负责让这条链路本身越跑越快 |
| **在流程中的角色** | 《项目立项与研发流程规范》中的 **项目负责人（Owner）**，不区分工种 |
| **产能来源** | 缺的工种由 **AI 工作流 + 项目 AI 机器人** 补齐；本人是「指挥 + 把关 + 决策」 |
| **双重身份** | ① 对外：项目交付第一责任人；② 对内：Agent 工作流 / Harness 的建设与维护者 |

> [!important] 与「传统开发岗」的关键区别
> 考核的不是「写了多少代码」，而是 **交付了多少可验收的系统** + **让下一次交付快了多少**。写代码是手段，Harness 是复利。

## 三、核心职责

### 3.1 项目交付职责（按六阶段展开）

| 阶段 | 本岗位要做的事 | 主用工作流 | 交付物 |
|---|---|---|---|
| **立项** | 判定立项门槛与项目级别，提交立项材料；建知识库 + 项目 AI 机器人 + 代码仓库 | — | 立项申请、可行性与投入估算 |
| **① 需求** | 直接对接客户，把原始需求结构化为需求文档；写清范围边界与验收口径 | `工作流-原型`（需求提取）/ `工作流-规格` | 需求文档、功能清单 → **评审①** |
| **② 原型** | 产出高保真、可交互、可访问、基于真实数据的原型；带客户上手迭代；timebox 内收敛并取得**书面冻结** | `工作流-原型` | 原型真链接、specs、冻结确认 → **评审②** |
| **③ 设计** | 反推技术设计：架构 / 数据流 / ER / 接口契约 / 安全 / 运维 / 非功能性；高风险点先做 spike | `工作流-设计` | 设计说明书 → **评审③** |
| **④ 开发** | 在 AI 辅助下落地可运行实现（后端 + 接线前端 + 数据库 + 一键启动）；**在无直接经验的语言/框架领域也要保质量** | `工作流-开发` | 可运行 MVP / 参考实现 |
| **⑤ 测试** | 生成并真实执行单元 + 接口测试，达测试硬门槛，缺陷归类整改 | `工作流-测试` | 测试报告、缺陷修复记录 |
| **⑥ 交付** | 打可移植部署包并净室演练；跑 `/security-review`；备齐部署/验收/操作手册，与运维交接 | `工作流-部署` | 部署包、交付清单 → **评审④** |
| **收尾** | 汇总项目指标、1 周内 retro，改进项回写规范 | — | 度量数据、复盘记录 |

### 3.2 Harness 工程职责（本岗位的差异化价值）

> [!tip] 一句话：把「我这次是怎么让 Agent 干成的」变成「下次谁都能这么干」
- **Skill / Workflow 沉淀**：把重复跑通的 Agent 用法固化成可复用的 Skill、Slash 命令、工作流（如 `工作流-原型/设计/开发/测试/部署`），并维护其版本与文档。
- **Prompt / Context Engineering**：设计并持续调优系统提示、上下文组织方式、记忆与知识库喂养策略；对 KV Cache、上下文预算、长会话压缩有实际优化动作。
- **Harness 设计**：设计 Agent Loop、工具集（Tool Use）、Subagent / Multi-Agent 分工、审批与安全边界（危险操作二次确认）、失败重试与验证闭环。
- **MCP / 工具接入**：把公司内外系统（知识库、飞书、部署环境、第三方 API）接成 Agent 可调用的工具。
- **项目 AI 机器人**：为每个项目搭建并保鲜项目机器人（挂载知识库、每阶段结束同步），作为 Owner 的「第二大脑」，并满足「可接管」验收标准。
- **模型与产品选型**：跟进主流 Agent 产品与模型能力变化，做横向评测，给出团队选型建议。

### 3.3 质量与风控职责

- **过闸不放行**：四个评审 gate（需求 / 交互 / 架构 / 交付）材料准备与整改闭环；交付评审必须显式通过。
- **不盲信 AI 产出**：逐阶段执行「AI 产出人工必检清单」——需求有无臆造、原型有无客户没要的自动补全、架构是否过度设计、代码关键逻辑与边界条件、部署脚本有无明文凭据。
- **守脱敏红线**：公开仓库零明文（合同、客户 PII、服务器/数据库凭据、密钥、Token 一律 `【已脱敏】`）。
- **变更管理**：原型冻结后的需求变更一律走变更单，评估工期/成本/架构影响，大变更触发报价与工期调整，杜绝无限免费返工。
- **巴士因子对冲**：关键决策与决策对口人双人知晓；知识库做到「另一个人能接手」。

## 四、任职能力要求

### 4.1 硬性能力

| 维度 | 要求 |
|---|---|
| **Vibe Coding** | 能用 AI Agent 工具完成真实软件开发；在**没有直接经验的语言 / 技术 / 框架**下也能产出有质量保证的代码；软件开发领域学习能力极强 |
| **UI/UX 素养** | 具备设计品味，能在 AI 辅助下独立完成产品原型图、UI 设计等产品设计工作（对应阶段②原型的「高保真」硬要求） |
| **Agent 产品重度使用** | 是 Agent 产品的高强度用户，熟悉各种形态；深度使用过 Claude Code、Cowork、Codex、Cursor、OpenCode、GitHub Copilot、Manus、OpenClaw、Hermes 等代码类与通用类 Agent 产品，并已融入自己的工作和生活 |
| **模型判断力** | 对模型行为**有品味、有判断力**；对开发者体验（DX）与用户体验（UX）有强感知 |
| **技术原理** | 理解 LLM 与 Agent 基本机制：LLM API、KV Cache、Agent Loop、Tool Use、Reasoning、Planning、Skills、MCP、Memory、Subagent、Multi-Agent |
| **三大课题第一手实践** | **Prompt Engineering / Context Engineering / Harness Engineering** ——不是看过，是自己调过、踩过坑、有产出 |

### 4.2 软性要求

- 对 Agent 与 Agent Harness 的开发有**极大热情**（这是岗位的前提，不是加分项）。
- 单人负责制下的自驱与闭环能力：从客户对接到线上交付，无人催也能推到底。
- 客户沟通与预期管理能力：原型阶段能带着客户收敛，而不是被客户牵着无限改。
- 诚实的工程态度：AI 说「跑通了」不算跑通，以真实验证结果为准。

## 五、考核指标（对齐规范 §九 度量）

| 类别 | 指标 |
|---|---|
| **交付** | 各阶段实际耗时 vs 估算；按期交付率 |
| **质量** | 评审打回次数（按 gate）；测试通过率；交付后客户缺陷数；安全高危项数（应为 0） |
| **需求收敛** | 原型迭代轮数 / 是否超 timebox；**冻结后变更数**；返工率 |
| **Harness 复利** | 沉淀并被他人复用的 Skill / 工作流数量；同类项目第二次交付的提速比例 |
| **知识资产** | 项目知识库「可接管」自检通过；机器人保鲜（每阶段结束已同步） |

---

## 六、红线（违反即打回 / 安全事故）

> [!danger] 与《项目立项与研发流程规范》§十 一致
> - 原型未经客户书面冻结 + 评审② 未过，不得进设计/开发。
> - 架构未过评审③，不得写业务代码。
> - 测试未达硬门槛，不得进交付。
> - 交付前未跑 `/security-review` 或有未处理高危项，不得交付。
> - 公开仓库零明文凭据；凭据不入聊天、不入文档。
> - **AI 产出未经人工必检直接交付** —— 本岗位特有红线：Agent 是工具，责任在人。
