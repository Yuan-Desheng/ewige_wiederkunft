**• 实时运行监控** ○ 遥测数据展示：实时显示功率、电压、电流、频率、温度、SOC等运行参数 ○ 遥信数据展示：实时显示设备开关状态、告警状态、工作模式等状态信息 ○ 数据刷新频率：支持分钟级（1分钟/5分钟/15分钟）数据刷新 ○ 历史数据存储：自动存储运行数据，支持按时间范围查询与导出

**• 用户行为数据分析** ○ 用电习惯统计：统计用户日/周/月用电模式，生成用电特征曲线 ○ 峰谷时段用电分析：分析峰平谷时段用电占比，识别可调节时段 ○ 行为模式识别：基于历史数据识别用户用能行为模式（如工作日/休息日模式） ○ 异常用电告警：识别用电异常行为（如超负荷用电、非正常时段用电）并触发告警

#### 1.3 资源画像中心

**• 画像标签管理** ○ 自动标签生成：基于设备运行数据自动计算调节潜力、碳排敏感度、响应速度等标签 ○ 标签分类体系：建立多维度标签体系（调节特性标签、碳排特性标签、经济性标签） ○ 手动标签调整：支持人工修正标签值，记录修正原因与时间 ○ 标签权重设置：设置各标签在调度决策中的权重系数

**• 分钟级画像更新** ○ 动态画像刷新：分钟级自动更新资源画像数据 ○ 画像变更记录：记录画像标签的历史变更轨迹 ○ 画像对比分析：对比不同时间点画像变化，识别资源特性演变趋势

**• 碳效评估报告** ○ 碳排量计算：计算设备/集群的碳排放量、碳减排量 ○ 碳效指标统计：统计碳强度（单位电量碳排放）、碳效比等指标 ○ 碳效评估报告：生成日/周/月碳效评估报告，支持导出PDF/Excel ○ 碳排趋势分析：分析碳排放趋势，预测未来碳排水平

### 1-1-多元数据感知总览

这份 UI 原型图展示了一个**“融合大模型智能体的虚拟电厂仿真系统”**中的**“多元数据感知总览”**页面。作为一个典型的 B 端能源管理系统，它的结构非常清晰，符合高效办公的设计逻辑。

以下是对该原型的核心功能模块识别、业务逻辑说明及组件化拆分建议：

---

## 1. 核心功能模块识别

|**模块名称**|**视觉表现与组成**|**核心作用**|
|---|---|---|
|**顶部导航 (Global Header)**|包含系统标题、六大主业务入口（资源画像、负荷预测等）、通知及个人中心。|提供系统级的全局切换和状态提醒。|
|**侧边功能菜单 (Sidebar)**|垂直菜单栏，包含数据采集管理、监控、关联数据管控等子模块。|针对“多元数据感知”这一特定业务领域的深度功能导航。|
|**KPI 指标看板 (KPI Cards)**|四个并列的卡片，展示总负荷、环境温度、碳排因子、电价。|实时汇总核心业务指标，通过颜色（红/绿）和趋势图标示意波动。|
|**负荷趋势可视化 (Data Viz)**|中心区域的折线/面积图。|展示时间维度下的数据波动，辅助用户进行趋势预测。|
|**资源状态列表 (Status List)**|底部网格布局，展示不同类型设备（空调、储能、充电桩等）的实时状态。|颗粒化监控末端设备，提供在线/离线/故障的快速识别。|

---

## 2. 业务功能承载说明

根据页面的文案和布局，该页面承载了以下核心业务逻辑：

- **多维数据监控**：不仅监控电力数据（总负荷、电价），还引入了环境数据（温度）和环保指标（碳排因子），体现了“多元”感知的深度。
    
- **分级预警机制**：在“资源状态”模块中，通过不同颜色的标签（如：绿色-在线、红色-离线、橙色-故障）实现异常的即时反馈，帮助运维人员快速定位问题设备。
    
- **云边协同逻辑**：从侧边栏的“数据采集管理”和“关联数据管控”可以看出，系统涉及从物理设备（边缘侧）到仿真系统（云端）的数据打通与同步。

- **信息变更**：通过**新增编辑采集源**对已有配置进行在线更新。

    - **用户行为数据视图**：若该采集源涉及终端交互，可进一步查看用户对设备的调控指令记录。

整个“多元数据感知”模块以 **[多元数据感知总览]** 为核心枢纽，向下分化为两条平行的核心业务流：

### 二、 核心参数传递逻辑分析（重点）

在 UI/UX 设计转化为前端开发时，明确“页面之间传了什么参数”是重中之重。以下是该模块中四个最核心的参数传递场景说明：

#### 场景 1：列表页到表单页的“身份传递” (List to Form)

- **路径**：`数据采集管理` 点击“编辑” $\rightarrow$ 跳转 `新增编辑采集源`。
    
- **参数传递逻辑**：
    
    - 当点击“新增”时，参数为空，系统渲染空白表单。
        
    - 当点击某一行数据的“编辑”时，列表页会将该行的 **`源 ID (Source_ID)`** 作为 URL 参数（例如 `?id=1024&mode=edit`）传递给编辑页。
        
    - **目标页展示**：编辑页接收到 `Source_ID` 后，自动向后端拉取该采集源的所有历史配置数据（如已填写的名称、URL、协议类型等），并反显在表单中。
        

#### 场景 2：表单配置到联调反馈的“状态传递” (Form to Feedback)

- **路径**：`新增编辑采集源` 点击“测试连接” $\rightarrow$ `测试连接结果`。
    
- **参数传递逻辑**：
    
    - 用户在表单填写的临时参数（**`URL`**、**`Token`**、**`Protocol`**）被打包作为 Payload 传递给后端进行模拟握手。
        
    - 后端返回握手结果包（包含 **`Status_Code`** 状态码、**`Latency`** 延迟毫秒数、**`Error_Message`** 错误信息）。
        
    - **目标页展示**：结果页根据返回的 `Status_Code` 决定渲染绿色成功 UI 还是红色失败 UI；并将 `Latency` 的值（如 43ms）映射为进度条的长度。
        

#### 场景 3：宏观看板到微观视图的“上下文下钻” (Dashboard Drill-down)

- **路径**：`数据采集监控` $\rightarrow$ `运行数据视图` / `用户行为数据视图`。
    
- **参数传递逻辑**：
    
    - 在监控总览中，如果用户在“过滤器”中选择了特定条件（如：**`Region=杭州市西湖区`**，**`Device_Type=5G基站`**），当用户点击下钻进入明细视图时，这些过滤参数必须通过全局状态 (State) 或 URL 参数被携带过去。
        
    - **目标页展示**：`运行数据视图` 初始化时会读取这些参数，其顶部的筛选框会自动锁定为“杭州市西湖区”和“5G基站”，底部的表格仅渲染符合这些条件的明细数据。
        

#### 场景 4：组件间状态联动的“权重传递” (State Synchronization)

- **路径**：`关联数据源配置` $\rightarrow$ `关联数据管控`。
    
- **参数传递逻辑**：
    
    - 表单中的 **`Priority`** (优先级滑动条，取值 0-100) 和 **`Status`** (启用/禁用开关) 保存后写入数据库。
        
    - **目标页展示**：管控列表页读取这些参数，将 `Priority` 渲染为横向的可视化进度条长度，并将排序逻辑设定为按此参数从高到低排列。

### 二、 核心参数传递逻辑分析（重点）

在 UI/UX 设计转化为前端开发时，明确“页面之间传了什么参数”是重中之重。以下是该模块中四个最核心的参数传递场景说明：

#### 场景 1：列表页到表单页的“身份传递” (List to Form)

- **路径**：`数据采集管理` 点击“编辑” $\rightarrow$ 跳转 `新增编辑采集源`。
    
- **参数传递逻辑**：
    
    - 当点击“新增”时，参数为空，系统渲染空白表单。
        
    - 当点击某一行数据的“编辑”时，列表页会将该行的 **`源 ID (Source_ID)`** 作为 URL 参数（例如 `?id=1024&mode=edit`）传递给编辑页。
        
    - **目标页展示**：编辑页接收到 `Source_ID` 后，自动向后端拉取该采集源的所有历史配置数据（如已填写的名称、URL、协议类型等），并反显在表单中。
        

#### 场景 2：表单配置到联调反馈的“状态传递” (Form to Feedback)

- **路径**：`新增编辑采集源` 点击“测试连接” $\rightarrow$ `测试连接结果`。
    
- **参数传递逻辑**：
    
    - 用户在表单填写的临时参数（**`URL`**、**`Token`**、**`Protocol`**）被打包作为 Payload 传递给后端进行模拟握手。
        
    - 后端返回握手结果包（包含 **`Status_Code`** 状态码、**`Latency`** 延迟毫秒数、**`Error_Message`** 错误信息）。
        
    - **目标页展示**：结果页根据返回的 `Status_Code` 决定渲染绿色成功 UI 还是红色失败 UI；并将 `Latency` 的值（如 43ms）映射为进度条的长度。
        

#### 场景 3：宏观看板到微观视图的“上下文下钻” (Dashboard Drill-down)

- **路径**：`数据采集监控` $\rightarrow$ `运行数据视图` / `用户行为数据视图`。
    
- **参数传递逻辑**：
    
    - 在监控总览中，如果用户在“过滤器”中选择了特定条件（如：**`Region=杭州市西湖区`**，**`Device_Type=5G基站`**），当用户点击下钻进入明细视图时，这些过滤参数必须通过全局状态 (State) 或 URL 参数被携带过去。
        
    - **目标页展示**：`运行数据视图` 初始化时会读取这些参数，其顶部的筛选框会自动锁定为“杭州市西湖区”和“5G基站”，底部的表格仅渲染符合这些条件的明细数据。
        

#### 场景 4：组件间状态联动的“权重传递” (State Synchronization)

- **路径**：`关联数据源配置` $\rightarrow$ `关联数据管控`。
    
- **参数传递逻辑**：
    
    - 表单中的 **`Priority`** (优先级滑动条，取值 0-100) 和 **`Status`** (启用/禁用开关) 保存后写入数据库。
        
    - **目标页展示**：管控列表页读取这些参数，将 `Priority` 渲染为横向的可视化进度条长度，并将排序逻辑设定为按此参数从高到低排列。
