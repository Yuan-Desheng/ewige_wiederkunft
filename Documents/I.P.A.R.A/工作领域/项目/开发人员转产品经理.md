# 培养计划（2026-07-14）

## 为什么是现在

过去二十年，一个开发的稀缺性写在"怎么做"上：会写代码、能搭架构、能把系统跑起来。VibeCoding 把这一整段的边际成本压到接近零——写代码、改 UI、写测试、跑部署，AI 一次能给二十个方案，人只需产出并把关。行业已经在为这件事重新定价：单人创立的初创从 2019 年的 23.7% 升到 2025 年中的 36.3%；Base44 一个人四个月做出平台、上线一个月做到约 150 万美元月收入、被 Wix 以 8000 万美元收购，他用 AI agent 顶掉了 PM、QA、开发三种角色。Karpathy 造出 "vibe coding" 这个词一年后就说它过时了，专业交付进入 "agentic engineering"——"English bootstraps；engineering sustains"，自然语言能起步，但要靠人把关的工程判断才撑得住产品。

**结论只有一句：当"把东西做出来"变廉价，"做对的东西"就成了唯一的稀缺。** 价值和话语权结构性地前移到 PM 前端——做什么、为谁做、凭什么值钱。这不是我们要不要转型的选择题，是市场已经替我们做完的判断题。

而我们团队恰好站在这个推力的正前方。**单人全栈负责制的 Owner，已经是一个准 PM。** 一个人从对接客户、拆需求、做原型、设计、开发、测试到交付全包，他缺的早已不是执行力——AI 在干体力活——缺的是 PM 的判断维度。我们的《项目立项与研发流程规范》(四评审 gate + 原型驱动需求收敛)其实已经把这条结构性推力焊成了组织制度，只是还没有人把它命名为"PM 训练"。

> 这份计划要做的，就是把这个"结构性推力"变成一套**刻意练习体系**：不新增流程、不搞考证运动，让每个 Owner 手上的每个项目，都变成一次可观测、可评估、可晋级的 PM 能力练兵。

一句话把魂立住：**VibeCoding 没让产品经理消失，它让"会写文档的 PM"和"能交付的 PM"分道扬镳。我们要练的，是让每个开发跨到"能交付"那一侧的判断力。**

## 一、能力模型：开发者要补的到底是什么

先做一个贯穿全篇的二分——这是整套计划的地基：

| | 🤖 A 类：AI 已能替干的「how / 执行」 | 🧠 B 类：开发者必须自己长出来的「why-what / 判断」 |
|---|---|---|
| 内容 | 编码、测试、部署、原型产出、PRD 成文、竞品罗列初稿、数据清洗、报表 | 真需求发现、价值定义、方向选择、优先级取舍、商业化、成功指标定义 |
| 特征 | 有明确输入→输出、正确性可验证、能被"产出+把关"覆盖 | 无标准答案、需承担后果、依赖对人和市场的现场判断 |
| 怎么对待 | **不设课，只设标准**——考核"能否高质量指挥 AI 产出并把关" | **刻意练习的主战场**——用真实项目做训练场 |

我们的能力模型只练 B 类，分三层，每层给**可观测的行为标准**（而不是"具备 XX 意识"这种测不出来的话）。

### L1｜能用工作流独立交付客户项目（会听懂、会说清、会交付）

对应 NPDP 的市场研究基础 + 新产品流程前端 + 文档；对应苏杰的"需求奋斗史"前三关。

**可观测行为标准：**
- [ ] 能独立跑完六阶段，用 AI 工作流交付一个真实客户项目，四评审 gate 全部一次或两次内通过
- [ ] 能做一次结构化客户访谈，并在需求文档里区分"客户说的要"和"客户真正要解决的问题"
- [ ] 写的需求文档过需求评审 gate：有目标用户、场景、要解决的问题、验收口径、**以及"不做什么"**（范围界定）
- [ ] 带**能点的原型**去和客户对一遍，在原型阶段暴露分歧，而不是开发完才发现做错
- [ ] 对 AI 补全的字段/功能会做"客户没要的删或标注待确认"——抵抗 feature creep
- [ ] 会指挥 AI 出发散初稿（头脑风暴/SCAMPER/SWOT/竞品罗列），并能筛

**L1 的分水岭**：从"接需求的开发"变成"对交付结果负总责的 Owner"。他还在响应给定需求，但已经能高质量地把它闭合、交付。

### L2｜会做需求收敛与多维评审（能定义价值、能做取舍）

对应 NPDP 的组合管理 + 市场研究进阶 + 工具度量；对应苏杰的 Y 模型 + KANO + 真伪判断。

**可观测行为标准：**
- [ ] 能用 **Y 模型**当着评审的面拆一个需求：用户说的（右上）→ 他的目标/场景（右下）→ 人性/价值（中心）→ 反推真正该做的功能（左）
- [ ] 会用**真伪三连问**判需求：谁在什么场景遇到这问题？多普遍多痛？不解决他有没有 workaround？——三个都答不实就敢标"伪需求"
- [ ] 能写一句**价值主张**：为谁、解决什么、凭什么比现状好、凭什么值钱
- [ ] 会用 **KANO + 性价比排序**做减法，并能**有理由地对客户/自己说不**（"这个先不做，因为它是无差异型"）
- [ ] 能为一个产品**定义成功指标**：选 1 个北极星 + 1-2 个护栏指标，并解释为何是它
- [ ] 交付后能做一次**产品复盘**：这交付物当成产品该怎么收费、单价怎么定、有没有可复用模块
- [ ] 冻结后变更能收住：走变更单 + 影响评估 + 大变更触发报价/工期调整

**L2 的分水岭**：从"高质量交付给定需求"变成"能判断需求真假、能定义价值、能做取舍"。他不再照单全收，开始对"做什么"有主张。

### L3｜能主动做市场/竞品/商业化，从 0 定义产品（能选方向、能扛结果）

对应 NPDP 的新产品开发战略 + 组合战略 + 上市后管理；对应苏杰的"战略"与"产品的 Y 模型放大版"。

**可观测行为标准：**
- [ ] 能主动做**市场/竞品/行业洞察**：给一个方向做 PEST + TAM-SAM-SOM + 3-5 个对标竞品差异分析，判断"值不值得进"
- [ ] 能算一个产品的**商业化基本盘**：成本结构、定价逻辑、变现路径、单位经济模型入门——不是被动的"改需求加钱"，是主动定价
- [ ] 能从 0 完成**真需求发现→价值定义→商业化闭环**，不依赖别人给需求（能发起，不只是响应）
- [ ] 面对多个机会能做**组合取舍**：说清先做哪个、砍哪个、赌哪个方向、放弃了什么，并承担结果
- [ ] 能把一个项目沉淀成**可复用的标准产品/模块**（从"接项目"升级到"攒产品"）
- [ ] 能做**交付后的数据闭环**：拿到真实使用数据、判断留存/转化、决定要不要迭代/加码/收手
- [ ] 复盘失败能区分"方向错了"还是"执行错了"，沉淀成团队可复用的判断力

**L3 的分水岭**：从"响应者"变成"发起者"。他能自己定义要做什么、为谁做、凭什么值钱，并为商业结果负责。这就是"独当一面"。

> **一条贯穿的红线**：三层都要求"能指挥 AI 完成全部 A 类执行，把自己的时间越来越多地投在 B 类判断上"。L1 大概 5 成时间在判断，L3 应该 9 成时间在判断。

## 二、分阶段成长路线图（4 个季度阶段）

设计原则：**每阶段都寄生在真实项目上，学的东西下一周就能用在手上的项目里。** 不脱产、不搞集训。

### 阶段一（Q1）｜打地基：从"实现思维"到"问题思维"

| 维度 | 内容 |
|---|---|
| **目标** | 完成第一次思维转变：动手前先问"为谁解决什么、凭什么值钱"，而不是先想架构 |
| **学什么** | 苏杰"一个需求的奋斗史"(采集→分析→筛选→PRD→迭代)；Y 模型；用户研究四象限(定性/定量 × 说/做) |
| **练什么** | 在当前项目上：每个需求动手前强制写一句"谁+在什么场景+遇到什么问题+不做会怎样"；做一次真实客户访谈；用 Y 模型拆 3 个需求 |
| **产出** | 每个项目一张"需求奋斗史"复盘；一份过了需求评审的 PRD（含"不做什么"） |
| **里程碑** | 独立交付 1 个客户项目，需求 gate 两次内通过 → **达 L1** |

### 阶段二（Q2）｜练收敛：从"技术最优"到"用户/商业最优"

| 维度 | 内容 |
|---|---|
| **目标** | 学会做减法、学会说不、接受 MVP 不完美 |
| **学什么** | KANO 模型；性价比排序；马斯洛需求层次判真伪；NPDP 门径管理的"模糊前端"；"需求精度决定 AI 速度天花板" |
| **练什么** | 每个需求评审用 KANO 分类；每个版本明确"本版只打一个核心场景，砍了 X 因为它是无差异型"；原型阶段观察客户"做"什么而非只听"说"什么 |
| **产出** | 每个项目一份"砍需求清单 + 理由"；一句可量化的价值主张 |
| **里程碑** | 交付评审能说清"这版砍了什么、为什么"；冻结后变更数明显下降 → **向 L2 过渡** |

### 阶段三（Q3）｜建闭环：从"交付即完成"到"交付是起点"

| 维度 | 内容 |
|---|---|
| **目标** | 建立数据闭环与商业化意识 |
| **学什么** | 北极星指标 + 护栏指标；AARRR/留存转化基础；单位经济模型入门；定价逻辑；NPDP 上市后管理 |
| **练什么** | 为交付的产品定 1-2 个"上市后"指标（哪怕只是"客户实际用了没"）；交付后做一次产品复盘（该怎么收费、有无可复用模块） |
| **产出** | 每个项目一份"产品/商业复盘"；至少沉淀 1 个可复用模块/模板 |
| **里程碑** | 能独立完成"需求辨别→价值定义→成功指标"全链，主导四评审 → **达 L2** |

### 阶段四（Q4）｜够前端：从"响应需求"到"发起产品"

| 维度 | 内容 |
|---|---|
| **目标** | 迈向 L3：能主动做市场/竞品/商业化，尝试从 0 定义一个产品 |
| **学什么** | PEST/波特五力；TAM-SAM-SOM；产品组合管理；NPDP 新产品开发战略（创新战略咬死经营战略） |
| **练什么** | 给手上项目补一页"机会与战略"；参加季度产品组合复盘做取舍；尝试主动向客户提一个未被要求但被采纳的改进；（进阶）提一个内部孵化/标准产品的机会画布 |
| **产出** | 1 份完整的机会画布（含市场规模+竞品+定价）；1 个主动提案被采纳 |
| **里程碑** | 能独立发起并论证一个方向，对商业结果负责 → **迈入 L3** |

## 三、以项目为练兵场（最重要）：把 PM 练习焊到六阶段 + 四评审上

**核心原则：不新增流程，只在既有 gate 上加维度、在既有阶段上加动作。** 让 PM 能力练习"寄生"在已经要做的事情里，零额外仪式感。这是整套计划最重要、也最不容易变成纸上谈兵的一节。

### 3.1 四评审里，每个 gate 各加一个 PM 维度

| 评审 gate | 现在卡什么 | **加挂的 PM 练习维度** | 练哪层 |
|---|---|---|---|
| **立项评审** | 该不该做、谁做、范围、定级 | **加「机会与战略」一页**：这需求背后市场多大？有无竞品/替代方案？我们凭什么能做？手上多个项目为什么先做这个？ | L3 |
| **需求评审①** | 范围清不清、验收能不能量 | **加「真需求/价值」维度**：用 Y 模型拆一遍（客户说的 vs 真正要解决的）；目标用户是谁、什么场景；这功能对客户创造什么**可量化**价值 | L2 |
| **交互评审②** | 交互流、覆盖度、客户认可 | **加「用户体验主观判断」**：抛开客户提没提，你作为 PM 认为这流程好用吗？有没有更优解你没提给客户？ | L2 |
| **交付评审④** | 实现、质量、安全 | **加「商业化 checkpoint」**：本项目实际利润率？变更收住了吗？有无可复用为标准产品/模板的部分？ | L2→L3 |

### 3.2 阶段两端，新增两个轻量动作

**动作 A — 立项前置：5 分钟「机会画布」（挂在阶段①之前）**
> 每个项目开工填一张极简画布（做成 Templater 模板）：目标用户 / 要解决的真问题 / 现有替代方案 / 我们的差异化 / 大致商业价值。**不追求准，追求逼 Owner 主动想"为谁做、凭什么"。** 补上我们最缺的"模糊前端"那一段。

**动作 B — 交付后延伸：一次「产品复盘」（扩展现有 retro）**
> 现在的 retro 只复盘流程。加一段"产品/商业复盘"：
> - 这交付物当成一个**产品**，它的用户是谁、该怎么收费、单价怎么定？
> - 交付后能不能拿到真实使用数据？定 1-2 个"上市后"指标（哪怕是"客户实际用了没"）。
> - 有没有能抽成**标准产品/可复用模块**的东西？（从"接项目"升级到"攒产品"）

### 3.3 跨项目：季度「产品组合」复盘

> 把所有 Owner 的项目摆一起，练"组合视角"：哪些方向值得沉淀成产品线？哪些客户/行业该多接？哪些是赔本赚吆喝该放弃？成本极低（把现有 retro 数据汇总即可），却是练 L3 组合取舍最直接的场。

### 3.4 度量升级：给现有度量加「PM 类指标」

现有指标全是交付效率类（耗时/打回/返工）。加几个牵引 PM 能力的：

| 新增指标 | 牵引什么能力 |
|---|---|
| **需求辨别命中率**：需求评审中被识别为"伪需求/客户没真正要"的条数 | 真需求发现（L2） |
| **主动提案数**：Owner 主动提的、客户没要求但被采纳的改进数 | 产品判断力（L2→L3） |
| **项目毛利率 / 变更增收额** | 商业化（L3） |
| **可复用沉淀数**：本项目产出的可复用模块/模板数 | 从项目到产品（L3） |

> 加了这一层，现有规范就从"交付流水线"变成"**交付流水线 + PM 养成轨道**"，几乎零新增流程负担。**四评审 gate 从"质量关卡"升级为"能力评估锚点"**——需求 gate 考 L1，交互/架构 gate 考 L2，交付 gate + 商业结果考 L3。

## 四、配套学习机制

都贴合我们已有的 AI 工作流和知识库，不搞额外脱产培训。

### 4.1 双主线读书会（每两周一次，一次 1 小时）

- **主线一《人人都是产品经理》(苏杰)**：按六大主题（用户/需求/项目/团队/战略/修养）拆读。**规则：每次分享必须带一个自己项目的真实案例**——"我这个项目里的这个需求，用 Y 模型/KANO 该怎么判"，禁止空谈概念。
- **主线二 NPDP 精讲（B 站）**：只挑权重最高、最缺的三块讲——战略管理、门径管理、市场研究/需求定义。**不以考证为目的**（见风险节），只取框架。

### 4.2 项目分享会（每月一次）

每个 Owner 讲一个项目，但**不讲技术实现**（那是 A 类），只讲三件事：这需求真假我怎么判的、我砍了什么为什么、如果当产品卖该怎么定价。

### 4.3 影子跟岗（Shadowing）

L1 的开发跟一个 L2/L3 的 Owner 跑一次完整的客户对接 + 需求评审，重点观察"他怎么在客户'说'的背后挖到真需求""他怎么有理由地说不"。**客户关系不能外包**，这一课只能靠贴身看。

### 4.4 AI 陪练：用项目 AI 机器人当 PM 教练

这是最贴合我们基础设施、也最能规模化的一环。用现有的可接管知识库 + AI 机器人，配三套 PM 教练 prompt：

- **需求苏格拉底**：Owner 输入一个需求，AI 扮演"苏杰"用真伪三连问 + Y 模型追问到底，逼出真需求。
- **KANO 分诊台**：输入一版功能清单，AI 帮做 KANO 分类初稿 + 性价比排序，Owner 来终审（练 A 类指挥 + B 类把关）。
- **红队定价官**：输入一个交付物，AI 扮演客户/CFO 反问"凭什么值这个价、成本多少、竞品怎么收费"，练商业化。

> 注意分工：AI 陪练练的是"如何指挥 AI 高质量产出并把关"（A 类）+ 用 AI 逼自己想清楚（B 类的脚手架）。**最终判断必须人做**——领域深度、担责决策不能外包给机器人。

## 五、评估与晋级：怎么判断一个开发到了 L1/L2/L3

**原则：用客观信号，不用主观印象。** 所有信号都来自我们已经在记录的项目数据和评审记录，不额外造表。晋级由季度产品组合复盘会集体评议 + 数据佐证。

| 层级 | 客观晋级信号（需同时满足多数） |
|---|---|
| **达 L1** | ① 独立交付 ≥1 个客户项目；② 需求评审平均两次内通过；③ 其 PRD 含明确"不做什么"；④ 能指挥 AI 完成全部执行、无需他人代写代码 |
| **达 L2** | ① 需求辨别命中率 >0（真的判出过伪需求并被评审认可）；② 冻结后变更数低于团队均值；③ 交付评审能说清"砍了什么、为什么"；④ 至少 1 次产品复盘含"该怎么收费"的实质分析；⑤ 沉淀 ≥1 个可复用模块 |
| **达 L3** | ① 提交过 ≥1 份含市场规模+竞品+定价的机会画布；② 有 ≥1 个主动提案被客户采纳；③ 负责项目毛利率/变更增收可量化且健康；④ 参与季度组合复盘并做过一次"砍哪个/赌哪个"的取舍决策；⑤ 能对一次失败区分"方向错"还是"执行错" |

**几个特别提醒的信号解读：**
- **评审打回率**：不是越低越好。L1 打回率高很正常；但如果一个人**从不被打回却也从不主动提案**，多半是"照单全收的交付型"，卡在 L1 上不来——这比打回率高更危险。
- **复盘质量 > 复盘数量**：看他复盘时能不能区分"方向错/执行错"。只会写"下次多沟通"的是没入门。
- **独立拿下需求的能力**：L3 最硬的信号——他能不能不等别人喂需求，自己发现一个机会并论证。这是"响应者→发起者"的唯一试金石。

## 六、落地 Checklist + 风险

### 落地 Checklist（按优先级，ROI 从高到低）

**最小落地（先做这两样，改动最小、补最痛的缺口）：**
- [ ] 需求评审①加"真需求/价值维度"（Y 模型拆一遍）
- [ ] 交付后加一段"产品复盘"（该怎么收费 + 有无可复用模块）

**模板化：**
- [ ] 把"机会画布"和"产品复盘"做成 Templater 模板，Owner 填空即用
- [ ] 配好三套 AI 陪练 prompt（需求苏格拉底 / KANO 分诊台 / 红队定价官）接进项目机器人

**写回规范：**
- [ ] 把"PM 维度"正式补进规范的评审节和复盘节，作为 0714 版迭代（符合"流程靠复盘自迭代"的机制）
- [ ] 度量表加 4 个 PM 类指标（需求辨别命中率 / 主动提案数 / 毛利率 / 可复用沉淀数）

**机制：**
- [ ] 排期双主线读书会 + 月度项目分享会 + 影子跟岗配对
- [ ] 季度产品组合复盘会，兼做晋级评议

### 风险与规避（每一条都对着我们容易犯的错）

| 风险 | 表现 | 规避 |
|---|---|---|
| **变成又一个考证运动** | 大家忙着背 NPDP 考点、刷题，不落到项目 | NPDP/苏杰**只取框架不考证**；所有分享必须带自己项目的真实案例 |
| **耽误交付** | 加了一堆 PM 动作，项目反而变慢 | 练习**寄生在既有 gate/阶段**里，不新增流程；机会画布只要 5 分钟；A 类不设课 |
| **纸上谈兵** | 会写价值主张，但落不到真实客户和数据 | 晋级信号全部要求**真实项目数据/真实客户采纳**，不认 PPT |
| **单人负责制下没人踩刹车** | Owner 既是油门又是刹车，功能越堆越多 | 交互/交付评审强制问"砍了什么"；KANO 分诊做减法；把"有理由地说不"当成可观测行为标准 |
| **用技术品味替代产品品味** | 追求代码优雅/可配置，用户根本不需要 | 判断标准从"代码好不好"换成"用户更爽了吗/更赚钱了吗" |
| **AI 陪练代替了人的判断** | 把定价/需求判断整个甩给机器人 | 明确分工：AI 出初稿+当红队，**最终判断人做、人担责** |
| **一刀切拔苗助长** | 逼 L1 的人去做 L3 的商业化 | 严格按层级走，里程碑达成才推下一阶段；允许不同 Owner 处在不同层 |

> **收口一句**：这套计划不增加一条新流程，只是把我们已经在做的"交付流水线"重读成一条"PM 养成轨道"。Vibe coding 把"怎么做"交给了 AI，我们就把省下来的人的时间，全部押在"做什么、为谁做、凭什么值钱"上。
