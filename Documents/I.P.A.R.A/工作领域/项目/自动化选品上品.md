## 一、现状工作流拆解（基于真实操作 + 官方帮助站）

> 来源：源文件 [[自动化选品上品（原始需求）（目前可行方案）]] 的操作截图 + 布丁猫官方帮助站 `help.bdmozon.com` + 八爪鱼私享应用。

### 1.1 完整链路

```text
① 前台准备(布丁猫插件): OZON前台切【俄语/人民币/收货地址莫斯科】
        │
② 选品(布丁猫插件): 浏览OZON, 插件显示销量框, 找爆款竞品
        │
③ 采集+上品(布丁猫「快速上传/采集上货」= 接口上传, 走OZON Seller API):
        复制竞品SKU → 编辑属性(去品牌/改图/货号/变体) → 打乱图 → ×2.3调价
        → ×0.5最低价 → 打水印(防踢跟卖) → 5分钟后加库存10 → 选店铺 → 开始导入
        │  （批量≤200, 推荐每次≤5; 必须先切俄语否则报品名错误）
        │
④ 导出SKU表: 复制sku → 新建工作表移到最前 → 粘贴 → 保存
        │
⑤ 货源验证(八爪鱼「陆空联运/陆运」私享应用):
        读SKU表 → 逐个用商品图去【1688拍立淘图搜】(air.1688.com/.../pc-image-search)
        → 有同款货源? ──有──→ 上架  ；  ──无──→ 不上架
```

> ⚠️ **0714 澄清**：⑤ 这一步是**源文件截图里观察到的操作**。但用户后来上传的 `SKU_AutoFilter`（标称"陆空+陆运版"）**经逆向证实并不是这个工具**——它不联网、跟 1688 无关（见 §1.5）。**⑤ 的 1688 匹配逻辑至今未拿到实现**，自研不依赖逆向它，改走 §3.4 的 OpenCLI 路径。

### 1.5 SKU_AutoFilter 逆向结论（0714，`资料/SKU_AutoFilter_portable_陆空+陆运版_20260509`）

> ⚠️ **最重要的一条：这个工具跟 1688 / 图搜 / 采集毫无关系**，此前「八爪鱼 = 1688 货源验证 gate」的推断**对这个包不成立**。

**决定性证据**：全包 grep `1688` / `alibaba` / `selenium` / `拍立淘` / `ozon.ru` **命中数全为 0**；PyInstaller 的 648 个模块里 `requests`/`urllib3`/`selenium`/`pandas` **全是 0**；应用代码只 import `argparse/calendar/csv/math/re/sys/datetime/pathlib/typing`。

**它的真身**：一个**纯离线的 Excel 筛选器 + 物流费测算器**，且输出的 `更多自动化工具` sheet 里硬编码着一段广告——

```text
工具名称：OZON大麦家 | 功能：自动上架 / 自动匹配1688货源 / 自动测算物流价格 / 自动计算亏损调整上架倍数 | 微信：fanwang0303
```

→ **SKU_AutoFilter 是「OZON大麦家」的免费引流工具（lead magnet）。真正的 1688 匹配能力在那个产品里，本包拿不到一行相关代码。**

**输入/输出**：递归扫目录下所有 xlsx/xls/csv（**只读第 1 个 sheet**）→ 合并 → 7 条筛选 → SKU 去重 → 输出 `符合条件SKU_时间戳.xlsx`（7 张 sheet：筛选结果 / 筛选结果(陆运) / 筛选明细含来源 / 处理汇总 / 已扫描文件清单 / 未处理文件 / 更多自动化工具）。

**7 条硬筛选规则**（⚠️ 不是 README 写的 9 条，以逆向为准）：

| # | 条件 | 常量 |
|---|---|---|
| 1 | 品牌 == `без бренда`（无品牌） | `BRAND_TARGET` |
| 2 | 国家 == `中国` | `COUNTRY_TARGET` |
| 3 | 月销量 ≥ 2（None 不通过） | `MIN_MONTHLY_SALES=2` |
| 4 | 月销售变化 > 0（严格） | `MIN_SALES_CHANGE=0.0` |
| 5 | 创建时间 ≥ cutoff（UTC 回溯 6 自然月） | `MONTHS_LOOKBACK=6` |
| 6 | 卖家数量 ≤ 49 | `MAX_SELLERS=49` |
| 7 | 变体数量 0 ≤ n ≤ 6 | `MAX_VARIANTS_INCLUSIVE=6` |

> ⚠️ **「评分 ≥ 4.6」是死代码**：全二进制搜不到 `4.6`，`parse_rating` 函数定义了但 **0 处调用**。评分仍是必填列、仍透传输出，但**不参与过滤**。

**陆空 vs 陆运不是两个版本**，是同一个 exe 在同一循环里算的两张 sheet，**差别只在 `per_kg` 单价**（陆空 36.4/26.0/23.92，陆运 **17.68**/26.0/23.92；陆空 6 条费率规则、陆运 5 条）。

```text
算法（已复刻验证）：
wkg = round(weight_g/1000, 3); l,w,h = mm/10
候选 = [round(base + per_kg*wkg, 2) for r in 费率规则 if 匹配(r)]
运费 = min(候选)        # 无匹配 → None
匹配条件 = 单边≤max_l/w/h 且 三边和≤sum_max 且 weight∈[w_min,w_max] 且 卢布价∈[value_min,value_max]
（只用实重，无体积重）

利润 = round(人民币价格/1.5  - 运费, 2)   # 1.5 倍加价率下的毛利
保本 = round(人民币价格/1.25 - 运费, 2)   # 1.25 倍下的余额
```

**自研怎么复刻**：**零硬依赖**（不登录、不联网、无授权/时间锁）。整个工具就是一个纯函数：43 列 DataFrame → 7 条布尔筛选 → 两张查表计费。**≈200 行 Python，半天 TDD 写完**，直接内建为平台一个环节（§3.5 commit #5），**别做成"导出 xlsx 再跑 exe"**。费率表抄成 YAML 常量即可（费率会变要可配，但别为此做插件框架）。

> **别拿它论证形态**：它单机 exe + 双击 bat + 手工丢 xlsx，是"没有后端"的妥协，不是设计选择——它本地化只因为它是个发微信的引流小工具。
> **未能确认**：费率表的货代来源与生效日期（仅从目录名 `20260509` 推测 2026-05 前后，**需向货代核实时效**）；`/1.5`、`/1.25` 是否还隐含 OZON 佣金/汇率（代码无注释）。

## 二、需求分析

### 2.1 业务模型

OZON（俄罗斯跨境）多店精铺 + 国内供货：**OZON找爆款竞品 → 采集SKU → 1688反向找同款货源+比价 → 翻译/改价/打水印 → 批量上品到自己OZON店 → 库存/订单管理**。

### 2.2 四大痛点（自研要解决的目标）

1. **成本高 / 被卡免费额** —— 布丁猫、八爪鱼都是付费 SaaS，限量、数据在别人手里 → 要完全自托管。
2. **1688 找同款 + 比价不够智能** —— 图搜验证 + 利润测算要更自动、更准。
3. **选品数据不准 / 不全** —— OZON 无官方竞品销量，要自建可信的"卖得好不好"数据。
4. **上品效率 / 批量能力差** —— 采集→翻译→改价→多店上传要真正批量、稳定。

### 2.3 关键事实（可行性）

- ✅ **OZON 官方 Seller API 可用**（`Client-Id`+`Api-Key`，你已生成密钥）→ 上品/改价/库存/订单全走官方 API。布丁猫「接口上传」证明此路可行。
- ⚠️ **OZON 有反爬**（~~DDoS-Guard~~ → **实为 OZON 自研 FAB / abt-challenge**，0715 实测证实，见 §四.1）→ 买家端采集用**真实 Chrome 登录态**最稳。
- ⚠️ **1688 官方图搜 API（拍立淘）需企业认证**（营业执照）→ 见 §3.4 三路径。
- 💡 **P0 零翻译**（0714 修正）：「必须先切俄语否则报品名错误」说明布丁猫**直接抄前台俄语标题原样上传**——它没翻译，它是复制。我们的输入（Excel「商品名称」列）本来就是俄语，**翻译推迟到 P1+**（仅在需要改写标题时才用）。

## 三、方案设计（架构 B：本地优先）—— 2026-07-14 修正版

> 🔄 **原「架构 A：浏览器插件 + Web 后台(阿里云 ECS, FastAPI+PostgreSQL+Celery) + 官方 API」已推翻。** 修正依据：四条线调查（逆向 SKU_AutoFilter / 调研 OpenCLI+BrowserOS / 形态重审 / 后端功能与选型）。

### 3.1 为什么翻案（决定性事实）

**整条链路里最需要「常驻服务器」的 S4 定时回采，恰恰是最不能放服务器上的。**

| 功能 | 需要真实登录态？ | 能跑 ECS 吗 |
|---|---|---|
| S1 上品（Seller API） | ❌ 只需 Client-Id/Api-Key | ✅ 能，但**没必要** |
| S2 OZON 采集 | ✅ 必须（FAB/abt-challenge） | ❌ **不能** |
| S3 1688 图搜（前台） | ✅ 必须 | ❌ **不能** |
| S4 定时回采 | ✅ 必须 | ❌ **不能** |
| **S5 水印图托管** | — | ✅ **必须**（OZON 服务器要来拉 URL） |
| S7 订单同步 | ❌ | ✅ 能 |

原方案「上云换 7x24」的理由被反爬直接击穿：IDC IP 在 FAB 眼里是高危段，服务器**能常开但爬不到**（要配俄罗斯住宅代理 ≈ **$5–15/GB**，商品图流量下不是小钱，且照样被挑战）；而**能爬的浏览器在本地**。

> **所以「上云换 7x24」实际是：花代理费 + 提高封号率，去换一台本地常开机器（Mac mini / 旧笔记本，一次性几百块）就能解决的问题。这交易是亏的。**

**本地形态的代价（诚实说清）**：① Mac 合盖不跑定时任务（launchd 只在唤醒后补跑）；② 换电脑要迁数据；③ **多人协作会立刻崩**——第 ③ 条是**唯一真实的升级触发器**。

> ⚠️ **未核实**：OZON Seller API 是否支持 Api-Key 绑定 IP 白名单。若支持，固定公网 IP 才有价值，是唯一可能翻盘上云的因素。据了解 OZON 无此机制，**但未核实，别按它做决策**。

| 形态 | Web 后台 @ ECS | **本地 Python 包 + `aps` CLI** | 见 §3.1；P2+ 可加 `127.0.0.1` 页面，非 Electron |
| 存储 | PostgreSQL | **SQLite(WAL)** + stdlib `sqlite3` + 手写 SQL + 幂等 migration runner | 用户=1人 → **写并发=1**（SQLite 唯一软肋在此不存在）；年增 <1GB。**更硬的反证：2万 SKU 每天回采一次、即便 1 req/s 也要 5.5 小时，瓶颈是采集速率与封号风险，不是数据库——你被封之前根本喂不饱一个 PG** |
| 后端框架 | FastAPI | **无（P0–P1）** | P0 是**批处理**不是请求-响应。套 FastAPI = 给一个只有你自己按回车的程序写 HTTP 路由 + 再写客户端调它自己。第一个真实理由在 P2（浏览器不能写 SQLite）→ 那时加 30 行 localhost 端点，**且先确认 OpenCLI Bridge 是否已够** |
| 任务 | Celery / APScheduler | **DB 表当队列 + launchd 调 CLI** | 所有「长任务」都是**跨进程/跨天的持久化状态**（延迟5分钟加库存、跨3天审核轮询）→ 任何内存队列都是错的答案。**DB 已经是队列，再加一个 = 两份状态 = 一致性 bug** |
| 浏览器 | 自研 MV3 插件 | **复用 OpenCLI Browser Bridge** | 已跑通，且自带 1688 adapter（§3.4） |
| 密钥 | 服务器 `.env` 600 | **`keyring`（Keychain/DPAPI）** | 见 §3.5 |
| 图床 | (未提) | **阿里云 OSS** | P1 起必需——`product/import` 传图 URL，**OZON 服务器会来拉** |
| 图像/测试 | Pillow / pytest | **Pillow / pytest + `respx` 录制回放** | 反爬/限额下不能对着真 API 跑测试 |
| 部署 | ECS | **`uv sync` + `git pull`** | 真给运营用再 PyInstaller |

**净效果：砍掉 PostgreSQL、Celery/Redis、Vue/React、ECS 部署、FastAPI —— 5 个组件、5 份运维。**

> 其它两个反直觉结论：
> 🔴 **P0 的大头不是调 API，是「类目必填属性补全」**——OZON 每类目一套必填 `attributes`，字典型属性还要查字典值 id（布丁猫的「AI属性优化」就在干这个）。**低估它 P0 就卡死。**
> 💡 **P0 零翻译**——「必须先切俄语否则报品名错误」说明布丁猫**直接抄前台俄语标题原样上传**，它没翻译，它是复制。我们的输入（Excel「商品名称」列）本来就是俄语。

### 3.4 1688 路径：**B 打底 + C 增强 + A 并行申请**（互补，不是三选一）

**重大发现：OpenCLI 自带官方 1688 adapter**（`clis/1688/`：`search/item/assets/download/store/auth`，**每个都配 `.test.js`**）。`search` 输出字段几乎就是选品链路要的：`offer_id/title/price_min/price_max/moq_value/location/badges/sales_text/`**`return_rate_text`（退货率——第三方 API 给不了的硬指标）**。

**但官方文档明确排除**：*No image search (拍立淘)* → **关键词搜开箱即用，图搜要自己拼**：

```text
本地图片 →① browser upload → 阿里CDN → imageId
        →② search.1688.com/youyuan/index.htm?tab=imageSearch&imageId=<id>
             └─ 页面内 XHR: imageSearchOfferResultViewService → 同款货源 JSON
映射到 OpenCLI：open → upload → wait selector → network --filter imageSearchOfferResultViewService -f json → close
```

**这条比通用爬虫稳的根本原因**：走真实登录 Chrome，1688 的 `_m_h5_tk` token / 滑块 / 设备指纹**天然成立，不用逆向签名算法**（自研爬 1688 最大的成本项，直接绕过）；`network` 拿的是页面自己发的请求的响应，**不伪造任何请求**。

| 维度 | **A. 官方开放平台** | **B. 第三方聚合 API** | **C. OpenCLI 真实浏览器** |
|---|---|---|---|
| 准入 | ❌ 企业实名+营业执照，审 1–3 天 | ✅ 注册即用 | ✅ **零门槛，已跑通** |
| 图片入口 | 官方规范 | onebound 支持**文件直传**；⚠️ **TMAPI 只吃阿里系图片 URL → OZON 图喂不进去** | ✅ 本地文件直传 |
| 稳定性 | 🟢 最高 | 🟡 中 | 🟠 改版即挂 |
| 风控 | 🟢 无 | 🟢 转嫁服务商 | 🟠 **有**，重则封 1688 账号 |
| 成本 | 免费额度+阶梯 | 按量；⚠️ **失败也计费** | 电费+维护工时 |
| 数据丰度 | 官方字段 | 中等 | 🟢 **最全**（退货率/徽章/起订量） |

- **主力 B**：图搜是高频、大批量、幂等动作——API 主场，也是浏览器自动化最易触发风控的动作。**用 onebound 而非 TMAPI**。⚠️ 接入前**小额充值实测「无结果也计费」的真实扣费比例**——选品图搜命中率注定不高，这**直接决定单位成本，可能是隐藏成本炸弹**。
- **增强 C**：拿到 `offer_id` 后的低频高价值动作交给 OpenCLI（`item/assets/download/store`）。**`assets`+`download` 直接对接下游「打水印/上品」，是 C 不可替代之处。**
- **并行 A**：有 PlantLove 营业执照，审核仅 1–3 天，**零成本纯期权**——批下来换掉 B，批不下来无损失。⚠️ `secret` 严禁下发客户端。

**BrowserOS 排除**：开源 Chromium 分叉 + 内置 LLM Agent（对标 ChatGPT Atlas/Comet）。能驱动，但**不该用**——定位是交互式 AI 浏览而非批量采集；每次采集过 LLM 推理，**选品是高频结构化任务，用 LLM 解析 1688 卡片是大炮打蚊子：慢、贵、且同样输入可能给出不同字段**；对 1688 零内置支持。**选品链路要的是确定性，不是智能性——OpenCLI 的 adapter 是写死的解析器，这正是优点。**

> 🔴 **1688 风控红线**：**不要用指纹浏览器 + 住宅代理伪装。** Facebook 那套方法论**这条必须反过来**——那边你伪装陌生人，这边你是**真实采购商，实名+采购历史本身就是最好的通行证**；北京实名企业号突然从美国住宅 IP 登录**反而是风控信号**。要做的是**行为节流**：请求间隔 2–5s **随机**（定频比高频更像机器人）、单账号图搜 <100 次/小时、2–3 个**真实企业子账号**轮换、`1688 item` 比 search 更敏感须**串行别并发**。

### 3.6 密钥方案：**这恰恰是反对上云的最强论据**

自研动机之一就是「不想把 Client-Id/Api-Key 交给布丁猫」。这个逻辑一路推下去**指向本地**：

| 存放位置 | 攻击面 | 后果 |
|---|---|---|
| 布丁猫（第三方 SaaS） | 第三方全员 + 其数据库 | 第三方对你所有店铺有改价/下架/读订单 PII 全权限。**已被拒绝** |
| ~~ECS `.env` mode 600~~ | SSH + Web 端口 + 整条依赖链 + **快照/备份带走明文** | 一次 RCE = 全部店铺沦陷。**mode 600 只挡非 root，是安慰剂——此方案撤回** |
| **本地 OS 凭据库** ✅ | 你自己的电脑 | 单机受损，且**密钥从不经过网络** |

**做法**：`keyring`（macOS Keychain / Windows Credential Manager），key 形如 `autopickshelf / ozon:<shop>`；**DB 只存引用不存明文**；**禁止 `.env`**（明文躺盘、易被 `git add`、被备份同步走）；录入走 CLI 一次性交互（`getpass`，不落 history 不落盘）；令牌类型**按需勾选别全选**（上品/改价/库存/订单分店分权）；日志/异常**强制脱敏**，Api-Key 永不进 stdout。

> **上云后仍成立的原则**：**服务端永远不持有密钥**——本地 agent 轮询服务端任务队列 → 取任务 → **用本地密钥在本地调 OZON API** → 只回传结果。服务端被打穿也拿不到任何店铺权限（CI runner / Tailscale 模型）。

### 3.7 演进：什么时候才上云

**形态一（现在，本地）→ 形态三（混合）**，且**是演进出来的，不是一开始就付的**。

**上云触发条件（写死，满足任意 2 条再动手）：**
1. 使用人数 > 3，且需并发读写同一份 SKU 库/选品结论；
2. 确实需要真 7x24 且团队没有任何常开机器（**这条大概率一台 Mac mini 就消解了**）；
3. 需要给不装软件的人（老板/外部）看数据看板。

**届时上云的只有「数据仓 + 定时调度 + 看板」。密钥和浏览器采集永远留在本地。**

### 3.8 成本对比

- **现状**：布丁猫月费 + 八爪鱼月费 + 被限量，数据受制于人。
- **自研（修正后）**：一次性开发 + **阿里云 OSS 按量（几乎可忽略）** + 1688 图搜按量。**ECS/PG/Redis 全省了**；边际成本趋近零、数据与密钥全自主。

## 四、2026-07-15 重大修正（形态终审 + 插件逆向 + GitHub 调研）

### 4.1 OZON 反爬真相：不是 DDoS-Guard，是自研 FAB（0715 实测一手证据）

```text
curl https://www.ozon.ru/
  → HTTP/2 307 | server: nginx | location: ?__rr=1
    set-cookie: __Secure-ETC=...
    ❌ 无 __ddg1/__ddg2   ❌ 无 server: ddos-guard        → 确认不是 DDoS-Guard

curl https://docs.ozon.ru/api/seller/swagger.json
  → HTTP 403 {"incidentId": "fab_chlg_20260715075920_01KXJCK5T7BEJ3TSRXK3HD7KSP",
              "challengeURL": "https://docs.ozon.ru/challenge.html?challenge=..."}
```

`fab_chlg` = **FAB challenge**（OZON 自研 antibot），只加载 `cdn2.ozone.ru/s3/abt-challenge/captcha_v10.js`。**连文档站 `docs.ozon.ru` 都拦**（从中国 IP）。

> **影响**：所有「打 DDoS-Guard」的方案（JA3 库 / `ddos-guard-bypass` / FlareSolverr）**都打错靶子**。防护梯队：**IP 信誉 > cookie/JS 挑战 > 浏览器指纹 > 行为**。

### 4.2 🔴 架构红线：采集 IP 与 Seller API 的 IP 必须物理隔离

OZON 官方《Seller API: как избежать блокировок》明确要求：**可信运营商静态 IP**、**禁止 VPN**、云服务商**必须独享 IP**、**排除对 OZON 站点在「允许域名」外的自动化 parsing**；收到带事件号（`fab_...`）的报错 = **你的 IP 上被记录了 bad activity**。

而 0715 实测拿到的事件号是 `fab_chlg_...`，**与官方文档里 Seller API 封禁的事件号前缀/格式完全同构**，且 FAB 覆盖 `*.ozon.ru`（前台 + 文档站均拦）。

> 【推断，高置信】**买家前台的 abt-challenge 与 api-seller 的封禁是同一套 FAB 在按 IP 声誉打分。**

**真实因果链（vc.ru 有实名案例走完全程）：**
```text
爬买家前台 ──┐
             ├──→ IP 被 FAB 标记 bad activity
中国机房IP ──┘                │
                              ▼
            同一 IP 上的 api-seller 调用被切断
                              ▼
            库存/价格停止同步 → 卖出不存在的商品 → 吃平台处罚
```

> **🔴 不可妥协：采集 IP 与 Seller API IP 永不复用。** 两者需求天然冲突——API 要**固定、可追踪、高声誉**的独享静态 IP；采集要**可轮换、可烧**的 IP。**一套网络方案满足不了两边。**
> ⚠️ **待确认**：现在调 OZON API 是否走 VPN？**若是，这本身即明文违规**，可能正是「莫名其妙被封 API」的真实原因。正解是俄区合规的独享静态 IP，**不是 VPN**。

### 4.3 🔴 安全事故：布丁猫在自动上传你卖家后台的完整 cookie

插件源码 `src/background.js`（**证据，非推测**）：

```js
const e = await O.cookies.getAll({url:"https://seller.ozon.ru/"});
await dn({method:"post", url:"/public/token/add", data:{client_id: sc_company_id, cookies: r}});
```

**不是「复制登录凭证」按钮——是 background 自动把整个 cookie jar 上传到布丁猫服务器。** 加上 manifest 的 `host_permissions:["*://*/*"]` + `cookies` 权限 + `<all_urls>` content script，它技术上能读**任意站点**的 cookie。

| 存放位置 | 第三方实际拿到 |
|---|---|
| 我原以为 | Client-Id/Api-Key（= 官方 API 权限，受令牌勾选约束） |
| **实际** | **+ 卖家后台完整会话 cookie** = 官方 API 给不了的一切（内部接口/活动/归档/财务），**且不受 API Key 权限约束** |

> **这把自研动机从「省钱」抬到了「安全事故止损」。** 建议：seller.ozon.ru **登出所有会话**使已上传 cookie 失效 + 评估是否继续挂该插件。

### 4.4 🔴 内嵌浏览器拿不到销量——痛点②不会因换形态被解决

插件源码 `src/content_scripts/index.js`：
```js
async function fT(e){ const t = await Jt.post("/plugin/data/get_data", {sku:e});
  return t.status===204 ? Ya(Zf) : rT(t.data.result) }   // Zf = "暂无销量的商品"
```
插件把 SKU 发给 **`bdmozon.com/prod-api` 换数据**，204 = 未收录（locale 里 `notYetIncluded=暂未收录` 印证收录制）。那些字段（曝光次数/转化率/详情页访问量/退货率）**全是 OZON 卖家后台 Analytics 口径，公开前台没有**。

> **布丁猫的护城河是它的数据库，不是插件。** 内嵌完整 Chromium、完美过 FAB，打开商品页——**页面上没有月销量这个数**。

**（顺带）`analysis.js` 不是采集 hook**——它命中 `/premium\/status/` 就伪造 200 响应，`dataPoints` 是 `Math.floor(Math.random()*1e3)`。**纯客户端付费墙欺骗，且数字是随机数。不要复刻，一行都不要。**（另：`_locales` 里全是 `asinInput/averageBSR` → **这插件是个亚马逊插件改的皮**，locale 不能当功能清单用。）

### 4.5 形态终审：BrowserOS / Electron / Tauri 内嵌 —— 全否

| 形态 | 判决 | 决定性理由 |
|---|---|---|
| **Tauri 2 内嵌爬** | ❌ | **不打包 Chromium**（macOS=WKWebView/Safari、Win=WebView2、Linux=WebKitGTK）；**macOS 系统级无法拦截 https**（WebKit #138169，十年未修；`tauri-cdp` 标注 Windows only）→ 你在 Mac 上开发，类 CDP 能力直接归零 |
| **Electron** | ❌ | 能干活，但**它是 Chromium 不是 Chrome**：UA 带 `Electron/`、**缺 UA Client Hints**（改 UA 字符串补不上）、`window.chrome` 不完整；**反侦察生态零上游支持**。付 150MB + 自维护补丁，换来的能力**真实 Chrome 本来就有** |
| **BrowserOS** | ❌ | **`CHROMIUM_VERSION`=148**（Stable 已 150，落后 2 个大版本）；grep UA/指纹改动**零命中**=无任何反侦察工程；`is_chrome_branded=false` → **UA 自称 `Chrome/148` 但 Sec-CH-UA 自称 `"Chromium";v="148"`**（一行 JS 就能测出）；agent 走**未修补的 CDP**；装机量 ~2.5 万 = 指纹全网稀有；不支持 headless、定时任务 10min 超时、**AGPL-3.0** |
| **CEF/cefpython** | ❌ | 停在 **Chromium 66（2018）**，页面本身就渲染不出来 |
| **D. 桌面壳 + 驱动真实 Chrome** | ✅ **推荐** | Tauri 只渲染**你自己的 UI**（从不访问 ozon/1688，故引擎无关）；后台 patchright + `channel="chrome"` + 独立 `user_data_dir` → **指纹 = 本机真实 Chrome**；一店一 profile = 白送多账号隔离；**Python CLI 零重写** |

**一条硬证据**：Google 自 2021 起**全面封禁一切 CEF/Electron 嵌入式浏览器登录**，与 headless 无关、与真人无关 → **识别「非 stock Chrome 的 Chromium」在工程上是已解决问题**。

> **「BrowserOS 当日常浏览器养熟」不成立**：**个人一致性**（同设备长期稳定）能养；**人群基数稀有性**（全网多少人是这个指纹）**完全不能**。阿里 umid 看后者。**你不是混进人群，你是给自己焊了个终身车牌。**
>
> **🔴 壳最后再写** —— P0 全部功能走官方 API，**一行浏览器代码都不需要**。

### 4.6 封号风险的真相：引擎选型根本不是重点

| 通道 | 用谁的身份 | 最坏后果 | 封号风险 |
|---|---|---|---|
| **OZON Seller API** | 平台发给你的 Key | 429 限流 | **≈0**（但受 §4.2 IP 红线牵连） |
| **OZON 买家前台** | **匿名，无账号** | 403 + 验证码 | **无号可封 → 封 IP**（换 IP/等一天） |
| **1688 前台** | **你的实名企业采购号** | 滑块 → 限制 → 封 | 🔴 **本项目唯一真实封号点** |

> **引擎决定你「烦不烦」（弹不弹验证码）；IP + 速率 + 行为 + 账号权重决定你「死不死」（封不封号）。这两个几乎独立。**
> **常见误区：把「不弹验证码」当成「安全」的代理指标。**
> 换引擎的边际收益在「真实 Chrome」之后迅速衰减：直连HTTP→真Chrome 是巨大跃迁；真Chrome→扩展 是小幅改善；**真Chrome→BrowserOS 是负收益**。**过了「不比 stock Chrome 差」这个下限，80% 精力该花在 IP / 节流 / 行为上。**

**防封规程（1688，可直接写进代码）**：请求间隔 **2–5s 随机**（定频比高频更像机器人）；单账号图搜 **<100 次/小时**；**串行不并发**（`1688 item` 比 search 更敏感）；2–3 个**真实企业子账号**轮换；**检测到滑块就 throw 让人工处理，绝不绕过**。
🔴 **绝不用指纹浏览器 + 住宅代理伪装 1688**——你是真实采购商，**实名+采购历史本身就是通行证**；北京实名企业号突然从美国住宅 IP 登录**反而是风控信号**。

**顺带澄清**：`_m_h5_tk` **是接口鉴权，不是风控**——`sign = md5(f"{token}&{ts}&{app_key}&{data}")`，纯 MD5、hashlib 五行。**用真实浏览器跑，签名是浏览器自己算的，你没伪造任何东西**。「签名伪造被封号」这个担心在「驱动真实浏览器」形态下**不成立**。

### 4.8 GitHub 调研结论：没有轮子值得 fork

**这个领域客观没有开源**（不是没搜到）：多平台统一 SDK 全网最高 9★；开源 ERP 全是「搭自己商城」方向，无 marketplace-seller 侧刊登工具。

**值得抄的两段**：① **OZON 官方 swagger**（380 paths / 2.7MB）→ codegen 那 7 个端点的模型 + 契约测试（⚠️ 从官方源抓，别 vendor 无 license 的仓库）；② **OpenCLI `clis/1688/shared.js`**（Apache-2.0）的风控检测 `CAPTCHA_URL_MARKER='/_____tmd_____/punish'` + `isCaptchaState`——**哲学是「检测到滑块就 throw，从不绕过」**。

**明确否决**：`nodriver`/`zendriver` = **AGPL-3.0**（将来套 Tauri 分发有真实法务风险）；`DrissionPage` = NOASSERTION；`undetected-chromedriver` 死一年；`litequeue`/`huey`/`sqlite-migrate` = 为省 30–40 行引无人维护的依赖。

**反向证实已定架构**：star 最高的 OZON 爬虫（102★）靠「9 次硬撞」过反爬 → patchright+真Chrome 严格优于它；独立 `user_data_dir` 是 **Chrome 136+ 的硬性前置条件**（不再允许 CDP 驱动默认 profile）；某 AGPL 铺货工具作者自陈「**UI 上品最后一个按钮，所有自动化都突破不了**」→ **反证 P0 走官方 API 是对的**。

## 五、采集路线裁决（0715）：插件 vs patchright vs OpenCLI

> 起因：准备开新对话做开发时提出两条路线——**①完全仿照布丁猫、用浏览器插件爬** vs **②OpenCLI/Playwright 等**。裁决结果：**①否决，②降级到 P2，且限定为 patchright**。

### 5.1 决定性发现：43 列里 **14 列物理上爬不到**

| 类别 | 列 |
|---|---|
| ✅ **可自采（24 列）** | SKU / 商品名称 / 卢布价格(→人民币/美元可算) / 评分 / 评论数 / 变体数量 / 商品链接 / 品牌 / 商品类目 / 跟卖最低价 / 卖家数量 / 国家 / 卖家名称 / 卖家链接 / 配送方式 / 页面上的价格 / 主图 / 长宽高重量(⚠️卖家填才有) 等 |
| ❌ **绝对拿不到（14 列）** | **月销量、月销售额、月销售变化、退货率、搜索转化率、购物车转化率、曝光次数、曝光转化率、详情页访问量、搜索结果的详情页访问量、促销收入占比、推广费用占比**、开启促销天数、开启模板活动天数 |
| ⚠️ 只能估算 | 后台价格(估) / 跟卖最低价后台价（布丁猫也是**估算模型不是数据**）、创建时间（前台无，只能拿最早评论日期兜底） |

> **能采的 24 列回答「这个品长什么样、卖多少钱、几个人在卖」＝ 验证阶段信息。**
> **缺的 14 列回答「有没有需求、涨还是跌、退货吃不吃利润、流量转不转化、广告要花多少」＝ 发现阶段信息。**
> **而选品工具的价值 90% 在发现阶段。**

**两条铁证：**
1. **Apify Ozon Scraper PRO**（商业级、99.9% 成功率）的输出 schema **明确声明不返回**销量/营收/转化/曝光 → **别人把爬虫做到极致也拿不到。这是天花板，不是水平线。**
2. **竞品销量是「数据网络效应」产品**：必然靠**全体用户授权数据聚成 panel 再外推**（正好解释布丁猫的 204「暂未收录」；也解释某友商「与官方 API 对接 100% 精准」却要用户自己填 API key 的矛盾——Seller API 只能读自己店）。**自研工具用户数=1、panel 规模=1 → 数学上走不通，与代码质量无关。**

**月销量能否间接推算？** 业内用 **Δstock 库存差分**，但 **OZON 前台不公开库存件数**（与 WB 的根本差异，WB 的 JSON 直接给 `qty`）→ 只能靠**加购探针**（逐 SKU 逐日的**写操作**，最像机器人）〔中置信推断〕；评论增量法误差 5–20 倍且滞后 7–30 天。**放弃。**

### 5.2 三形态对比：数据边界由平台决定，不由形态决定

| 维度 | **A 自研 MV3 插件** | **B patchright + 真Chrome** | **C OpenCLI Bridge** |
|---|---|---|---|
| **能拿到的数据** | 24/43 | **24/43（完全相同）** | **24/43（完全相同）** |
| 反爬存活率 | 最高（日常 profile+真人噪声） | 高（冷 profile 更"新"） | ≈A |
| 与 Python CLI 集成 | 🔴 **最难，且会改掉架构** | ✅ **零成本**（同进程，结果直接进同一 SQLite 事务） | 🟡 subprocess 解析 stdout |
| 无人值守批量 | 🔴 **不行**（MV3 SW **30 秒空闲即杀**、单事件 >5min 即杀、关浏览器即死） | ✅ 可排队/限速/cron | 🟡 需 Chrome 常驻 |
| 多店隔离 | 🔴 与日常 profile 绑死 | ✅ 一店一 `user_data_dir` | 🔴 绑死单 profile |
| 分发 | 🔴 爬 OZON 违反 ToS → **上不了 Web Store** | ✅ 复用系统 Chrome | ✅ 已装 |
| 调试 | 差（SW devtools 随 SW 销毁） | ✅ 断点+trace+video+HAR | 中（黑盒） |

**A（插件）否决的三个决定性理由：**
1. **插件的头号优势「复用登录态」在 OZON 场景价值归零**——**买家前台匿名可访问、不需要登录**。该优势的价值在 **1688**（图搜/企业价必须登录），不在 OZON。
2. **数据边界完全相同（24/43）**——三者都是真实 Chrome 渲染同一页面、同一个 `entrypoint-api.bx`。**差异 = 0。**
3. **架构会被迫变回布丁猫的形状**：插件把数据交给 Python 只有三条路——native messaging（要打包+固定扩展ID+装 host json）、**localhost HTTP（逼你常驻 HTTP server = 违背 §3.3「Python CLI、无 FastAPI」）**、WebSocket（同样要常驻）。**而布丁猫的形状你已经逆向过，知道它烂在哪。**

> **插件唯一不可替代的优势：「真人浏览顺带采（piggyback）」**——你人工翻竞品时页面已渲染，插件顺手落库：零额外请求、零额外 IP 风险、流量画像 100% 是真人。**但这是「顺手积累」不是「批量补采」**（受 MV3 SW 30 秒限制）。**列 P2，可砍。**

### 5.3 修正后的顺序

```text
0. 先解决 IP（不写代码）  拿到 IP#1(SellerAPI，静态独享非VPN) + IP#2(采集)  ← IP 没隔离前写的采集代码全白写
1. P0 官方 API 上品       14 task，输入=43列Excel，一行浏览器代码不写        ← 风险≈0、价值最高、不阻塞
2. 选品数据源拍板         ①外购 / ②自建回采 / ③只用自己店Analytics          ← 不阻塞 P0
3. P1 1688 采购           OpenCLI + 图搜 adapter                            ← 唯一真实封号点，慢慢来
4. P2 采集（若还需要）     patchright，先跑单 SKU 端到端                      ← 只有 24/43 且缺致命列，性价比最低
```

### 5.4 🟡 唯一可能翻盘的实验（需你亲自实测，1 小时）

`JTJag/ozon-sellers-parser` 用 Frida 逆向 OZON App，报告 **「移除认证 header 后 endpoint 依然正常响应」**，19 并发跑完 42691 个店铺页 <2 小时、零错误、未用代理——**与 0715 实测的 307+FAB 冲突**。

合理解释：**FAB 挂在 Web 入口（www.ozon.ru），API 入口（`composer-api.bx`/`entrypoint-api.bx`）策略更松**；或作者是俄罗斯 IP。

**实验**：用**中国 IP + 与 SellerAPI 物理隔离的一次性 VPS**，`httpx` 直打 `https://api.ozon.ru/composer-api.bx/page/json/v2?url=/product/<slug>/`
- 放行 → 路线2 **连 Chrome 都不需要**，纯 httpx 拿 24 列，成本骤降
- 拦 → 路线2 需 patchright + 真 Chrome，性价比进一步恶化
- **⚠️ 无论结果如何，24/43 的天花板不变、月销量拿不到不变。别信 README，必须自己复现。**

> **窄而真实的用途**：#39 最终成交价（Seller API 关掉 `marketing_price` 后拿不到）+ #24/#26 跟卖监控。只扫你关心的几十个 SKU，速率极低、风险可控。**这叫价格监控，不叫选品。**
