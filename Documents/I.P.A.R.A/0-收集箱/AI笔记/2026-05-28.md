**CLAUDE.md 是什么**
- Claude Code 在每个项目根目录下读取 `CLAUDE.md` 作为上下文指令

## 主题2：LLM Wiki（Karpathy 模式）

### 知识点

**什么是 LLM Wiki**
- 由 Andrej Karpathy 提出的知识管理模式，区别于传统 RAG
- 传统 RAG：每次查询重新检索，知识不积累
- LLM Wiki：知识编译一次、持续更新、交叉引用已就位、矛盾已标记
- 核心思想：**人负责筛选来源和方向，AI负责摘要、交叉引用、归档、维护一致性**

**三层架构**
```
Layer 1 — raw/：不可变原始资料（agent只读不写）
Layer 2 — concepts/entities/comparisons/queries/：Wiki页面（agent维护）
Layer 3 — SCHEMA.md：结构规则、标签分类、约定
```

**与鱼先生 IPARA 的映射方案**
- `raw/` → `0-收集箱/raw/`（articles, papers, transcripts）
- `concepts/` → `学习领域/资源/concepts/`
- `entities/` → `学习领域/资源/entities/`
- `comparisons/` → `学习领域/资源/comparisons/`
- `queries/` → `学习领域/资源/queries/`
- `SCHEMA.md` → vault 根目录
- `wiki-index.md` / `wiki-log.md` → `学习领域/资源/`

**关键操作流程**
1. **Orient（定位）**：每次会话开始必须先读 SCHEMA.md → index.md → log.md 最近条目
2. **Ingest（导入）**：捕获原始资料 → 讨论要点 → 检查已有页面 → 写/更新页面 → 更新导航
3. **Query（查询）**：读 index → 搜索 → 读相关页 → 综合 → 有价值的答案存入 queries/
4. **Lint（检查）**：孤立页面、断链、frontmatter 验证、过期内容、矛盾标记

**避坑要点**
- raw/ 下的文件**永远不修改**，修正写在 wiki 页面中
- 每个新页面至少要有 2 个 `[[wikilinks]]` 指向其他页面（避免孤立）
- 标签必须来自 SCHEMA.md 中定义的分类（防止标签膨胀）
- 页面超过 200 行时拆分
- 矛盾不要静默覆盖，要标记 `contested: true` 并提交用户审核

## 主题3：Obsidian 笔记 Frontmatter 批量整理

### 知识点

**YAML Frontmatter 基础**
- Obsidian 笔记头部的 `---` 界定区域，存储元数据
- 被 Dataview、Datacore、Bases View 等插件读取，用于查询和筛选
- 缺少 frontmatter 的笔记不会出现在数据库视图中

**鱼先生 vault 的 frontmatter 标准格式**
```yaml
---
createTime: YYYY-MM-DD HH:mm
笔记ID: YYYYMMDDHHmmss
multiFile:
multiMedia:
description:
笔记类型: 收集笔记 | 项目笔记 | wiki笔记 | AI整理
阐述日期:
tags:
aliases:
cssclasses:
卡片盒笔记主题:
---
```

**批量操作用到的命令**
- `sed -i 's/^笔记类型:\s*$/笔记类型: 收集笔记/'` — 批量填充空字段
- `sed -i '/^阐述日期:/a tags:'` — 在指定行后插入字段
- `grep -rl "^笔记类型:\s*$" --include="*.md" .` — 递归查找匹配的文件
- `head -20 "$f" | grep -c "^tags:"` — 检查 frontmatter 中是否存在字段

**注意事项**
- 含空格的文件名在 bash for 循环中会被拆分，需要用 `while IFS= read -r` 或 `find -print0 | xargs -0`
- `sed` 替换时 `\s` 匹配空白符，`$` 匹配行尾，`\s*$` 可以匹配字段值为空的各种情况

### 知识点

**ECharts 扩展包机制**
- ECharts 官方库不原生支持韦恩图（Venn Diagram）
- 社区扩展 `@echarts-extension/venn` 提供了直接的韦恩图支持
- 安装：`npm install echarts @echarts-extension/venn`
- 使用：在代码中引入 ECharts 后导入该扩展包，`setOption` 中将 series type 设为 `venn`

**韦恩图数据结构**
- 3个集合（A、B、C）产生7个段（ABC、AB、AC、BC、A-only、B-only、C-only）
- ECharts venn 扩展需要的数据格式与普通饼图不同，需要注意数据映射

**ECharts 文本大小不生效的排查思路**
- 检查是否被 CSS 样式覆盖（外部样式可能覆盖 ECharts 内联样式）
- 检查图表容器的 `font-size` 是否被全局 CSS 影响
- ECharts 中文本样式优先级：series.label > series.itemStyle > 全局 textStyle
- 如果使用自定义 formatter，确保返回的富文本样式正确

## 主题6：Vue 主题切换跨路由失效（vpp-simulator-frontend 项目）

> [!ai] AI整理标记
> 以下内容来自跨对话整理 — 项目：虚拟电厂仿真系统前端

### 知识点

**问题现象**
- 在负荷预测页面设置为暗色主题
- 切换到可调能力页面后，主题变为浅色
- 切回负荷预测页面又恢复暗色
- 表现为：主题切换只对当前路由页面生效

**根本原因**
- Vue 的主题状态（dark/light）存储在组件级别的状态中，而非全局状态
- 切换路由时组件重新挂载，未从全局状态读取主题配置
- 导致每个路由页面维护独立的主题状态

**解决方案**
- 将主题状态提升到全局状态管理（Pinia store 或 provide/inject）
- 在 `App.vue` 或 `layout` 组件中监听主题变化，统一设置 `document.documentElement` 的 class
- 使用 CSS 变量（`--bg-color`、`--text-color` 等）配合 `:root` 和 `.dark` 选择器实现主题切换
- 在路由切换时通过 `watch` 或导航守卫确保主题状态同步

**Vue 状态管理基础**
- `ref` / `reactive` — 组件内状态，组件卸载后丢失
- `Pinia store` — 全局状态，跨组件、跨路由共享
- `provide/inject` — 祖先→后代的状态传递，适合主题等跨层级场景
- `localStorage` — 持久化存储，页面刷新后仍保留

### 官方文档参考
- [Vue 3 响应式基础](https://cn.vuejs.org/guide/essentials/reactivity-fundamentals.html)
- [Pinia 官方文档](https://pinia.vuejs.org/zh/)

## 主题8：韦恩图样式优化与图表高度调整（vpp-simulator-frontend）

> [!ai] 今日新增内容 — 场景参与重叠分析图表从 SVG 重构为 ECharts 实现

### 知识点

**SVG viewBox 文本缩放问题**
- SVG `viewBox` 中的所有单位（包括 `font-size`）会按容器宽度比例缩放
- 例如：`viewBox="0 0 400 260"` 的 SVG 在 800px 容器中，所有尺寸放大 2 倍
- 导致 `font-size="13"` 实际渲染为 26px，文本显得巨大
- 解决方案：使用更宽的 viewBox（`500×200`）减少缩放倍数，或改用 ECharts

**ECharts graphic 组件实现韦恩图**
- `@echarts-extension/venn` 包在 npm 上**不存在**
- 使用 ECharts 自带的 `GraphicComponent` + `vue-echarts`
- 文本以固定像素渲染，不受容器缩放影响

```typescript
import { use } from 'echarts/core'
import { GraphicComponent } from 'echarts/components'
import { CanvasRenderer } from 'echarts/renderers'
import VChart from 'vue-echarts'

use([GraphicComponent, CanvasRenderer])

const option = computed(() => ({
  backgroundColor: 'transparent',
  graphic: {
    elements: [{
      type: 'group',
      left: 'center',
      top: 'middle',
      children: [
        // 圆形、文本元素
      ]
    }]
  }
}))
```

**图表高度自适应技巧**
- 固定高度：`height: 200px` → 图表显得太小
- Flex 布局：`flex: 1; min-height: 240px` → 图表填充 ChartCard 主体
- 使用 `autoresize` 属性让 ECharts 响应容器变化

**韦恩图几何计算**
- 圆心排列成等边三角形，圆心距 `d = avgR × 0.9`
- 圆面积 ∝ 场景总用户数，半径 `r ∝ √count`
- 标签位置 `labelDist = avgR + 26` 避免与圆圈重叠

## 主题10：路由导航 Bug — 静默失败排查（vpp-simulator-frontend）

> [!ai] AI整理标记
> 以下内容来自跨对话整理 — 项目：虚拟电厂仿真系统前端（代码对话，保留原文）

### 用户问题

> 现在点击顶部导航想要进入可调能力页面，但没有跳转路由，控制台也没有报错

> 现在我重启和刷新后点击导航还是无法进入可调能力页面

### 排查过程

**第一轮**：检查路由注册、RouterLink 配置、路由守卫 → 全部正确 → 怀疑 Vite HMR 未正确更新 → 建议重启

**用户反馈**：重启并硬刷新后问题依旧

**第二轮**：运行 `pnpm build` 生产构建 → **发现根本原因**

### 根因

`HistoryCalendar.vue` 从 `echarts/charts` 导入了 `CalendarChart`，而 **ECharts 5.5 中不存在该模块**。这个错误导入导致模块加载失败，Vite 开发模式下**静默**阻止了路由导航（不报错），生产构建会明确显示错误。

### 修复

```typescript
// 错误导入（CalendarChart 不存在于 ECharts 5.x）
import { CalendarChart } from 'echarts/charts'

// 正确用法：日历热力图只需这两个
import { HeatmapChart } from 'echarts/charts'
import { CalendarComponent } from 'echarts/components'
```

### 基础知识点

**ECharts 5.x 中日历热力图的正确用法**
- 系列类型是 `type: 'heatmap'`（使用 `HeatmapChart`），不是 `type: 'calendar'`
- `CalendarComponent` 提供日历坐标系
- 不存在独立的 `CalendarChart` 类

**Vite 开发模式 vs 生产构建的调试策略**
- 开发模式下模块加载失败可能**完全静默**（无控制台报错）
- 但会阻止依赖该模块的路由导航
- 生产构建会明确报出导入错误
- **当开发模式不报错但行为异常时，运行 `pnpm build` 是最有效的排查手段**

|---|---|---|

### 基础知识点

**Scrapy Pipeline 优先级**
- Pipeline 通过 `process_item()` 方法处理数据
- 数字越小优先级越高：`YouTubeVideoPipeline(950)` 在 `MinIOImagePipeline(1000)` 之前执行
- 数据先经过业务处理 Pipeline，再经过图片上传 Pipeline

**相对时间解析的陷阱**
- API 返回 "2天前"、"5小时前" 等相对时间文本
- 解析时需要同时支持中英文格式
- 需要覆盖所有时间级别：秒/分/时/天/周/月/年
- 边界数据（刚好在过滤阈值附近）可能被错误包含或排除

**view_count 存储的最佳实践**
- 数据库字段应使用数值类型（BigInteger），而非字符串
- 在 Pipeline 层一次性将 "4,417,277次观看" 转换为数字 4417277
- 保留原始文本字段用于展示，数值字段用于排序/过滤/聚合
